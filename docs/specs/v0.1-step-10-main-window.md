## 1. Purpose & Background

Step 10 creates the first real `QWidget` application surface and runnable entry point. It turns the existing Step 8 manager and Step 9 bridge into a visible, testable vertical slice: a `QMainWindow` shell renders the current state, updates when the bridge emits `state_changed`, and owns bridge teardown on close.

The release deliberately emphasizes a launchable MVC seam rather than final visual design. Menus, toolbar, docks, turn controls, and a central map area exist as stable placeholders so later rendering and action work can replace their contents without redesigning application construction or lifetime ownership.

## 8. Architecture and Design

### 8.1 Architecture Summary

`MainWindow` is built before the bridge so the bridge can use it as a Qt parent. `build_main_window()` then constructs the manager, bridge, and binding in that order and returns all three references. `main()` owns only GUI application lifecycle and the event loop. The view uses a `TYPE_CHECKING` bridge import for annotations and consumes state payloads opaquely; `app.py` is the composition root permitted to import model, controller, and view.

### 8.2 Architecture Views

#### 8.2.1 Context View

The user launches `python -m stmrr`. The application composition root constructs the MVC triad. Step 8 emits through Step 9; the main window updates its state indicator and owns teardown when the user closes the window.

#### 8.2.2 Container / Deployment View

The application is one Linux desktop process with one `QApplication` and one main window. Tests use an offscreen Qt platform and subprocesses for singleton states that cannot coexist in one process.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| `MainWindow` | Shell chrome, bridge consumption, and close ownership. | Constructor, `bind_bridge()`, `closeEvent()`. | No model imports. |
| `build_main_window()` | MVC composition and lifetime return values. | Zero-argument builder under an existing GUI application. | Fails clearly on misuse. |
| `main()` | GUI singleton, metadata, show, and event loop. | Returns integer exit code. | Reuses pytest-qt application. |
| `__main__.py` | Module execution adapter. | Raises `SystemExit(main())`. | One executable line. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Build the window bare and bind the bridge afterward. | The window must exist before the bridge can be parented to it. | Constructor injection creates a parent-order cycle. | ADR-0003 |
| D-002 | Amend the view event contract to permit indirect imports only. | It allows typed bridge annotations while continuing to forbid direct model-event access. | A local Protocol failed the verified Pyright descriptor check. | ADR-0003 |
| D-003 | Test fullscreen by action state and called method. | Offscreen window-manager state is unreliable. | `isFullScreen()` assertions were rejected by research and tests. | — |
| D-004 | Reuse or construct one GUI application and fail on `QCoreApplication`. | Qt permits one application singleton and widgets require the GUI subtype. | Unconditional application construction can raise or abort. | — |
| D-005 | Keep unwired controls disabled. | The visible shell must not advertise inert gameplay actions as available. | Enabled no-ops were rejected. | — |

> **§8.4 (Solution Alternatives Considered) is Full-tier** and is intentionally omitted at the Standard profile.

### 8.5 Design Constraints

- `main_window.py` imports no `stmrr.model.*`.
- The window is constructed before its bridge; binding occurs exactly once.
- Owner-side teardown precedes superclass close handling.
- Widget construction occurs only under a GUI `QApplication`.
- Offscreen tests assert requested Qt behavior, not unreliable window-manager outcomes.
- Placeholder controls remain disabled until their real handlers land.

> **§8.6 (Dependency Policy) is Full-tier** and is intentionally omitted at the Standard profile.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. `main()` obtains the live application or constructs a GUI application.
2. `build_main_window()` constructs the bare window, initial state manager, and window-parented bridge.
3. The window binds the bridge and renders the initial state.
4. `main()` shows the window and enters the Qt event loop.
5. Model transitions reach the window only through the bridge.
6. Window close tears down the bridge before superclass close handling.

Expected result: the application launches one wired shell, displays current state, and exits without stale model subscriptions.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | pytest-qt already owns a GUI application. | `main()` reuses the exact singleton and does not overwrite its metadata. | Smoke test returns without a second application. |
| AW-002 | A state payload lacks `to_state`. | The indicator displays `repr(payload)`. | The view remains model-type-agnostic. |
| AW-003 | The user toggles fullscreen. | The checkable action calls the matching full-screen or normal-window method. | Intent remains testable offscreen. |
| AW-004 | The window closes before a bridge is bound. | Close delegates normally without teardown. | No exception occurs. |

### 10.3 Edge Cases

| ID | Edge Case | Expected Behavior |
| --- | --- | --- |
| EC-001 | A non-GUI `QCoreApplication` already exists. | `main()` raises a clear `RuntimeError` instead of constructing widgets. |
| EC-002 | The builder is called without any application. | It raises a clear `RuntimeError` in the subprocess guard. |
| EC-003 | Offscreen Qt does not report fullscreen state. | Tests still pass by asserting the action and invoked method. |
| EC-004 | A direct model-event import is added to the view. | Import-linter reports a broken contract. |

### 10.4 State Transitions

The main window has no independent workflow state machine. It displays the Step 8 current state and follows the simple lifecycle `constructed → bound → shown → closed`; closing is terminal in v0.1.

#### Purpose

The **first `QWidget`-class module in the codebase** and the first runnable entry point. `view/main_window.py` is the empty `QMainWindow` shell from the scaffold step order (`tech-stack-pyside6.md` section 11 step 5 / `DESIGN.md` section 10.1 vertical-build step 5 — _"empty `QMainWindow` shell with menu bar and dock placeholders. Verify it launches."_). `app.py` is the entry point that builds the `QApplication`, wires the MVC triad (`GameStateManager` → `ModelBridge` → `MainWindow`), and shows the window; `__main__.py` makes `uv run python -m stmrr` launch it.

This step **closes the `app.py` deferral** recorded by SPEC-S009's scope and owner-side teardown contract: the bridge's owner is now real, so its lifetime contract — construct the GSM, construct `ModelBridge(manager, parent=main_window)`, and call `bridge.teardown()` owner-side in `MainWindow.closeEvent()` (never `destroyed.connect`) — is implemented here, not just specified.

The window is a **shell**: `MapView`/`GridScene`/items do not exist yet (`tech-stack-pyside6.md` section 11 steps 6–7), so the central area, dock contents, and most menu/toolbar actions are deliberate placeholders. The one piece of real behavior is the **minimal MVC seam consumer**: the window reads `bridge.current_state` for an initial state indicator and updates it on `bridge.state_changed`, proving the model→controller→view path end-to-end before any scene exists — which is the entire point of the vertical build order (`DESIGN.md` section 10.1 _"catches MVC seam issues in week one"_).

#### Layering and constraints

- **Amends one existing `import-linter` contract (no additional contract).** `main_window.py` annotates with `ModelBridge` under `TYPE_CHECKING`, creating a `stmrr.view.main_window → stmrr.controller.model_bridge` graph edge. **import-linter includes `TYPE_CHECKING` imports and checks _indirect_ chains by default** (verified empirically 2026-05-29 + Import Linter docs), so the existing `view-does-not-import-model-events` `forbidden` contract would flag the indirect `view → controller.model_bridge → model.events` path and break CI (SA-001). Fix: add `allow_indirect_imports = True` to that one contract — it then forbids only a **direct** `view → model.events` import (the dangerous edge that actually bypasses the bridge), while permitting the legitimate indirect path through the bridge. **Empirically verified (2026-05-29):** with the amendment, a `TYPE_CHECKING` `ModelBridge` import yields `5 kept / 0 broken`, _and_ a direct `from stmrr.model.events import …` in a view module still reports `BROKEN` — the contract keeps its teeth. This mirrors the two existing seam contracts (`blinker-only-in-events`, `controller-events-via-bridge-only`), which already use `allow_indirect_imports = True` for the same reason. (A local `Protocol` to avoid the import entirely was tried first and **rejected** — the historical May 2026 probe passed mypy but failed Pyright on a `Signal`/`SignalInstance` descriptor mismatch; see the rejected-alternatives table.)
- **`view-does-not-import-model-events` (amended) is honored.** `main_window.py` imports **no** `stmrr.model.*` at all (its only cross-layer import is the `TYPE_CHECKING` `ModelBridge`). It treats the `state_changed` payload opaquely (`payload: object`) and reads the _class name_ of `bridge.current_state` without importing `GameState`. This keeps the view aligned with the repository's Qt-free-model and single-MVC-seam conventions.
- **`app.py` (`stmrr.app`) is governed by none of the view/controller `forbidden` contracts** (they scope `stmrr.view` / `stmrr.controller`). It may freely import `GameStateManager`, `MainMenuState` (model.state), `ModelBridge` (controller), and `MainWindow` (view). It does **not** import `model.events` — the bridge is the only events importer (the `controller-events-via-bridge-only` contract is unaffected).
- **Imports** (runtime vs `TYPE_CHECKING`) in `main_window.py`:
  - **Runtime:** `from PySide6.QtCore import Qt` (dock-area + alignment enums), `from PySide6.QtGui import QAction, QCloseEvent`, `from PySide6.QtWidgets import (QMainWindow, QWidget, QLabel, QDockWidget, QTextEdit, QToolBar, QPushButton, QMessageBox, QVBoxLayout)`, `from stmrr import __version__` (root package only — for the About text; **not** a `model.*` import, and `stmrr/__init__.py` pulls in no submodules).
  - **`TYPE_CHECKING` only:** `from stmrr.controller.model_bridge import ModelBridge` (annotation on `bind_bridge` / the `_bridge` attribute; the instance is injected at runtime — no hard runtime coupling to the controller).
  - Python 3.14-native annotation semantics apply; a universal `from __future__ import annotations` directive is no longer required.
- **Static typing:** `[tool.basedpyright]` governs source and tests in strict mode. All three files are fully annotated and pass the current repository gate.
- No new dependencies (`PySide6`, `loguru`, `pytest-qt` already declared).
- Module + class docstrings mandatory. Method docstrings on `bind_bridge` (seam-consumer rationale), `closeEvent` (owner-side teardown order — non-obvious), and `build_main_window` (the testable-seam rationale).

**`bind_bridge(bridge)`** (the minimal-but-real seam consumer):

```python
def bind_bridge(self, bridge: ModelBridge) -> None:
    """Attach the model→view seam: initial render + live state tracking.

    Stores the bridge for owner-side teardown (closeEvent), renders the initial
    mode from `current_state` (the step-9 initial-render hook, before any
    transition fires), and tracks subsequent transitions via `state_changed`.
    The payload is treated opaquely (`object`) so the view imports no model.events.

    Does NOT (re)parent the bridge — the caller (`app.py`) constructs it already
    parented via `ModelBridge(manager, parent=window)`; bind_bridge only stores
    the reference, renders, and connects. Calling it twice would stack a second
    `state_changed` connection — v0.1 binds exactly once at startup.
    """
    self._bridge = bridge
    self._state_indicator.setText(type(bridge.current_state).__name__)
    bridge.state_changed.connect(self._on_state_changed)
```

**`_on_state_changed(payload)`**:

```python
def _on_state_changed(self, payload: object) -> None:
    # View slot: payload is opaque (no model.events import). StateChangedPayload
    # carries `to_state: type[GameState]`; read it duck-typed.
    to_state = getattr(payload, "to_state", None)
    name = to_state.__name__ if isinstance(to_state, type) else repr(payload)
    self._state_indicator.setText(name)
```

**`_on_fullscreen_toggled(checked)`**: `self.showFullScreen()` if `checked` else `self.showNormal()`. (Tested via the action's `isChecked()` + a mock on `showFullScreen`/`showNormal`, **never** `isFullScreen()` — research #4.)

**`_show_about()`**: `QMessageBox.about(self, "About Star Trek Retro Remake", f"...{__version__}...")` using `stmrr.__version__`. (Tested by monkeypatching `QMessageBox.about` — research #8.)

**`closeEvent(event)`** (owner-side teardown — research #3, SPEC-S009 owner-side teardown contract):

```python
def closeEvent(self, event: QCloseEvent) -> None:
    """Release the bridge's blinker subscriptions at window close (exit-only).

    Step-10 close is an EXIT path: v0.1 leaves `quitOnLastWindowClosed` at Qt's
    default (True), so closing the main window quits the event loop and the
    process exits — there is NO reopen-after-close. (Accepting a close event only
    HIDES the widget unless `WA_DeleteOnClose` is set, which step 10 does not set;
    the process exit is what tears everything down — SA-005.) teardown() runs
    before super().closeEvent() as defensive ordering: it releases the blinker
    subs (bridge ← model events) while the bridge is unambiguously alive; the
    Qt-signal half (view slots ← bridge signals) is Qt object-tree parenting's
    job. NOT wired via destroyed.connect (SPEC-S009 owner-side teardown contract / SA-002). Reopen
    support, if ever needed, would require re-binding a fresh bridge — out of
    scope for v0.1.
    """
    if self._bridge is not None:
        self._bridge.teardown()
    super().closeEvent(event)
```

##### `app.py` — entry point

```python
import sys

from loguru import logger
from PySide6.QtWidgets import QApplication

from stmrr import __version__
from stmrr.controller.model_bridge import ModelBridge
from stmrr.model.state.game_state_manager import GameStateManager
from stmrr.model.state.states import MainMenuState
from stmrr.view.main_window import MainWindow


def build_main_window() -> tuple[MainWindow, ModelBridge, GameStateManager]:
    """Construct and wire the MVC triad; return all three for lifetime ownership.

    The testable seam: no QApplication creation, no exec(). **Requires a GUI
    QApplication to already exist** (main() or pytest-qt creates it). Constructing
    a QWidget without one aborts the process at the C++ level, so this public,
    importable seam fails fast with a clear RuntimeError instead (CR-002). The
    single isinstance guard covers both no-app (instance() is None) and a non-GUI
    QCoreApplication singleton. Order matters — the window must exist before the
    bridge so the bridge can be Qt-parented to it (SPEC-S009 owner-side teardown contract). Returns the bridge
    and manager so the caller holds Python refs that keep them alive (PySide6
    parenting does NOT pin the Python wrapper, and blinker holds the bridge with
    weak=False — research #5).
    """
    if not isinstance(QApplication.instance(), QApplication):
        raise RuntimeError(
            "build_main_window() requires a GUI QApplication; call stmrr.app.main() "
            "or construct a QApplication first."
        )
    manager = GameStateManager(MainMenuState())
    window = MainWindow()
    bridge = ModelBridge(manager, parent=window)
    window.bind_bridge(bridge)
    return window, bridge, manager


def main() -> int:
    """Build/reuse the QApplication, show the main window, run the event loop."""
    logger.info("Starting Star Trek Retro Remake v{}", __version__)
    app = QApplication.instance()
    if app is None:
        # Only when WE create the app: own it and set metadata. Under pytest-qt a
        # session QApplication already exists (SA-002); reusing it avoids the
        # "destroy the QApplication singleton before creating a new one"
        # RuntimeError, and NOT mutating its name/org keeps the shared test app
        # pristine for other tests.
        app = QApplication(sys.argv)
        app.setApplicationName("Star Trek Retro Remake")
        app.setOrganizationName("star_trek_retro_remake")  # conventional application metadata
    elif not isinstance(app, QApplication):
        # A non-GUI QCoreApplication already exists: instance() returns IT (not
        # None — verified 2026-05-29). Widgets cannot be constructed under it, and
        # a second QApplication cannot replace a live singleton. Fail clearly
        # instead of the cryptic C++ abort "QWidget: Cannot create a QWidget
        # without QApplication" (SA-006).
        raise RuntimeError(
            "stmrr requires a GUI QApplication, but a non-GUI QCoreApplication "
            "already exists; cannot start the main window."
        )
    # After the branches above, `app` is narrowed to QApplication.
    window, _bridge, _manager = build_main_window()
    window.show()
    return app.exec()
```

- **`build_main_window()` requires (does not create) a GUI `QApplication`** — it raises a clear `RuntimeError` if none exists or if the singleton is a non-GUI `QCoreApplication` (CR-002), rather than letting `MainWindow()` abort the process at the C++ level. `main()` satisfies this by ensuring the app first; tests satisfy it via `qtbot`. The guard's `raise` is exercised by the subprocess coverage case and is not counted by the in-process coverage run.
- **`main()` reuses an existing `QApplication`** via `QApplication.instance()`, constructing one only when absent (SA-002), and **rejects a non-GUI `QCoreApplication`** singleton with a clear `RuntimeError` rather than aborting on `MainWindow` construction (SA-006 — `instance()` returns the `QCoreApplication`, not `None`; verified 2026-05-29). The reuse-safety makes the `main()` smoke test safe under pytest-qt (whose session `qapp` exists); a second `QApplication(sys.argv)` would raise `RuntimeError: Please destroy the QApplication singleton…` (reviewer-probed). After the guard block, `app` is narrowed to `QApplication`, so `app.exec()` typechecks with no cast (this resolves the earlier A-018 union-typing caveat).
- `build_main_window` keeps the bridge + manager referenced via the returned tuple; `main` binds them to `_bridge`/`_manager` locals that live for the duration of `exec()`. The window also holds `self._bridge`; the bridge holds `self._manager`. Both the Qt parent **and** the Python ref are present (research #5).
- `setApplicationName`/`setOrganizationName` are set **only on an app `main` itself constructs**, before any widget or `QSettings` — conventional startup hygiene under the application-metadata decision. They do not, alone, establish the design's exact INI path (SA-003).
- loguru's default stderr sink is used as-is (one `info` line) — sufficient for DoD #1 _"no errors in the loguru log."_ No custom sink configured this step.

#### Cross-cutting design decisions

##### Window built bare, bridge attached via `bind_bridge` (chicken-and-egg)

SPEC-S009's owner-side teardown contract specifies `ModelBridge(manager, parent=main_window)` — the bridge is parented to the window, so the **window must be constructed first**. A constructor that took the bridge would invert that order. `bind_bridge()` resolves it: build the window, build the bridge parented to it, then attach. `bind_bridge` is also the natural home for the initial-render hook and the `state_changed` connection, and it makes the seam independently testable (construct a window, call `bind_bridge(fixture_bridge)`, assert it reacts).

##### The minimal seam consumer is real, not ceremonial

With no scene or status panels yet, the window has little model state to render — but rendering _something_ from `current_state` + `state_changed` is what proves the model→controller→view path in week one (`DESIGN.md` section 10.1). The `_state_indicator` label is that consumer: it shows `"MainMenuState"` at startup (SPEC-S009 initial-render hook) and updates on every transition. It is replaced/augmented by real dock panels in later steps, but the seam it exercises is permanent.

##### The view imports no `model.*`; payload is opaque

`view-does-not-import-model-events` forbids `stmrr.view → stmrr.model.events`. Rather than import the payload type from elsewhere, the slot annotates `payload: object` and reads `to_state` duck-typed (`getattr` + `isinstance(to_state, type)`), and the initial render reads `type(current_state).__name__`. No `stmrr.model.*` import appears in `main_window.py` at all — the strongest form of the decoupling, and it sidesteps any debate about whether `view → model.state` (a non-events model import) is acceptable.

##### Fullscreen as a checkable `QAction`; tested by intent, not WM outcome (research #4)

The `offscreen` QPA plugin (mandated by the repository's headless-test convention) has no window manager and does **not** reliably report `isFullScreen()`/`hasFocus()`/`isActiveWindow()`. So F11 is a **checkable** `QAction` whose `toggled(bool)` drives `showFullScreen()`/`showNormal()`, and the test asserts (a) the action's `isChecked()` flipped and (b) `showFullScreen`/`showNormal` was _called_ (mock), never the realized WM state. `setMinimumSize` and programmatic geometry **are** reliable under offscreen and may be asserted directly.

##### `app/organizationName` now, `QSettings` later (SA-003 corrected)

Persistence (DoD #8) is deferred. Setting application/organization names at startup is conventional hygiene and avoids the `QSettings.status() == AccessError` a default-constructed `QSettings()` hits when they are unset (research #9). **But it does not establish the design's `~/.config/star_trek_retro_remake/window_state.ini` path** — default `QSettings()` on Unix uses NativeFormat (`.conf`), and the exact `.ini` filename requires the explicit `QSettings(path, QSettings.IniFormat)` constructor. That filename/format decision belongs to the persistence step (SA-003); Step 10 only sets the names, and only on an app it constructs under the application-construction contract.

##### `build_main_window()` / `main()` split for testability (research #2)

`exec()` blocks; pytest-qt already runs its own loop, so tests must never call the real `exec()`. Splitting wiring (`build_main_window`, no loop) from the loop (`main`) lets tests exercise all wiring directly and smoke-test `main()` by monkeypatching `QApplication.exec`. The split also keeps each function within one screen.

##### Disabled placeholders, not enabled no-ops (review: missing consideration)

Every unwired menu/toolbar/turn-bar action is created `setEnabled(False)`, not left enabled-but-inert. An enabled control that silently does nothing on click is a UX defect and an ambiguous test target; a disabled (greyed) control honestly reads "not yet available." Later steps flip `setEnabled(True)` as they wire each action to `action_handlers`. Only the five self-contained actions (Exit, Fullscreen, two dock toggles, and About) ship enabled.

#### Invariants

Properties step 10 contributes; a reviewer should probe these.

1. **`python -m stmrr` launches the window** (DoD #1) — `__main__.py` → `app.main()` → `QApplication` + `MainWindow().show()` + `exec()`, with a loguru startup line and no errors.

5. **The seam is live end-to-end.** Binding a bridge renders the initial state name; a real model `transition_to` updates it via blinker → bridge Qt signal → view slot. Pinned by the focused main-window tests.

7. **Window minimum size is 1600×1000** (`DESIGN.md` section 6.5) — reliable under offscreen, asserted directly.
8. **`stmrr.view` re-exports `MainWindow`** with `__all__ == ["MainWindow"]` (mirrors the Step 8/9 package-export discipline). Pinned by the focused package-export test.

## 12. Error Handling and Recovery

### 12.1 Expected Failures

| ID | Failure Mode | User/System Behavior | Logging / Observability | Recovery |
| --- | --- | --- | --- | --- |
| ERR-001 | `build_main_window()` runs without a GUI application. | A clear `RuntimeError` replaces a potential C++ abort. | Subprocess stderr and exit status prove the guard. | Construct or reuse `QApplication` before calling the builder. |

| ERR-004 | Window close occurs before bridge binding. | Close completes without teardown or error. | Unbound close regression test passes. | No recovery needed. |
| ERR-005 | Bridge teardown raises during close. | The exception remains visible rather than silently leaving a stale receiver. | Test or application exception reporting observes it. | Repair teardown before relaunch; no hidden retry occurs. |

### 12.2 Retry and Idempotency

Application construction and widget actions are not automatically retried. Repeated user fullscreen toggles are valid state changes. Close is terminal in v0.1. A failed startup may be retried only after the GUI-singleton precondition is corrected.

### 12.3 Rollback / Recovery

Step 10 persists no state, so rollback is code-level: close the process and run the prior verified revision. A startup guard fails before constructing the triad. If close teardown fails, the process should exit rather than reopen the same window under uncertain subscriptions.

## Appendix B: Agent Implementation Contract

Binding when this spec is implemented by a coding agent. (Applies equally well to human contractors.)

### B.1 Implementation Rules

The implementer shall:

- Read this entire specification before making changes; per session thereafter, re-read at minimum §7 (Requirements), §21 (Open Questions), and the Deviations Log — Background and References may be read once.
- Preserve all explicit non-goals, won't-haves, constraints, and design constraints.
- Treat **Must** requirements as mandatory and **blocking** open questions as hard stops for the affected work.
- On encountering underspecified behavior: file an `OQ-` row **with a proposed default assumption** and proceed on it only if non-blocking — never guess silently.
- On any divergence from the spec: record a `DEV-` row (spec reference, what, why) rather than adapting silently.
- Add or update tests for every implemented requirement; keep §17.3 (traceability) current.
- Follow the milestone order in §19; do not build later milestones on unproven earlier ones.
- Prefer small, reviewable changes; avoid broad refactors unless the spec requires them.
- Document any discovered mismatch between the spec and existing code as a `DEV-` or `OQ-` row.

### B.2 Prohibited Behaviors

The implementer shall not:

- Invent requirements not present in this spec.
- Remove existing behavior unless explicitly required.
- Introduce external services or dependencies not agreed with the owner without an approved `OQ-`.
- Store secrets in source control or print them in CI logs.
- Ignore failing tests unrelated to the change without documenting them.
- Treat examples as exhaustive or normative unless explicitly stated.
- Mark a requirement complete without a verification entry in §17.3.

### B.3 Required Completion Report (verification gate)

At completion, provide:

- Summary of changes and files changed.

- Deviations (`DEV-` rows) and their approval status.
- Known limitations and remaining open questions.
- Documentation deliverables completed (§18.7).

### B.4 Session Handoff

For multi-session implementations: record current milestone, in-progress requirement IDs, and unresolved `OQ-`/`DEV-` items in the repository's session-state/handoff documents at the end of each session, per the repo's documentation convention.
