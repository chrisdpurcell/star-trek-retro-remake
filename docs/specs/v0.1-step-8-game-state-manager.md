## 1. Purpose & Background

Step 8 closes the v0.1 model layer's controller-pivot surface. It provides a headless, hand-rolled manager for deterministic state transitions and the two concrete states needed to move between the main menu and sector map. The manager must expose a stable current state, run lifecycle hooks in a fixed order, and publish one typed model event only after a successful transition.

The first release deliberately keeps state hooks empty and world ownership at the wire-up layer. That preserves ADR-0003's Qt-free model boundary and leaves later controller, persistence, tracing, and additional-state work possible without changing the v0.1 lifecycle contract.

## 2. Scope

### 2.1 In Scope

- `GameStateManager` construction, read-only state access, transition validation, lifecycle ordering, failure postconditions, and `state_changed` emission.
- `MainMenuState` and `SectorMapState`, including their mutual transition sets and no-op lifecycle hooks.
- State-package exports, model-boundary enforcement, focused tests, and the coordinated umbrella-spec corrections recorded in the preserved contract.

## 6. Glossary

| Term | Definition | Notes / Not to be confused with |
| --- | --- | --- |
| Current state | The entered `GameState` instance exposed by the manager's read-only property. | It is not a state class or persisted discriminator. |
| Allowed transition | Membership of the target's exact class in the current state's class-valued transition set. | Subclasses are not accepted by inheritance alone. |
| Lifecycle hook | A state's synchronous `enter()` or `exit()` method. | v0.1 concrete hooks are intentionally no-ops. |
| Committed transition | The point after `_current_state` is assigned to the target. | An `enter()` failure occurs after commitment but before event emission. |

## 8. Architecture and Design

### 8.1 Architecture Summary

`GameStateManager` is a plain Python orchestrator. It runtime-imports only the model event and exception modules; `GameState` is used for annotations without a runtime backedge. The two concrete states remain stdlib-only model classes. The manager publishes through blinker, and Step 9 translates that event at the sole Qt seam.

### 8.2 Architecture Views

#### 8.2.1 Context View

The wire-up layer constructs the initial state and manager. Model callers request transitions. The manager invokes state hooks and emits one model event; the controller bridge observes that event.

#### 8.2.2 Container / Deployment View

The state modules run in-process in the Linux desktop application and in headless pytest processes. They have no independent service, datastore, or deployment unit.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| `game_state_manager.py` | Current-state ownership and transition lifecycle. | Constructor, property, `transition_to()`. | Plain Python; no Qt. |
| `states.py` | Base-state contract and v0.1 concrete graph. | Three state classes and class-valued transition sets. | Mutual reference patched after class creation. |
| `model.events` | Transition notification. | `state_changed`, `StateChangedPayload`. | Existing Step 5 surface. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Use an explicit five-step transition lifecycle. | Hook and subscriber observations remain deterministic. | Implicit callbacks would obscure ordering. | ADR-0005 |
| D-002 | Resolve the two-state cycle with post-class assignments. | Both classes declare the required attribute without string registries or import cycles. | String names and lazy properties were rejected. | ADR-0005 |
| D-003 | Propagate hook failures without rollback. | The behavior follows directly from lifecycle position and avoids hidden recovery. | Automatic rollback would require compensating hooks and new policy. | — |
| D-004 | Keep state hooks empty in v0.1. | World ownership and UI cueing already have separate architectural owners. | Constructing world objects or logging in each hook was rejected. | ADR-0003 |

> **§8.4 (Solution Alternatives Considered) is Full-tier** and is intentionally omitted at the Standard profile.

### 8.5 Design Constraints

- The lifecycle order is `validate → exit → mutate → enter → emit`.
- Exact target classes, not inheritance or instance identity, govern validation.
- `state.states` remains a runtime leaf.
- State hooks do not construct world entities or perform UI cueing.
- Reentrant transitions from an event receiver remain unsupported in v0.1.

> **§8.6 (Dependency Policy) is Full-tier** and is intentionally omitted at the Standard profile.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. The wire-up layer constructs `MainMenuState`.
2. `GameStateManager` retains it and calls `enter()` without emitting an event.
3. A caller requests transition to `SectorMapState`.
4. The manager validates the exact class, exits the menu state, commits the target, enters it, and emits one payload.
5. A subscriber observing the event sees the target as `current_state`.

Expected result: the manager and subscribers agree on one entered current state.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | A caller requests a self-transition or identity-equal target. | Exact-class validation rejects the target. | `IllegalTransitionError`; no lifecycle or event side effect. |
| AW-002 | A caller transitions back from sector map to main menu. | The same five-step lifecycle runs in the opposite direction. | One entered menu state and one event. |

### 10.3 Edge Cases

| ID | Edge Case | Expected Behavior |
| --- | --- | --- |
| EC-001 | `exit()` raises. | The outgoing instance remains current and no event is sent. |
| EC-002 | `enter()` raises. | The target remains current and no event is sent. |
| EC-003 | A receiver reads `manager.current_state` during event delivery. | It observes the entered target instance. |
| EC-004 | The post-class patch is removed. | Focused transition-set tests fail because both sets remain empty. |

### 10.4 State Transitions

| State | Meaning | Entry Condition | Exit Condition |
| --- | --- | --- | --- |
| `MainMenuState` | v0.1 session start/menu mode. | Initial construction or valid transition from `SectorMapState`. | Valid transition to `SectorMapState`. |
| `SectorMapState` | v0.1 in-game sector mode. | Valid transition from `MainMenuState`. | Valid transition to `MainMenuState`. |

Self-transitions and every other class transition are invalid.

#### Purpose

Two artifacts that close the v0.1 model layer's **controller-pivot surface** — the hand-rolled state machine plus its two concrete states:

- `model/state/game_state_manager.py` — `GameStateManager(initial_state: GameState)`: holds `current_state: GameState`; method `transition_to(target: GameState) -> None` runs the SPEC-ML01 FR-011 five-step `validate → exit → mutate → enter → emit` lifecycle, raises `IllegalTransitionError` (already declared in `model/exceptions.py:76-82`) on disallowed transitions, emits `state_changed` (already declared in `model/events.py:76`) with `StateChangedPayload(from_state, to_state)` carrying class objects (`type[GameState]`), not instances.
- `model/state/states.py` — extends the existing ABC stub (step 5, HEAD `5420568`) with two concrete subclasses: `MainMenuState`, `SectorMapState`. Each declares `allowed_transitions: ClassVar[frozenset[type[GameState]]]` pointing at the _other_ class. Mutual reference is resolved by the preserved post-class patch contract.

They land together because (a) `state.game_state_manager` cannot be tested in isolation — its happy-path `transition_to` requires two concrete `GameState` subclasses with non-empty `allowed_transitions` sets that reference each other (a single concrete state with `allowed_transitions = frozenset()` can only test the rejection path); (b) the post-class patch idiom is a cross-module concern between the manager's validation contract and the states' attribute lifecycle — bundling them surfaces this in one review; (c) together they satisfy SPEC-ML01's "main-menu shell + sector load" DoD prerequisites (the controller bridge layer that drives the transitions lands at step 9+; step 8's completion is the model-layer surface, not the user-visible behavior).

This spec also identifies and amends three stale rows in `v0.1-model-layer.md`: two module-surface rows under-specified what Step 8 ships, and the `state.game_state_manager` runtime-DAG row over-declared `state.states` as a runtime import. That stale edge came from an earlier defensive-`isinstance` design rejected by the Q4 lock. The preserved umbrella-amendment instructions retain the exact replacements.

```python
    lifecycle `validate → exit → mutate → enter → emit`.
    `__init__` fires the initial state's `enter()` synchronously (no
    `state_changed` event for construction — see SPEC-S008's Q2 lock).

    World ownership rule (SPEC-ML01 FR-018): instances of `SectorMap` and other
    runtime entities are NOT constructed in any `GameState.enter` body;
    `app.py` (or a wire-up session object) owns world construction.
    `GameStateManager` knows only about states.
    """

    def __init__(self, initial_state: GameState) -> None: ...
    @property
    def current_state(self) -> GameState: ...
    def transition_to(self, target: GameState) -> None: ...
```

##### `__init__(initial_state)` semantics

1. Store `initial_state` on a private attribute (`self._current_state`).
2. Call `initial_state.enter()` synchronously.
3. Do NOT emit `state_changed`. Lifecycle invariant: every observable `current_state` has been entered and not yet exited; construction is the only path that satisfies the invariant without an event.

**No defensive `isinstance(initial_state, GameState)` check** — the type annotation is the contract; BasedPyright strict enforces typed call sites. (Per the Q4 lock, defensive `isinstance` adds runtime cost and a parallel exception type for a footgun the type system already catches.)

##### `current_state` property

Returns `self._current_state`. Read-only — no setter. The only mutation path is `transition_to`. This is enforced by convention (no `@current_state.setter`), not by `__setattr__` machinery; the underscore-prefixed `_current_state` signals "do not write" to readers.

##### `transition_to(target: GameState) -> None` semantics

Runs the five-step lifecycle per SPEC-ML01 FR-011. The order is load-bearing; subscribers reading `manager.current_state` inside a `state_changed` handler MUST see the new state.

1. **Validate**: `if type(target) not in self._current_state.allowed_transitions: raise IllegalTransitionError(from_state=type(self._current_state), to_state=type(target))`. Note `type(target)` — the validation set holds class objects (`type[GameState]`), not instances. `IllegalTransitionError` is declared in `model/exceptions.py:76-82` (step 5) with the exact `from_state`/`to_state` kwarg signature this method uses.
2. **Exit**: `self._current_state.exit()`. The outgoing state is still bound to `self._current_state` at this point — `exit()` may read it via the manager if needed (though v0.1's `pass` bodies do not).
3. **Mutate**: `from_state_cls = type(self._current_state); self._current_state = target`. Capture `from_state_cls` BEFORE the assignment — needed for the payload in step 5.
4. **Enter**: `target.enter()`. The new state is now bound to `self._current_state`.
5. **Emit**: `state_changed.send(self, payload=StateChangedPayload(from_state=from_state_cls, to_state=type(target)))`. Sender is the manager instance (`self`); payload carries class objects.

**Idempotence is data-driven, not code-driven.** Self-transitions (target is the same class as `current_state`) raise `IllegalTransitionError` because neither concrete transition set includes its own class. No explicit `if type(target) == type(current_state): ...` branch exists.

**Identity short-circuit is NOT performed.** `if self._current_state is target: return` is rejected by the Q6 lock; composition handles it because the target class is not in the allowed set.

**Receiver exceptions during `state_changed.send`** propagate per SPEC-ML01 ERR-006. The state mutation has already committed before `send()` is called; a buggy receiver leaves the manager in a consistent state but raises out of the caller's `transition_to` call. v0.1 inherits SPEC-S007 WH-005; mitigation (`_send_robust`) lands when a second non-bridge subscriber connects.

#### Cross-cutting design decisions

##### Why `pass` bodies for `enter`/`exit` in v0.1

Per SPEC-ML01 FR-018, state lifecycle hooks are "for view/UI cueing, not constructors". The model layer does not do UI cueing — cueing happens via the `state_changed` event, which `controller/model_bridge.py` (Step 9+) converts to a Qt signal. So `enter`/`exit` bodies on the model side may stay `pass` permanently for these two states.

Alternatives considered and rejected:

- **`loguru.logger.debug(...)`** — adds a runtime dependency import to `state.states`, which is otherwise a pure-stdlib leaf in the SPEC-ML01 Runtime DAG. Marginal value; the `state_changed` event already gives observers a hook. **Defer**; if trace logging is wanted, add it once and globally in `GameStateManager.transition_to` rather than peppering every state class.
- **`raise NotImplementedError`** — these ARE the concrete classes; there is nothing further to delegate to. Wrong tool.
- **World construction (e.g., `self.sector_map = SectorMap(8, 8, 10)`)** — forbidden by SPEC-ML01 FR-018. Spec must call this out as a non-negotiable.

##### Mutual-class-reference resolution (Q1)

Python has no forward-class declaration syntax. The two viable patterns are:

- **(A) Post-class module-level patch (chosen).** Empty `frozenset()` in each class body satisfies `__init_subclass__`; module-level assignments after both classes exist update to the real sets. The preserved post-class patch above is authoritative.
- **(B) `classmethod` resolving the set on each call.** Breaks the umbrella + step-5 contract (`allowed_transitions` is data, not a method) and the `__init_subclass__` `vars(cls)` check. Rejected.

Research per [`docs/research/2026-05-26-v0.1-step-8-open-questions.md`](../research/2026-05-26-v0.1-step-8-open-questions.md) section Q1.

##### Self-transition forbidden by composition (Q5)

`MainMenuState.allowed_transitions = frozenset({SectorMapState})` does NOT include `MainMenuState`. A caller doing `manager.transition_to(MainMenuState())` while `current_state` is already a `MainMenuState` instance hits the validation step's `type(target) not in current_state.allowed_transitions` branch and raises `IllegalTransitionError`. No special-case code in `transition_to`.

This is observable behavior: the focused manager suite asserts that `MainMenu → MainMenu` raises. If a future PR adds `MainMenuState` to its own `allowed_transitions`, the test fails and forces the author to justify the change.

##### Lifecycle invariant: every observable state is entered

`GameStateManager.__init__` calls `initial_state.enter()` synchronously. Lifecycle invariant: every state reachable as `manager.current_state` has had `enter()` called exactly once and has not yet had `exit()` called.

The asymmetry: `__init__` fires `enter()` but does NOT emit `state_changed`. `transition_to` fires BOTH. This is intentional — `state_changed` semantically means "a transition occurred", and construction is not a transition. Subscribers that need to react to the starting state read `manager.current_state` directly after constructing the manager (or after connecting to the signal, depending on the wire-up order).

A reviewer may want to "fix" this asymmetry by emitting `state_changed` in `__init__` with `from_state=None`. **Reject** — `StateChangedPayload.from_state` is typed `type[GameState]`, not `type[GameState] | None`; widening the type for one construction edge case ripples through every subscriber. The construction and validation-gate evidence pins the approved asymmetry.

##### Lifecycle hook exception policy

v0.1 concrete states have `pass` bodies under the no-op-hook decision, so the question of "what if `enter()` or `exit()` raises?" is moot for production code paths. But `GameStateManager` accepts any `GameState` subclass, as the manager probe tests demonstrate, and a later state with non-trivial hook bodies could raise. The spec locks the policy now so the implementation cannot silently choose a different one.

**Policy: hook exceptions propagate; no rollback. Postconditions differ by hook.**

| Failing hook | `current_state` after raise | `state_changed` emitted? | `target.enter()` called? |
| --- | --- | --- | --- |
| `self._current_state.exit()` raises | Unchanged (still the outgoing instance) | No | No |
| `target.enter()` raises | The new `target` instance (mutation already committed) | No | (the raising call) |

**Rationale:**

- The five-step `transition_to()` lifecycle places `exit()` before mutation; if `exit()` raises, mutation has not happened, so leaving `current_state` pointing at the outgoing instance is consistent.
- `enter()` runs after mutation but before the event. If `enter()` raises, mutation has already committed; rolling back (`self._current_state = outgoing_state_capture`) would require a new local variable and a try/except — added complexity for a v0.1 scenario where the hook bodies are `pass`. The simpler "no rollback" policy is honest about the partial-transition reality: the caller sees an exception and the manager state matches what step 4 of the lifecycle just wrote.
- No `state_changed` emitted in either case — the event semantically means "a transition completed", which it did not.
- Receiver exceptions during the `state_changed.send()` lifecycle step are a separate concern handled by SPEC-ML01 ERR-006; by the time `send()` runs, both hooks have completed successfully.

Comparison points: `transitions` (pytransitions) documents that exceptions raised by callbacks halt processing of further callbacks but do not roll back the state change itself; `python-statemachine` exposes a `catch_errors_as_events` flag for opt-in fault isolation. v0.1's policy aligns with `transitions`' default (propagate, no rollback) and explicitly defers any fault-isolation work to v0.2 (alongside the `_send_robust` deferral inherited from step 7).

Two focused manager-test rows, one per failing hook, assert exception propagation, no event emission, and the documented `current_state` postcondition.

#### Invariants

Properties step 8 contributes that the rest of the model layer relies on; reviewer should probe these.

1. **`GameStateManager.current_state` is read-only at the public surface.** No `@current_state.setter`; the underscore-prefixed `_current_state` private attribute is the sole write site, and `transition_to` is the sole writer (with `__init__` performing the initial assignment).
2. **The five-step transition order `validate → exit → mutate → enter → emit` is locked.** `exit()` runs before `self._current_state = target`; `enter()` runs after the mutation but before `state_changed.send()`. Subscribers reading `manager.current_state` inside a `state_changed` handler see the post-mutation state (SPEC-ML01 FR-011; pinned by the focused manager suite).
3. **`from_state` in `StateChangedPayload` is captured BEFORE the mutation.** Captured into a local `from_state_cls` variable in step 3 of the lifecycle, before `self._current_state = target` runs. Tested via an inequality assertion on a MainMenu → SectorMap transition.
4. **`StateChangedPayload` field types are class objects (`type[GameState]`), not instances.** Subscribers compare by type, never by instance reference — keeps subscribers stateless. **Save/load alignment:** class objects are NOT directly representable in the TOML save schema (per ADR-0004, the writer is `tomli_w`, which serializes only primitives, lists, and dicts; stdlib `tomllib` is parse-only); persisting them is a v0.2 persistence-spec concern under SPEC-ML01 WH-003. The likely v0.2 mapping is fully-qualified-name strings (`"stmrr.model.state.states.MainMenuState"`) with a registry-driven reverse lookup on deserialization. v0.1 does not implement persistence; the design only ensures the payload shape is compatible with that future mapping. Instance-carrying alternatives (storing state instances in the payload) would force the persistence layer to deal with construction kwargs at load time — a harder problem.
5. **`__init__` does NOT emit `state_changed`.** The construction lifecycle is asymmetric with `transition_to` by design. Every observable `current_state` has had `enter()` called and not yet had `exit()` called; construction is the only path that satisfies the invariant without emitting an event.
6. **Self-transitions are forbidden by composition, not by code.** Neither `MainMenuState.allowed_transitions` nor `SectorMapState.allowed_transitions` includes its own class. `transition_to` has no `if type(target) is type(current_state): return` short-circuit; the validation step raises `IllegalTransitionError` naturally.
7. **Identity-equal targets are also forbidden by composition.** `manager.transition_to(manager.current_state)` raises `IllegalTransitionError` under the same SPEC-S008 FR-005 and FR-011 transition-set rule used for all self-transitions: `type(current_state)` is not in its own `allowed_transitions`. No `if self._current_state is target: return` short-circuit.
8. **Step 5's `__init_subclass__` enforcement at `states.py:33-51` is untouched.** Step 8 only adds concrete subclasses below the ABC; the ABC body, the `__init_subclass__` method, and the abstract `enter`/`exit` declarations remain at their step-5 positions and behavior.
9. **`MainMenuState.allowed_transitions` and `SectorMapState.allowed_transitions` are non-empty `frozenset` instances at module import time.** The preserved post-class patch runs at import. Concrete-state smoke tests catch accidental deletion of either assignment.
10. **`state_changed.send` is synchronous** (inherited from SPEC-ML01 FR-015 and SPEC-S007 D-006). Any receiver exception propagates out of `transition_to` while the state mutation is already committed. v0.1 accepts the bounded risk (one known-safe subscriber: the controller bridge); v0.2 mitigation is the `_send_robust` utility under SPEC-S007 WH-005.
11. **No back-edges from `state.*` to entities or combat.** `state.game_state_manager` runtime-imports only `events` and `exceptions`; `state.states` is imported under `TYPE_CHECKING` for annotations only. `state.states` runtime-imports nothing from `stmrr.model.*`. The amended SPEC-ML01 runtime-DAG rows accurately reflect this.
12. **`MainMenuState` / `SectorMapState` do not declare `kind: ClassVar[str]`.** The `kind` discriminator is entities-only; states are not persisted as entities. A concrete-state negative test pins this boundary.
13. **Lifecycle hook exception policy is propagate-without-rollback.** If `self._current_state.exit()` raises, no mutation occurs and `current_state` is unchanged. If `target.enter()` raises, mutation has already committed and no `state_changed` event fires. Two focused manager tests pin the asymmetry. Reviewed comparison: this aligns with `transitions` defaults and differs from `python-statemachine`'s optional fault isolation, which resembles the deferred `_send_robust` policy.

#### Open questions

##### Locked decisions

- **`transition_to(target: GameState)` takes an instance, not a class.** The SPEC-ML01 module-surface contract requires an instance. Validation uses `type(target) in current_state.allowed_transitions` (set holds classes). Instance is required because `enter()` and `exit()` are instance methods.
- **`__init__(initial_state: GameState)` fires `enter()` synchronously; no `state_changed` event for construction.** Q2 lock. Lifecycle invariant: every observable state has been entered.
- **`MainMenuState` / `SectorMapState` `enter`/`exit` bodies are `pass`.** Q3 lock. v0.1 has no model-side cueing; future cueing flows through the `state_changed` event consumed by the controller bridge.
- **Mutual class reference resolved via post-class module-level patch.** Q1 lock. Class body declares `allowed_transitions = frozenset()` (satisfies `__init_subclass__`); module-level re-assignment after both classes exist updates the values. Tests pin the patched values.
- **No defensive `isinstance(target, GameState)` check in `transition_to`.** Q4 lock. BasedPyright strict at typed call sites plus the validation step's `type(target) in ...` lookup handle the supported boundary.
- **No special-case self-transition logic; no identity short-circuit.** Q5 + Q6 locks. Composition (the allowed-transitions set) is the source of truth.
- **`from_state_cls` is captured BEFORE `self._current_state = target` in `transition_to`.** This preserves the exact source class required by SPEC-S008 FR-008 and DR-003.
- **One runtime DAG edge removed, no additions.** Step 8 amends the SPEC-ML01 Runtime DAG row for `state.game_state_manager` to move `state.states` from the runtime column to the TYPE_CHECKING column (the original runtime listing was an artifact of an assumed `isinstance(target, GameState)` check that the spec's Q4 lock rejects). No new edges introduced; `state.states` row unchanged (still a runtime leaf).
- **`state.states` remains a stdlib-only runtime leaf.** No `loguru` import; no `events` import; no `exceptions` import (states never raise model exceptions in v0.1 — they only have `pass` bodies). Confirmed by the SPEC-ML01 Runtime DAG.
- **Tests use try/finally connect/disconnect** mirroring `test_starship.py` / `test_turn_manager.py`. No new pytest fixture introduced.
- **No `__repr__` override on `GameStateManager` or the concrete states for v0.1.** The default `MainMenuState` object representation is sufficient for failure messages; `pytest` failure messages already include the class name. (See the still-open `GameStateManager.__repr__` concern below.)
- **Lifecycle hook exception policy: propagate without rollback** (the lifecycle-hook failure contract). `exit()` failure → no mutation, no event. `enter()` failure → mutation already committed, no event. Documented and tested explicitly so v0.2's first non-trivial hook body can't be a surprise. The asymmetry between `exit` and `enter` postconditions mirrors the five-step lifecycle order, not an arbitrary choice.
- **Reentrancy from inside a `state_changed` receiver is NOT supported in v0.1.** A receiver calling `manager.transition_to(...)` would mutate `manager._current_state` while the previous `send()` is still on the stack. v0.1 has one known-safe subscriber (controller bridge) and no use case for reentrant transitions; the spec does not test it, does not document a policy, and treats it as undefined. v0.2 may revisit when the bridge or replay layer needs to chain transitions.

##### Still open (v0.2 concerns, NOT v0.1 blockers)

1. **`__repr__` for `GameStateManager`.** Default Python repr (the default `GameStateManager` object representation) is uninformative in pytest failure messages. A `__repr__` returning `f"GameStateManager(current_state={type(self._current_state).__name__})"` is cheap and improves debugging. **Defer**: add when a debugging session feels the friction; not v0.1-blocking. Skip-trigger: spec author finds the default repr acceptable in step-9+ bridge debugging.

2. **Trace logging in `transition_to`.** A single `logger.debug(f"{type(from_state).__name__} → {type(to_state).__name__}")` line in `transition_to` would give state-machine trace visibility. **Defer**: requires importing `loguru` into `game_state_manager.py` (which currently has no logging imports) and creates a precedent for "should every action method log?". v0.2 may add a structured tracing layer that applies the SPEC-ML01 logging constraint uniformly to all model-layer transitions and action methods; better to wait for that decision than to scatter ad-hoc `logger.debug` calls.

3. **Planned growth toward roughly seven states; replacement trigger above roughly 15.** ADR-0005 names roughly 15 states, or hooks and callbacks becoming unwieldy, as the threshold for revisiting the hand-rolled approach in favor of `transitions` or `python-statemachine`. v0.1 has 2 states; v0.2 combat likely adds 2–3 (`CombatState`, optionally `PausedState`, `LoadingState`), and the broader planned graph remains roughly 7 states—still below the replacement threshold. No action.

4. **State-instance reuse vs. fresh construction.** `manager.transition_to(SectorMapState())` constructs a new instance on every transition. Reusing a single instance per state class (singleton-like) would save allocations and let states hold mutable inter-transition state. **Reject for v0.1**: state instances in v0.1 have zero state (empty `pass` bodies), so the optimization buys nothing and adds lifecycle complexity. v0.2 may revisit if a state needs to hold transition-spanning data (e.g., `CombatState` retaining initiative order across pause/resume cycles).

## 12. Error Handling and Recovery

### 12.1 Expected Failures

| ID | Failure Mode | User/System Behavior | Logging / Observability | Recovery |
| --- | --- | --- | --- | --- |
| ERR-001 | Target class is not allowed. | `IllegalTransitionError` propagates before hooks or mutation. | Typed exception exposes source and target classes. | Caller selects an allowed state. |
| ERR-002 | Outgoing `exit()` raises. | Exception propagates; outgoing state stays current; no event. | Test or caller observes the original exception. | Repair the hook before retrying. |
| ERR-003 | Incoming `enter()` raises. | Exception propagates; target stays current; no event. | Test or caller observes the original exception and committed state. | Repair explicitly; the manager performs no hidden rollback. |
| ERR-004 | A blinker receiver raises. | Exception propagates after the transition and mutation remain committed. | Caller receives the receiver exception. | Disconnect or repair the receiver; add fault isolation when WH-002's trigger occurs. |

### 12.2 Retry and Idempotency

The manager performs no automatic retries. An invalid or exit-failed transition may be retried after its cause is corrected because no mutation occurred. An enter-failed or receiver-failed transition must not be blindly replayed because the target is already current. Self-transition is invalid rather than idempotently ignored.

### 12.3 Rollback / Recovery

No automatic rollback exists. The lifecycle's observable state identifies the recovery point: an exit failure leaves the source current, while an enter or receiver failure leaves the target current. A caller must inspect `current_state`, repair the failed hook or receiver, and request only a valid next transition.

For multi-session implementations: record current milestone, in-progress requirement IDs, and unresolved `OQ-`/`DEV-` items in the repository's session-state/handoff documents at the end of each session, per the repo's documentation convention. The spec records _what and why_; handoff docs record _where work stands_.

## Appendix D: Tailoring

Pick the smallest profile that fits; upgrade if the project grows. Because numbering is stable across profiles, upgrading is **additive**: insert the missing sections at their canonical numbers and set `profile:` in the frontmatter — no existing section or ID reference changes.

| Profile | Template File | Use For |
| --- | --- | --- |
| **Light** | `spec-light-template.md` | Scripts, small tools, single-session agent tasks |
| **Standard** | this file | Typical features and services |
| **Full** | `spec-full-template.md` | Multi-service systems, durable data, external integrations, or multiple stakeholders |

Rules of thumb:

- Owns durable data → §18.6 Backup/DR is required.
- Talks to external paid/rate-limited APIs, makes automated decisions users must trust, or spans multiple services/stakeholders → upgrade to **Full** (adds §5, §8.4, §8.6, §14–§16, §18.4, §20, §19 Waves, and Appendix C modules).
- Implemented by a coding agent → Appendix B is required (it is the cheapest section and the highest-leverage one).
