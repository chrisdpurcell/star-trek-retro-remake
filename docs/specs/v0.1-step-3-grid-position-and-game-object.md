## 1. Purpose & Background

This foundation defines the immutable three-dimensional coordinate used throughout the game model and the identity-bearing mutable base class inherited by active entities. It lands before the dependent model modules so their coordinate, lifetime-identity, equality, and deactivation semantics are fixed and testable without Qt.

The v0.1 outcome is a small, headless API that supports the vertical slice while preserving a clean path to later persistence, concurrency, and subclass-specific actions.

## 8. Architecture and Design

### 8.1 Architecture Summary

`GridPosition` is a frozen, slotted value object and a runtime leaf. `GameObject` is a mutable identity object that imports `GridPosition`, owns only the common lifecycle fields, and delegates actions to subclasses. The module-level ID generator is deliberately process-local for v0.1.

### 8.2 Architecture Views

#### 8.2.1 Context View

`GridPosition` is consumed by world, entity, and view-projection modules. `GameObject` is consumed by concrete entity types and world containers. Neither module crosses the controller/view seam.

#### 8.2.2 Container / Deployment View

Both modules execute in-process as part of the desktop application and in headless unit-test processes; they have no independent deployment unit.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| `grid_position.py` | Coordinate validation and geometry helpers. | `GridPosition` public value type. | Runtime leaf; immutable. |
| `game_object.py` | Entity identity and soft lifecycle. | `EntityId`, `GameObject`, private ID generator. | Imports `GridPosition`; no action semantics. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Use a frozen slotted dataclass for `GridPosition`. | It supplies value equality, hashing, immutability, and compact instances. | A mutable class would weaken coordinate invariants. | — |
| D-002 | Use a process-local monotone integer `EntityId` for v0.1. | It is simple, typed, and TOML-compatible before persistence exists. | UUIDs or persisted counters are deferred to the persistence design. | ADR-0004 |
| D-003 | Preserve identity equality for `GameObject`. | Distinct entities must never collapse because their fields match. | Value equality was rejected. | — |
| D-004 | Keep action methods off the base class. | Subclass signatures and precondition/effect sequences differ. | A generic `move_to()` would be boilerplate or violate override typing. | ADR-0003 |

> **§8.4 (Solution Alternatives Considered) is Full-tier** and is intentionally omitted at the Standard profile.

### 8.5 Design Constraints

- Private mutable module state is `_entity_id_counter`; `_next_entity_id()` remains the allocator.
- `GridPosition` value semantics and `GameObject` identity semantics must remain deliberately different.
- Neither component may import Qt or perform file I/O.
- Neighbor ordering is part of the public deterministic behavior.

> **§8.6 (Dependency Policy) is Full-tier** and is intentionally omitted at the Standard profile.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. A caller constructs a validated `GridPosition`.
2. A caller constructs a `GameObject` or subclass with that position.
3. `_next_entity_id()` increments `_entity_id_counter` and assigns the new ID.
4. The object becomes observable with `active=True`.

Expected result: a distinct active entity references a valid immutable coordinate.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | A caller deactivates an entity more than once. | Each call assigns `False` without raising. | The entity remains inactive. |
| AW-002 | A caller needs one changed coordinate axis. | A `with_*` helper constructs and validates a new value. | The original remains unchanged. |

### 10.3 Edge Cases

| ID | Edge Case | Expected Behavior |
| --- | --- | --- |
| EC-001 | An axis is a bool. | Construction raises `TypeError` even though bool subclasses int. |
| EC-002 | Neighbor generation reaches an axis-zero boundary. | Negative candidates are omitted and documented face/edge/corner counts result. |
| EC-003 | Two entities have identical fields. | They remain unequal unless they are the same object. |

### 10.4 State Transitions

| State | Meaning | Entry Condition | Exit Condition |
| --- | --- | --- | --- |
| Active | `GameObject.active` is `True`. | Successful construction. | `deactivate()` is called. |
| Inactive | `GameObject.active` is `False`. | First or repeated `deactivate()` call. | No reactivation transition exists in this step. |

#### Detailed `GridPosition` Contract

##### Class Declaration

```python
from collections.abc import Iterator
from dataclasses import dataclass
from math import sqrt


@dataclass(frozen=True, slots=True)
class GridPosition:
    x: int
    y: int
    z: int
```

`frozen=True` gives equality, hashing, and immutability for free; `slots=True` drops the per-instance `__dict__` so thousands of positions stay cheap. `DESIGN.md` section 9.1: _"Logical coordinates are cartesian `(x, y, z)` stored on items."_

##### Validation Contract

`__post_init__` runs two checks per axis, in this order:

1. **Type check:** `isinstance(value, int) and not isinstance(value, bool)` — raises `TypeError` if it fails. BasedPyright strict rejects `Fraction`, `Decimal`, or `float` against an `int` parameter, but untyped callers, TOML deserializers, and external data can still hand in anything at runtime; the guard catches them at the boundary. `bool` is the residual footgun — an `int` subclass that can still reach runtime validation.
2. **Range check:** `value >= 0` — raises `ValueError` if it fails. Sector dimensions (max 20×20×7 per `DESIGN.md` section 4.3) are `SectorMap`'s responsibility; negatives are nonsense at the position level regardless of containing sector.

Separate exception types so messages name the actual failure mode.

##### Method Contracts

| Method | Signature | Semantics | Complexity | Errors |
| --- | --- | --- | --- | --- |
| `manhattan_distance` | `(self, other: GridPosition) -> int` | `\|Δx\| + \|Δy\| + \|Δz\|` | O(1) | none |
| `chebyshev_distance` | `(self, other: GridPosition) -> int` | `max(\|Δx\|, \|Δy\|, \|Δz\|)` | O(1) | none |
| `euclidean_distance` | `(self, other: GridPosition) -> float` | `sqrt(Δx² + Δy² + Δz²)` | O(1) | none |
| `is_adjacent` | `(self, other: GridPosition) -> bool` | `chebyshev_distance(other) == 1` | O(1) | none — explicitly `False` for `self` |
| `neighbors` | `(self) -> Iterator[GridPosition]` | yields up-to-26 valid (non-negative) adjacent positions; deterministic order sorted by `(dz, dy, dx)` lexicographically over `{-1, 0, +1}`³ excluding `(0, 0, 0)` | O(1) (≤26 items) | none |
| `with_x` | `(self, x: int) -> GridPosition` | returns a copy with new `x` | O(1) | `ValueError` if `x < 0` (re-validated via `__post_init__`) |
| `with_y` | `(self, y: int) -> GridPosition` | returns a copy with new `y` | O(1) | `ValueError` if `y < 0` |
| `with_z` | `(self, z: int) -> GridPosition` | returns a copy with new `z` | O(1) | `ValueError` if `z < 0` |
| `origin` (classmethod) | `cls() -> GridPosition` | returns `cls(0, 0, 0)` | O(1) | none |

**Examples:**

```python
GridPosition(0, 0, 0).manhattan_distance(GridPosition(1, 2, 3))   # 6
GridPosition(0, 0, 0).chebyshev_distance(GridPosition(1, 2, 3))   # 3
GridPosition(0, 0, 0).euclidean_distance(GridPosition(2, 3, 6))   # 7.0
GridPosition(5, 5, 0).is_adjacent(GridPosition(5, 5, 0))          # False
list(GridPosition(0, 0, 0).neighbors())                            # 7 entries (corner)
GridPosition(3, 4, 5).with_z(6)                                    # GridPosition(3, 4, 6)
```

`neighbors()` order is non-negotiable: AI pathfinding tie-breaks on iteration order; replay tests need bit-stable behavior. Counts depend on which axes touch zero — **interior 26, face 17 (one axis at 0), edge 11 (two), corner 7 (three)**. These are the four boundary classes the test suite must cover.

##### Dunder Behavior

`__repr__`, `__eq__`, `__hash__` come from `@dataclass(frozen=True)` — no custom code. Equality is _value_-based: same `(x, y, z)` ⇒ equal. This is the **opposite** of the identity equality required by FR-011 for `GameObject`; the contrast is intentional.

#### Detailed `GameObject` Contract

##### Module-Level Types and ID Generator

```python
from typing import NewType

from stmrr.model.world.grid_position import GridPosition

EntityId = NewType("EntityId", int)

# TODO(v0.2+): wrap _next_entity_id in threading.Lock once AI processing moves
# to QThreadPool. See docs/design/DESIGN.md section 9.4 "Threading". Single-threaded
# turn loop means v0.1 does not need synchronization.
_entity_id_counter: int = 0


def _next_entity_id() -> EntityId:
    global _entity_id_counter
    _entity_id_counter += 1
    return EntityId(_entity_id_counter)
```

`EntityId` is a `NewType` — a zero-cost static-typing hint catching `int` ↔ `EntityId` confusion while staying TOML-serializable (ADR-0004, [`docs/adr/0004-toml-not-pickle.md`](../adr/0004-toml-not-pickle.md)).

**v0.1 decision: monotone integer.** Counter resets on process restart; acceptable because v0.1 has no save/load. v0.2 persistence spec decides whether to persist the counter, switch to UUID4, or rebuild ID maps at load. The type stays `NewType("EntityId", int)` either way.

##### Why `GameObject` Is Not a Frozen Dataclass

Subclasses need mutable position plus component composition (`DESIGN.md` section 9.1). Frozen dataclasses force `dataclasses.replace` per update, breaking reference semantics the controller bridge needs for animation. Plain class wins.

##### Class Declaration and Method Contracts

```python
class GameObject:
    """Base class for all active entities on a sector grid.

    Identity is per-instance (lifetime ID), not per-position. See SPEC-S003
    FR-011 for the equality contract.
    """

    def __init__(self, position: GridPosition) -> None:
        self.id: EntityId = _next_entity_id()
        self.position: GridPosition = position
        self.active: bool = True

    def deactivate(self) -> None: ...
```

| Method | Semantics | Errors |
| --- | --- | --- |
| `__init__(self, position)` | assigns a fresh `EntityId`, sets `position`, sets `active=True`. No validation — `position` is already validated. | none |
| `deactivate(self)` | sets `self.active = False`. Idempotent — calling on an already-inactive object is a no-op, no error, no warning. | none |

Idempotent `deactivate`: the same destruction event may be observed by multiple subscribers; a second call must not throw.

**Why no base `move_to`.** Every subclass that moves does so under different action semantics — AP cost, adjacency check, event emission, sometimes a sector-map lookup. A base `move_to(self, position)` would either be empty boilerplate or get overridden by `Starship.move_to(target, sector_map)` with an incompatible signature, which BasedPyright strict rejects. The cleanest contract is: the base owns identity (`id`, `position` field, `active`), subclass action methods own mutation (assigning `self.position` directly inside their own precondition + AP-debit + event-emit sequence). Companion spec [`v0.1-model-layer.md`](v0.1-model-layer.md) records the `Starship.move_to` action contract.

##### Equality Contract

Identity-based:

```python
def __eq__(self, other: object) -> bool:
    return self is other

def __hash__(self) -> int:
    return id(self)
```

This matches default `object` behavior; writing it explicitly stops a future subclass author from overriding `__eq__` with value-equality (a footgun once entities enter pathfinding open-lists). Two `Starship` instances with identical state are **not** equal — different ships.

##### `__repr__`

```python
def __repr__(self) -> str:
    return (
        f"{type(self).__name__}(id={self.id}, "
        f"position={self.position}, active={self.active})"
    )
```

`type(self).__name__` ensures subclass reprs read correctly: `Starship(id=…, …)`, not `GameObject(…)`.

##### Subclass Implications

Subclasses (`Starship`, `Station`, `Anomaly`, `Projectile`) inherit the module-scope ID generator, the mutable `position` attribute (subclass action methods assign it directly inside their own precondition + AP-debit + event-emit sequence — there is no base `move_to` to override), and `active` as the universal soft-delete flag. Hard removal from `SectorMap` is separate.


#### Preserved Invariants

Properties the rest of the model layer relies on; reviewer should probe these.

1. `GridPosition.x`, `.y`, `.z` are non-negative integers for any constructed instance.
2. A `GridPosition` is immutable post-construction; assignment raises `dataclasses.FrozenInstanceError`.
3. The three distance methods are symmetric: `a.f(b) == b.f(a)`.
4. All three distance methods return `0` (or `0.0`) for self-distance.
5. `is_adjacent(self, self)` is `False`.
6. Every position yielded by `neighbors()` has non-negative coordinates and Chebyshev distance 1 from `self`.
7. `EntityId` values from `_next_entity_id()` are strictly monotonically increasing within a process lifetime.
8. `GameObject` equality is reference identity: `a == b` iff `a is b`. Two instances are never equal regardless of attribute values.
9. `deactivate` is idempotent.
10. `GameObject` exposes no action methods — only identity (`id`, `position`, `active`) plus `deactivate`. State mutation, event emission, sector-bounds validation, and inter-entity interaction live on subclass action methods exclusively.

#### Historical Review Questions

##### Locked Decisions

- **EntityId for v0.1: monotone `int`.** UUID4 migration is a v0.2 persistence-spec concern.
- **Validation taxonomy: `TypeError` for non-int, `ValueError` for negatives.** Two distinct checks per axis — both apply.
- **Axis fields stay `int`, not a `Coordinate` `NewType`.** Wrapping would noise-up every literal (`Coordinate(0)` everywhere) for marginal type-safety benefit at v0.1's scale. Revisit only if axis/AP/hull confusion shows up in practice.
- **`slots=True` on `GridPosition`.** pydantic v2 handles slotted dataclasses cleanly; the persistence boundary is its own concern, not a reason to drop the per-instance memory win.
- **`neighbors()` is a method, not a free function.** `tcod`'s graph adapter wants `(GridPosition) -> Iterable[GridPosition]`; `obj.neighbors` satisfies it without an extra layer.
- **No `_next_entity_id()` test reset hook.** Tests assert relative ordering (`id_2 > id_1`), not absolute values — there is no need to expose a knob production code must never call.

## 12. Error Handling and Recovery

### 12.1 Expected Failures

| ID | Failure Mode | User/System Behavior | Logging / Observability | Recovery |
| --- | --- | --- | --- | --- |
| ERR-001 | A coordinate axis is not a non-bool integer. | Construction raises `TypeError` before an invalid object exists. | Focused unit tests capture the exception contract. | Correct the caller input and retry construction. |
| ERR-002 | A coordinate axis is negative. | Construction raises `ValueError` before an invalid object exists. | Focused unit tests capture the exception contract. | Correct the caller input and retry construction. |
| ERR-003 | An immutable coordinate field is assigned. | Dataclass machinery raises `FrozenInstanceError`. | The immutability unit test captures the failure. | Construct a replacement with a `with_*` helper. |

### 12.2 Retry and Idempotency

Coordinate construction can be retried after caller input is corrected because failed construction has no side effects. `deactivate()` is explicitly idempotent. Entity construction is not idempotent: every successful call intentionally consumes a new process-local ID.

### 12.3 Rollback / Recovery

No persistent state is owned. A failed `GridPosition` construction leaves nothing to roll back; a `GameObject` can transition only from active to inactive in this step.

## Appendix B: Agent Implementation Contract

Binding when this spec is implemented by a coding agent. (Applies equally well to human contractors.)

### B.1 Implementation Rules

The implementer shall:

- Read this entire specification before making changes; per session thereafter, re-read at minimum §7 (Requirements), §21 (Open Questions), and the Deviations Log — Background and References may be read once.
- Preserve all explicit non-goals, won't-haves, constraints, and design constraints.
- Treat **Must** requirements as mandatory and **blocking** open questions as hard stops for the affected work.
- On encountering underspecified behavior: file an `OQ-` row **with a proposed default assumption** and proceed on it only if non-blocking — never guess silently.
- On any divergence from the spec: record a `DEV-` row (spec reference, what, why) rather than adapting silently.
- Add or update tests for every implemented requirement; keep §17.3 (traceability) current.
- Follow the milestone order in §19; do not build later milestones on unproven earlier ones.
- Prefer small, reviewable changes; avoid broad refactors unless the spec requires them.
- Document any discovered mismatch between the spec and existing code as a `DEV-` or `OQ-` row.

### B.2 Prohibited Behaviors

The implementer shall not:

- Invent requirements not present in this spec.
- Remove existing behavior unless explicitly required.
- Introduce external services or dependencies not agreed with the owner without an approved `OQ-`.
- Store secrets in source control or print them in CI logs.
- Ignore failing tests unrelated to the change without documenting them.
- Treat examples as exhaustive or normative unless explicitly stated.
- Mark a requirement complete without a verification entry in §17.3.

### B.3 Required Completion Report (verification gate)

At completion, provide:

- Summary of changes and files changed.

- Documentation deliverables completed (§18.7).

### B.4 Session Handoff
