## 8. Architecture and Design

### 8.1 Architecture Summary

`exceptions.py` and `states.py` use stdlib only; `events.py` adds blinker. Project type names referenced by exceptions and payloads remain annotation-only so the modules do not create runtime backedges. Import-linter and source-location tests make `events.py` the single declaration site.

### 8.2 Architecture Views

#### 8.2.1 Context View

Later model actions raise Step 5 exceptions and send Step 5 events. Step 8 subclasses `GameState`; Step 9 consumes the events through the controller bridge.

#### 8.2.2 Container / Deployment View

All modules run in-process in the desktop application and headless tests; none is independently deployed.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| `exceptions.py` | Typed model failure hierarchy. | Eight public exception types. | Runtime leaf. |
| `events.py` | Typed change-notification vocabulary. | Four payloads and four signals. | Private namespace; blinker only. |
| `state/states.py` | Minimal state abstraction. | `GameState`. | Concrete states arrive in SPEC-S008. |
| Enforcement tests | Import and declaration boundaries. | pytest and import-linter. | Dynamic walk is subprocess-isolated. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Keep parent exception classes concrete and use keyword-only rich leaves. | ABC exception machinery is unnecessary; leaf facts aid UI/logging. | Bare strings and abstract parent errors were rejected. | — |
| D-002 | Use a private blinker namespace plus three enforcement layers. | No single layer catches direct imports, namespace reuse, and payload declarations. | A public namespace and honor-system policy were rejected. | ADR-0003 |
| D-003 | Enforce transition-set declaration in `__init_subclass__` using `inspect.isabstract()` and `vars(cls)`. | The checker cannot require class-attribute override, and inherited values are unsafe. | Abstract property and default value approaches were rejected. | ADR-0005 |
| D-004 | Keep annotation-only project types out of runtime globals. | It preserves the cycle-free DAG. | Promoting types solely for `get_type_hints()` was rejected. | ADR-0004 |

- `events.py` is the sole signal and payload declaration site.
- Runtime leaves remain free of project runtime imports.
- Concrete state subclasses declare transition sets directly.
- The subprocess guard proves module-load behavior only; it does not claim to execute uncalled function bodies.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. A model action validates its preconditions.
2. On failure it raises the corresponding typed Step 5 exception.
3. On success it mutates state, creates the corresponding payload, and sends the named signal.
4. A connected receiver observes the exact sender and payload object synchronously.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | A concrete state omits or only inherits `allowed_transitions`. | Class definition raises `TypeError`. | Invalid concrete state never becomes importable. |
| AW-002 | A state subclass remains abstract. | Skip the transition-set presence check. | Its concrete descendant is checked later. |
| AW-003 | Runtime code requests resolved hints for an annotation-only payload. | `get_type_hints()` raises `NameError`. | Caller uses direct attributes or safe string-format annotation inspection. |

#### Purpose

Three modules that anchor cross-cutting concerns for the rest of the v0.1 model layer:

- `model/exceptions.py` — single-file exception hierarchy used by every action method and the state-machine transition guard.
- `model/events.py` — the `blinker.Namespace`, four typed payload dataclasses, and four named signals that are the model layer's only sanctioned change-notification channel.
- `model/state/states.py` — the **minimal `GameState` ABC stub**. Concrete states (`MainMenuState`, `SectorMapState`) defer to the state-machine step where they are designed alongside their consumer (`GameStateManager`).

All three are runtime leaves under the SPEC-ML01 runtime DAG. They landed together because (a) `events.py` field annotations forward-reference `GameState`, so the ABC must exist for strict static checking to resolve `type[GameState]`; (b) the exception hierarchy is what the next steps' action methods raise; and (c) all three are pure-Python low-dependency modules.

This spec also adds one cross-cutting test, `tests/unit/model/test_no_qt_imports.py`, which closes the deferral noted in step 3 (SPEC-ML01 Qt-free invariant) now that the model layer crosses three runtime modules.

#### Layering and constraints

- All three modules inherit ADR-0003 ([`docs/adr/0003-model-qt-free.md`](../adr/0003-model-qt-free.md)); the existing `model-is-qt-free` `import-linter` contract covers them statically. The new `tests/unit/model/test_no_qt_imports.py` adds runtime coverage for transient imports the static contract misses.
- Python 3.14-native annotation semantics apply. Annotation-only imports remain under `TYPE_CHECKING`, and source plus tests pass the repository-wide BasedPyright strict configuration.
- Imports: stdlib, `blinker`, and other model modules only. Forward-referenced types in payload + exception annotations are imported under `if TYPE_CHECKING:` only — neither module makes a runtime import edge to the modules it references for typing.
- Module + class docstrings mandatory on public types. Method docstrings only where the _why_ is non-obvious.
- Per SPEC-ML01 centralized-event invariant: `events.py` is the canonical declaration site for every signal and every payload dataclass in the model layer. Step 5 enforces this in **three complementary layers**, each catching an escape route the others miss:
  1. **`.importlinter` forbidden contract `blinker-only-in-events`** — forbids any module under `stmrr.model.*` other than `stmrr.model.events` from importing `blinker` directly. **Must** be configured with `allow_indirect_imports = True` so future legitimate paths like `entities.starship → events → blinker` are not flagged. The contract bounds _direct imports_, not transitive ones. Required snippet shape:

     ```ini
     [importlinter:contract:blinker-only-in-events]
     name = blinker only in events
     type = forbidden
     source_modules =
         stmrr.model
     forbidden_modules =
         blinker
     ignore_imports =
         stmrr.model.events -> blinker
     allow_indirect_imports = True
     ```

     This catches a contributor who tries to create a signal via `from blinker import signal; my_event = signal("...")` in another module.

  2. **Private namespace + grep ban on `.signal(` calls outside `events.py`** — the blinker `Namespace` instance is named `_stmrr_events` (leading underscore = internal), and the model-layer enforcement test asserts no line matching the regex `\.signal\s*\(` exists in `src/stmrr/model/**/*.py` outside `events.py`. **Why both:** an attacker on this invariant could route around layer (1) via `from stmrr.model.events import _stmrr_events; extra = _stmrr_events.signal("extra")` — no direct `blinker` import, contract passes. The `.signal(` grep catches the call regardless of how the namespace was reached. The leading underscore on the namespace name is the secondary signal that this is internal API.
  3. **Payload-class declaration-site grep** — same enforcement test asserts no line matching `^class \w*Payload\b` exists in `src/stmrr/model/**/*.py` outside `events.py`. Catches `@dataclass class MyPayload: ...` declarations elsewhere, which neither layer (1) nor layer (2) catches because dataclass payloads don't need any blinker symbol at all.

  Layers (2) and (3) are implemented in the same test file `tests/unit/model/test_invariant_10_enforcement.py` (renamed from the round-2 working name `test_payload_location.py` to reflect its broader scope). Cheap regex sweep over file source — no AST machinery needed for v0.1's naming conventions. A contributor who routes around all three layers (e.g., dynamic class creation via `type()`, signal creation via reflection) is willfully bypassing the contract; that case is out of scope for v0.1 enforcement.

  Mirrors how step 4 enforced Qt-free for the projection module via a dedicated contract — but layered, because `events.py` has more declaration shapes to police than projection had.

#### `model/exceptions.py` specification

##### Hierarchy

```text
ModelError(Exception)                              # root; concrete but never raised directly by convention
├── IllegalActionError(ModelError)                 # action-precondition failures; concrete catch-all
│   ├── InsufficientAPError       (*, required: int, available: int)
│   ├── OutOfBoundsError          (*, position: GridPosition, sector_dims: tuple[int, int, int])
│   ├── NotAdjacentError          (*, from_position: GridPosition, to_position: GridPosition)
│   ├── InactiveEntityError       (*, entity_id: EntityId)
│   └── NotDockableError          (*, ship_id: EntityId, station_id: EntityId)
└── IllegalTransitionError(ModelError)
                                  (*, from_state: type[GameState], to_state: type[GameState])
```

`ModelError` and `IllegalActionError` are **concrete, not abstract**. ABC machinery for an exception class is gratuitous; the convention "always raise a subclass" is enforced by code review, not by the type system. The only intended use of the parent types is `except ModelError:` for layer-wide catches and `except IllegalActionError:` for action-precondition catch-all. **All exception classes inherit from `Exception` (through `ModelError`), not from `ValueError`** — callers use `except ModelError:` to distinguish model-layer failures from generic value errors raised by, for example, `GridPosition.__post_init__` under the SPEC-S003 coordinate-validation contract.

##### Module shape

```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from stmrr.model.entities.game_object import EntityId
    from stmrr.model.state.states import GameState
    from stmrr.model.world.grid_position import GridPosition


class ModelError(Exception):
    """Root of the model-layer exception hierarchy. Never raised directly."""


class IllegalActionError(ModelError):
    """Raised when an action's preconditions fail. See SPEC-ML01."""


class InsufficientAPError(IllegalActionError):
    def __init__(self, *, required: int, available: int) -> None:
        self.required: int = required
        self.available: int = available
        super().__init__(
            f"action requires {required} AP, only {available} available"
        )


# ... remaining subclasses follow the same shape; see the constructor and exact-message contracts below.

__all__ = [
    "ModelError",
    "IllegalActionError",
    "InsufficientAPError",
    "OutOfBoundsError",
    "NotAdjacentError",
    "InactiveEntityError",
    "NotDockableError",
    "IllegalTransitionError",
]
```

`exceptions.py` is a **runtime leaf**: the `EntityId`, `GridPosition`, and `GameState` imports live under `if TYPE_CHECKING:`, and Python 3.14-native deferred annotation evaluation does not force a runtime import edge. This preserves the SPEC-ML01 runtime DAG.

##### `__init__` signature contract

Every concrete subclass uses **keyword-only arguments** — the parameter list opens with `*` so positional construction raises `TypeError`. Two purposes:

1. **Self-documenting call sites.** `InsufficientAPError(required=2, available=0)` reads at the call site; `InsufficientAPError(2, 0)` would not.
2. **Forward-compatibility.** v0.2 may add fields (e.g., `entity_id` to `InsufficientAPError`) without breaking positional-arg callers — because none can exist by construction.

Each subclass:

1. Stores every kwarg as a public typed attribute on `self` (e.g., `self.required: int = required`).
2. Computes a formatted message inline (no helper functions, no template module).
3. Calls `super().__init__(formatted_message)` so `str(exc)` and `repr(exc)` both render meaningfully without a custom `__str__`.

`ModelError` and `IllegalActionError` themselves accept the default `Exception` signature (`*args`); they are catch-all parents and have no v0.1 callers raising them directly.

##### Locked `__str__` format strings

These are tested verbatim. Localization (v2.0+) will replace them with translation keys; v0.1 ships English literals so the bridge can render them as-is.

| Exception | Format string |
| --- | --- |

#### `model/state/states.py` specification — minimal ABC stub

##### Class declaration

```python
import inspect
from abc import ABC, abstractmethod
from typing import Any, ClassVar


class GameState(ABC):
    """Base class for all game states. Per ADR-0005 — hand-rolled state
    machine, no `transitions` library, no `QStateMachine`.

    Subclasses MUST declare `allowed_transitions` as a class-level
    `frozenset[type[GameState]]`. Omission is caught at class-definition
    time by `__init_subclass__` (see the enforcement rationale below), not at instantiation.
    """

    allowed_transitions: ClassVar[frozenset[type["GameState"]]]

    def __init_subclass__(cls, **kwargs: Any) -> None:
        super().__init_subclass__(**kwargs)
        # Skip still-abstract intermediates: a subclass that inherits
        # @abstractmethods without overriding them is itself abstract,
        # and its concrete descendant will be checked at its own
        # __init_subclass__ time. Use inspect.isabstract(cls), NOT
        # cls.__abstractmethods__ — ABCMeta populates __abstractmethods__
        # after type.__new__ returns (i.e., after __init_subclass__ has
        # already run), so direct attribute access raises AttributeError
        # here. This ordering has held since CPython moved ABC machinery
        # to C in 3.7. inspect.isabstract reads the C-level _abc_impl
        # bookkeeping that IS populated during class creation.
        if inspect.isabstract(cls):
            return
        if "allowed_transitions" not in vars(cls):
            raise TypeError(
                f"{cls.__name__} must declare class attribute "
                f"`allowed_transitions: ClassVar[frozenset[type[GameState]]]`"
            )

    @abstractmethod
    def enter(self) -> None: ...

    @abstractmethod
    def exit(self) -> None: ...


__all__ = ["GameState"]
```

##### Why `__init_subclass__`, not `@property @abstractmethod`, not a default

The `allowed_transitions` attribute is **data**, not behavior — it's a class-level lookup table consumed by `GameStateManager.transition_to`. Three enforcement options were considered:

1. **`ClassVar` annotation alone (no enforcement).** Rejected: a strict static checker verifies provided values but does not require every concrete subclass to redeclare the inherited class attribute, so omission can fail only at first read.
2. **`@property @abstractmethod`.** Rejected: turns a static lookup table into a per-instance method call. Every concrete state would override a property instead of declaring a class attr, which is more ceremony for no static-typing win (the dispatch is per-instance, but the data is per-class).
3. **`__init_subclass__` runtime check (chosen).** Fires at class-definition (i.e., import) time. Skips still-abstract intermediates via `if inspect.isabstract(cls): return` — **not** `cls.__abstractmethods__`, which raises `AttributeError` inside `__init_subclass__` because `ABCMeta` populates `__abstractmethods__` after `type.__new__` returns (i.e., after `__init_subclass__` has already run). This has been the ordering since CPython moved ABC machinery to C in 3.7; it is not Python 3.14-specific. `inspect.isabstract` reads the C-level `_abc_impl` bookkeeping that is populated during class creation and is therefore observable at this hook. Uses `"allowed_transitions" in vars(cls)` (not `hasattr`) so subclasses cannot satisfy the check by inheriting a parent's value. Run-once cost, well-trodden pattern. The spec's test row pins the failure mode: subclass omission raises `TypeError` at class definition, not at instantiation.

A default of `frozenset()` (terminal-state semantics) was the simplest option, but it loses the defensive value: a concrete state that _forgets_ to declare its transitions silently behaves as terminal. Forcing opt-in via `__init_subclass__` catches the omission.

##### `test_no_qt_imports.py` — model-layer-wide runtime guard (subprocess-isolated)

Single test, dynamic walk, **executed in a clean Python subprocess**. Closes SPEC-ML01 Qt-free invariant's runtime obligation (deferred at step 3 pending ≥3 model modules; step 5 puts the layer at five non-package implementation modules — `world.grid_position`, `entities.game_object`, `exceptions`, `events`, `state.states` — plus a handful of package markers, both implementation packages (`world`, `entities`, `state`) and scaffold packages (`combat`, `missions`, `resources`, `systems`)). The exact `walk_packages` entry count is incidental; the test asserts the Qt-free _property_, not a count.

```python
"""Runtime guard: no `stmrr.model.*` module pulls in PySide6 or shiboken6
at import time.

Complements the static `model-is-qt-free` import-linter contract by
catching imports written at module scope, class body scope, decorator
scope, or default-argument scope — positions the static analyser may
miss when an import is conditional on `if TYPE_CHECKING:` style guards
or pulled in via dynamic patterns. Does NOT catch imports inside
function bodies that the probe doesn't call; those are caught by
controller-layer integration tests once the action methods land
(SPEC-ML01 Qt-free invariant, three-layer enforcement).

The walk runs in a clean Python subprocess — running it in the parent
pytest process would race with `pytest-qt` (or any other view-layer
test) loading PySide6 first, which would make the assertion fail for
reasons unrelated to model code.
"""
```

| Test | Form |
| --- | --- |
| Spawn `subprocess.run([sys.executable, "-c", PROBE_SCRIPT], check=True, capture_output=True)`, where `PROBE_SCRIPT` walks every submodule under `stmrr.model.*` via `pkgutil.walk_packages(stmrr.model.__path__, "stmrr.model.")`, imports each via `importlib.import_module`, then asserts `"PySide6" not in sys.modules` and `"shiboken6" not in sys.modules`. The test itself only checks the subprocess's exit code and surfaces stderr on failure. | inline |

**Why subprocess isolation (not `sys.modules` snapshot in-process):** `sys.modules` is an additive global. `pytest-qt` fixtures, view-layer integration tests, or any fixture that imports PySide6 anywhere earlier in the same pytest run leaves PySide6 in `sys.modules` for the rest of the process. An in-process `"PySide6" not in sys.modules` assertion would then fail for reasons unrelated to model code, and the failure mode is order-dependent (works in isolation, fails in the full suite). A snapshot-and-diff approach (capture `sys.modules` before model import, assert no Qt symbol _added_) is closer but still misses the case where Qt was already loaded but a model module would have re-imported it. Subprocess is the only clean isolation boundary; the ~50 ms startup cost is one test per CI run.

**Coverage scope — what this test catches and what it doesn't:** the probe imports each model module top-to-bottom, which executes module-scope code (top-level statements, decorators, class bodies, default-argument expressions). It catches Qt imports written at any of those positions. It does **NOT** catch `def some_method(self): import PySide6` patterns where the import lives inside a function body that the probe never calls — those imports happen only when the function runs. The static `import-linter` `model-is-qt-free` contract has the same blind spot (it parses imports but doesn't reason about call graphs). The third layer — controller-layer integration tests that actually call the model's action methods (`Starship.move_to`, `Starship.dock_at`, `TurnManager.advance_turn` once those modules land) — is what catches function-body Qt imports inside live code paths. For v0.1, the three-layer combination (static import-linter + import-time runtime guard + integration-test exercise) is sufficient; an AST-based scan that walks every function body for forbidden imports is the v0.2 escalation if a regression slips through.

**Stale-list footgun avoidance:** the probe uses dynamic walk, not an explicit `import stmrr.model.X` per line. If a future Qt-importing module is added, the walk discovers it and the assertion fires. An explicit list would have a stale-list failure mode: a forgotten line means the violation hides behind absence.

**Why the walk discovers more entries than implementation modules:** `pkgutil.walk_packages` returns every package (directories with `__init__.py`, both implementation packages like `world`/`entities`/`state` and scaffold packages like `combat`/`missions`/`resources`/`systems`) plus every module (`.py` files). Importing an empty `__init__.py` doesn't load Qt, so the test passes regardless of how many empty packages exist. The test asserts the _property_ (no Qt in `sys.modules`), not any specific _count_ of entries.

#### Open questions for review

##### Locked decisions

- **Bundling — three modules in one spec, one PR.** Step 3's two-module precedent justifies the shape; the `events.py` ↔ `state.states` forward reference forces the bundling.
- **`GameState` ABC stub only — concretes deferred to gsm step.** Smaller spec, concretes designed against their consumer.
- **`__init_subclass__` enforcement of `allowed_transitions` via `inspect.isabstract(cls)`.** Static typing does not require subclass redeclaration of inherited class attributes. A property abstractmethod is more ceremony for a static lookup table. `__init_subclass__` is the import-time check matching the data shape. `inspect.isabstract(cls)` is mandatory because `cls.__abstractmethods__` is not yet populated inside the hook; `vars(cls)` ensures direct declaration rather than inheritance.
- **Hybrid exception attribute richness (SPEC-ML01 action contracts plus this specification's keyword-only constructor and exact-message contracts).** Each subclass carries the v0.1-UX-relevant attrs as kwargs-only fields with locked `__str__` formats. Bare exceptions force string-parsing; rich-everything is YAGNI for v0.2 concerns.
- **Locked `__str__` formats.** v2.0 localization replaces them with translation keys; v0.1 ships English literals.
- **`_stmrr_events` namespace internal (leading underscore).** Subscribers import named signals; the `Namespace` instance is an implementation detail. Renamed from umbrella's `stmrr_events` to close the namespace-import escape route against `SPEC-ML01` C-004 — public name made it importable, and the namespace's `.signal()` method would have created signals outside `events.py`.
- **`IllegalActionError` and `ModelError` concrete, not abstract.** ABC machinery for an exception class is gratuitous.
- **`NotDockableError` no reason discriminator.** v0.2 problem; current attrs cover v0.1 + v0.2 debugging.
- **`test_no_qt_imports.py` dynamic walk + subprocess isolation, not explicit list and not in-process.** Dynamic walk has no stale-list failure mode. Subprocess isolation is the only clean boundary against `sys.modules`-additive contamination from `pytest-qt` or other view-layer fixtures running earlier in the same pytest process.
- **Per-payload `get_type_hints` expectations.** Three TYPE_CHECKING-deps payloads raise `NameError`; `TurnAdvancedPayload` (int-only) succeeds. The annotation-introspection and event-test contracts above lock the outcomes per payload.
- **`SPEC-S005` FR-008 enforces `SPEC-ML01` C-004 in three layers.** (1) `.importlinter` `blinker-only-in-events` forbidden contract on direct `blinker` imports (mirrors how step 4 promoted Qt-free for projection); (2) `_stmrr_events` namespace renamed with leading underscore, plus regex grep for `.signal(` calls outside `events.py` to close the namespace-import escape route; (3) regex grep for `*Payload` class declarations outside `events.py`. Round-3 audit identified the namespace-import escape; spec now closes it.
- **Annotation deferral follows Python 3.14-native semantics.** The historical PEP 563/649 review established the need for deferred annotation-only imports; current policy does not universally mandate a future import.

## 12. Error Handling and Recovery

### 12.1 Expected Failures

| ID | Failure Mode | User/System Behavior | Logging / Observability | Recovery |
| --- | --- | --- | --- | --- |
| ERR-001 | An action or transition precondition fails. | The corresponding typed `ModelError` leaf is raised with locked facts and message. | Exception tests and later action/state tests capture the contract. | The controller reports or handles the typed failure; no Step 5 retry policy is imposed. |
| ERR-002 | A concrete state omits its own transition set. | Class definition raises `TypeError` naming the class. | State tests capture the import-time failure. | Add the required class-level frozenset. |
| ERR-003 | Runtime hint resolution encounters an annotation-only model name. | `get_type_hints()` raises `NameError` for the three documented payloads. | Per-payload tests distinguish the outcomes. | Use direct attributes or safe non-resolving annotation inspection. |

### 12.2 Retry and Idempotency

Exception and payload construction are side-effect-free. Signal delivery itself is synchronous and not declared idempotent; action owners determine whether a repeated send is valid. Class-definition failures require correcting the class before re-import.

### 12.3 Rollback / Recovery

Step 5 owns no mutable domain or persistent state. Later action and transition specifications define mutation/rollback semantics around these errors and events.

## Appendix B: Agent Implementation Contract

Binding when this spec is implemented by a coding agent. (Applies equally well to human contractors.)

### B.1 Implementation Rules

The implementer shall:

- Read this entire specification before making changes; per session thereafter, re-read at minimum §7 (Requirements), §21 (Open Questions), and the Deviations Log — Background and References may be read once.
- Preserve all explicit non-goals, won't-haves, constraints, and design constraints.
- Treat **Must** requirements as mandatory and **blocking** open questions as hard stops for the affected work.
- On encountering underspecified behavior: file an `OQ-` row **with a proposed default assumption** and proceed on it only if non-blocking — never guess silently.
- On any divergence from the spec: record a `DEV-` row (spec reference, what, why) rather than adapting silently.
- Add or update tests for every implemented requirement; keep §17.3 (traceability) current.
- Follow the milestone order in §19; do not build later milestones on unproven earlier ones.
- Prefer small, reviewable changes; avoid broad refactors unless the spec requires them.
- Document any discovered mismatch between the spec and existing code as a `DEV-` or `OQ-` row.

### B.2 Prohibited Behaviors

The implementer shall not:

- Invent requirements not present in this spec.
- Remove existing behavior unless explicitly required.
- Introduce external services or dependencies not agreed with the owner without an approved `OQ-`.
- Store secrets in source control or print them in CI logs.
- Ignore failing tests unrelated to the change without documenting them.
- Treat examples as exhaustive or normative unless explicitly stated.
- Mark a requirement complete without a verification entry in §17.3.

### B.3 Required Completion Report (verification gate)

At completion, provide:

- Summary of changes and files changed.
- **Requirements implemented, each mapped to the test or command that proves it** — i.e., the completed §17.3 matrix. Claims without verification entries are not accepted.
- Tests added or changed.
- Deviations (`DEV-` rows) and their approval status.
- Known limitations and remaining open questions.
- Documentation deliverables completed (§18.7).

### B.4 Session Handoff

For multi-session implementations: record current milestone, in-progress requirement IDs, and unresolved `OQ-`/`DEV-` items in the repository's session-state/handoff documents at the end of each session, per the repo's documentation convention. The spec records _what and why_; handoff docs record _where work stands_.
