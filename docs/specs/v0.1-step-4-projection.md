## 1. Purpose & Background

This module is the single owner of isometric forward projection, inverse projection against the active z-level, and painter-order values. It deliberately remains pure Python despite living in the view package, giving later scene code one deterministic coordinate contract that can be verified headlessly.

## 6. Glossary

## 8. Architecture and Design

### 8.1 Architecture Summary

`projection.py` is a pure-function view utility with one model value-type dependency. The forward and inverse formulas form one round-trip contract; painter order is a separate bounded integer mapping. Qt scene/item code consumes these outputs but is not imported here.

### 8.2 Architecture Views

#### 8.2.1 Context View

`GridPosition` enters the projection boundary; scene coordinates and painter-order integers leave it for later Qt view components.

#### 8.2.2 Container / Deployment View

The module runs inside the Linux desktop process and headless test process; it has no independent service or datastore.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| Forward projection | World-to-scene mapping. | `world_to_scene()` | Total for every valid `GridPosition`. |
| Inverse projection | Active-layer scene-to-world snapping. | `scene_to_world()` | May return `None` or raise for invalid z. |
| Painter ordering | Bounded cell/layer order. | `z_value_for()` | Ties are intentional. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Use pure functions and no PySide6 import. | Headless correctness and reuse outweigh a Qt convenience wrapper. | A `QTransform` adapter is deferred. | ADR-0003 |
| D-002 | Use the 64×32 diamond formula with 32-pixel z lift. | It is the approved visual geometry for the v0.1 sector. | Other iso variants were rejected. | — |
| D-003 | Round before testing inverse negativity. | Near-origin clicks should snap to the nearest valid cell. | Checking raw negatives was rejected. | — |
| D-004 | Permit painter ties and delegate sub-ordering to item classes. | Projection must not depend on entity-kind precedence. | Encoding item types in the formula was rejected. | — |

> **§8.4 (Solution Alternatives Considered) is Full-tier** and is intentionally omitted at the Standard profile.

### 8.5 Design Constraints

- `MAX_Z_DEPTH` must stay greater than every supported world z value.
- Forward and inverse formulas must remain sign-consistent.
- Projection imports no Qt symbol and performs no sector lookup or mutation.
- The fixed-seed and adjacent-pair painter sampling remains reproducible.

> **§8.6 (Dependency Policy) is Full-tier** and is intentionally omitted at the Standard profile.

## 9. Data Model

No persistent model is owned. Inputs and outputs are immutable `GridPosition` values, primitive numeric scene coordinates, a numeric painter order, and fixed module constants.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. A caller passes a valid world coordinate to `world_to_scene()`.
2. The view positions an item at the returned scene point and assigns `z_value_for()` as painter order.
3. For hit-testing, the view maps the pointer into scene coordinates and calls `scene_to_world()` with the active z-level.
4. The returned coordinate is forwarded to the sector-boundary owner for membership validation.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | The rounded inverse coordinate is negative. | Return `None`. | The caller treats the click as outside the non-negative world. |
| AW-002 | Two items share painter order. | Leave the tie intact. | Qt/item-level insertion or precedence logic resolves sub-order. |

### 10.3 Edge Cases

| ID | Edge Case | Expected Behavior |
| --- | --- | --- |
| EC-001 | A click lies just outside the raw origin boundary. | Round first; return the origin when rounded coordinates are non-negative. |
| EC-002 | z is negative, bool, or another non-int. | Raise the locked `ValueError` or `TypeError`. |
| EC-003 | `sx` or `sy` is non-finite. | Allow Python's native `round()` exception to propagate. |

### 10.4 State Transitions

Not applicable: projection is stateless and mutates neither caller input nor persistent state.

#### Constants and formulas

##### Constants

```python
TILE_WIDTH: int = 64       # iso diamond width in scene pixels
TILE_HEIGHT: int = 32      # iso diamond height in scene pixels (2:1 dimetric)
Z_OFFSET: int = 32         # vertical scene-pixel rise per +1 world z
MAX_Z_DEPTH: int = 10      # painter-ordering headroom; > max GridPosition.z
```

`TILE_WIDTH:TILE_HEIGHT = 2:1` is the standard dimetric (commonly called "isometric" in game dev) ratio. `Z_OFFSET = TILE_HEIGHT` gives one-tile-height vertical rise per z-step — the boring-correct convention used by Diablo, RimWorld, Project Zomboid, and every other tile-iso engine — so a sprite at `(0, 0, 1)` sits visually directly above `(0, 0, 0)`'s diamond top vertex.

`MAX_Z_DEPTH = 10` is locked headroom over the `DESIGN.md` section 4.3 sector ceiling of 7. Any future ADR raising the sector z-ceiling past 9 must confront this constant; see C-003 and the preserved z-headroom invariant.

##### Iso layout choice

**Diamond / screen iso, x-axis northeast, y-axis southeast.** `GridPosition(1, 0, 0)` projects northeast of the origin; `(0, 1, 0)` projects southeast. Higher z renders higher on screen (subtracts from `sy` because Qt's scene-y axis points down). This is the standard `world_to_scene` shape used in every tile-iso reference engine; named explicitly here so a future reader knows immediately which iso variant they're looking at and doesn't try to map staggered-iso intuition onto the formula.

##### Forward formula

```text
sx = (x - y) * TILE_WIDTH / 2
sy = (x + y) * TILE_HEIGHT / 2 - z * Z_OFFSET
```

`world_to_scene` returns `(sx, sy)` as `tuple[float, float]`. `sx` can be negative for cells with `y > x` — that is correct and intended (origin sits at world `(0, 0, 0)`, not at the leftmost visible pixel). `MapView`'s `setSceneRect()` in step 6 handles negative scene coordinates natively.

##### Inverse formula

```text
adjusted_sy = sy + z * Z_OFFSET          # undo the z-lift
raw_x = sx / TILE_WIDTH + adjusted_sy / TILE_HEIGHT
raw_y = adjusted_sy / TILE_HEIGHT - sx / TILE_WIDTH
rounded_x = round(raw_x)
rounded_y = round(raw_y)
if rounded_x < 0 or rounded_y < 0:
    return None
return GridPosition(rounded_x, rounded_y, z)
```

**Round-then-check.** Negativity is checked on `rounded_x` and `rounded_y`, never on `raw_x` or `raw_y`. A click at `sx = -1.0, sy = 0.0` is visually 99% inside the origin tile; it must snap to `(0, 0, z)`, not vanish. Only clicks more than half a tile west or north of the origin's iso position at the active z-level actually fall out of bounds.

**Active-layer offset gotcha.** The "origin" of inverse projection is the active z-level's projected position, not scene `(0, 0)`. At `z = 3`, world `(0, 0, 3)` projects to scene `(0, -96)` because `Z_OFFSET * 3 = 96`. A mouse click at scene `(0, 0)` while the active layer is z=3 inverse-projects to `(3, 3, 3)`, not `(0, 0, 3)` — that's mathematically correct (the click is 96 scene-pixels below the projected layer origin, which is 3 tiles down the iso anti-diagonal). Step 6's mouse handler must pass `sx`/`sy` in scene coordinates, not viewport coordinates, and must understand that "click at scene origin" depends on which layer is active.

**Round-to-nearest.** Python's `round()` (banker's rounding for `.5` ties) is acceptable because the iso-cell hit area is symmetric about its center; the rounding-mode choice doesn't bias hit-testing in practice and the formula is documented as "nearest cell to the click point."

##### `scene_to_world`

```python
def scene_to_world(sx: float, sy: float, z: int) -> GridPosition | None: ...
```

| Aspect | Detail |
| --- | --- |
| Semantics | Inverse-projects `(sx, sy)` against the active z-level per the preserved Inverse formula. Round-to-nearest snapping; `None` if the rounded result has any negative axis. |
| Complexity | O(1). |
| Errors | `ValueError` if `z < 0`. Negative-z input is a caller bug at the function boundary, not a "click missed" — the same taxonomy as SPEC-S003 FR-001/FR-002. `TypeError` if `z` is not `int` (or is `bool`). `sx`/`sy` accept `int` or `float` (the natural shape from `QPointF.x()`/`.y()` and integer literals). **No runtime guard on `sx`/`sy`** — BasedPyright strict checks typed call sites. Behavior on `nan`/`inf`: `round()` raises `ValueError` on `nan` and `OverflowError` on `inf`, propagating without modification — those are caller bugs, not "click missed." `bool` values for `sx`/`sy` are not guarded against; they cannot arise in practice from the mouse path and the approved trade-off favors the simpler signature. **The bool-handling asymmetry is deliberate:** `z` is a discrete layer index, while `sx`/`sy` come from `QPointF` or numeric test literals. Implementations must not add a `bool` guard on `sx`/`sy` "for symmetry." |
| Examples | `scene_to_world(0.0, 0.0, 0)` → `GridPosition(0, 0, 0)` |
| Examples | `scene_to_world(32.0, 16.0, 0)` → `GridPosition(1, 0, 0)` |
| Examples | `scene_to_world(40.0, 18.0, 0)` → `GridPosition(1, 0, 0)` (rounds to nearest) |
| Examples | `scene_to_world(-1.0, 0.0, 0)` → `GridPosition(0, 0, 0)` (raw x ≈ -0.016, rounds to 0 — demonstrates post-rounding negativity rule) |
| Examples | `scene_to_world(-64.0, 0.0, 0)` → `None` (rounds to negative x) |
| Examples | `scene_to_world(0.0, -96.0, 3)` → `GridPosition(0, 0, 3)` (z=3 layer's projected origin sits at scene `(0, -96)`, not `(0, 0)` — see the preserved Active-layer offset gotcha) |
| Examples | `scene_to_world(0.0, 0.0, -1)` → raises `ValueError` |

##### `z_value_for`

```python
def z_value_for(pos: GridPosition) -> int: ...
```

| Aspect | Detail |
| --- | --- |
| Semantics | Returns `(pos.x + pos.y) * MAX_Z_DEPTH + pos.z`. The integer is intended for `QGraphicsItem.setZValue()`; higher values paint in front. |
| Complexity | O(1). |
| Errors | None. |
| Examples | `z_value_for(GridPosition(0, 0, 0))` → `0` |
| Examples | `z_value_for(GridPosition(1, 0, 0))` → `10` |
| Examples | `z_value_for(GridPosition(0, 1, 0))` → `10` (intentional tie — see the Note on intentional ties below) |
| Examples | `z_value_for(GridPosition(0, 0, 1))` → `1` |
| Examples | `z_value_for(GridPosition(2, 1, 3))` → `33` |

**Note on intentional ties.** Two distinct positions with the same `(x + y, z)` produce identical `zValue` (e.g., `(1, 0, 0)` and `(0, 1, 0)`). This is **permitted by design**. Two cases produce ties:

1. **Anti-diagonal ties:** distinct cells with the same `(x + y, z)` — e.g., `(1, 0, 0)` and `(0, 1, 0)`. These are visually distinct on screen (different `(sx, sy)` per the forward formula) and the tie only matters if both cells host an item at the same time.
2. **Same-cell ties:** two items at identical `(x, y, z)`. Per `DESIGN.md` section 4.3, _"Each cell can contain multiple entities"_, and `SectorMap.at(position) -> list[GameObject]` (per `SPEC-ML01` FR-002) returns a list, not a unique occupant. Same-cell occupancy is the canonical model state for, e.g., a `Starship` standing on an `Anomaly`. `z_value_for` returns the same integer for every entity in such a cell.

Both cases are resolved by Qt's stable insertion-order stacking for items sharing a `zValue` (`QGraphicsItem::setZValue()` documentation: items with equal Z stack in insertion order). The painter-correctness invariant `z_value_for` enforces is **"no occluding pair across distinct cells inverts"** (FR-009 and the preserved bounded painter-order invariants) — that's what prevents a high-z foreground tile from disappearing behind a low-z background tile. _Same-cell_ sub-ordering (which sprite paints on top when two ships occupy `(5, 5, 0)`) is **not** `z_value_for`'s job; it belongs to the item classes in step 7 (`StarshipItem`, `AnomalyItem`, etc.) and may use insertion order, `EntityId`, item-kind precedence, or any deterministic tiebreaker the rendering layer chooses. Trying to encode same-cell sub-ordering in `z_value_for` would couple projection to entity-kind precedence rules — a step 7 concern leaking into step 4.

#### Invariants

Properties the rest of the view layer relies on; reviewer should probe these.

1. `world_to_scene` is total — defined for every `GridPosition` (which already guarantees non-negative integer coordinates). Never raises.
2. `world_to_scene(GridPosition(0, 0, 0)) == (0.0, 0.0)` exactly. Origin sits at scene origin.
3. **Painter ordering by anti-diagonal (bounded domain):** for any `p1, p2` with `p1.z < MAX_Z_DEPTH` and `p2.z < MAX_Z_DEPTH` (i.e. within the z-headroom required by `SPEC-S004` A-001 and C-003), if `p1.x + p1.y < p2.x + p2.y` then `z_value_for(p1) < z_value_for(p2)`. (Cells further "back" in iso paint behind cells further "forward.") Outside the bounded domain — z values ≥ `MAX_Z_DEPTH`, which `GridPosition` does not reject — the ordering can invert; `MAX_Z_DEPTH` exists precisely to prevent this within the `DESIGN.md` section 4.3 sector ceiling.
4. **Painter ordering by z at same anti-diagonal (bounded domain):** for any `p1, p2` with `p1.z < MAX_Z_DEPTH` and `p2.z < MAX_Z_DEPTH`, if `p1.x + p1.y == p2.x + p2.y` and `p1.z < p2.z` then `z_value_for(p1) < z_value_for(p2)`. (Higher altitude paints in front at the same depth.)
5. **z-headroom invariant:** for every `GridPosition` constructible under `DESIGN.md` section 4.3's sector ceiling of `z ≤ 6`, `pos.z < MAX_Z_DEPTH`. A future ADR raising the ceiling past z=9 must update `MAX_Z_DEPTH` or the preceding bounded painter-order invariants silently break.
6. **Round-trip identity:** `scene_to_world(*world_to_scene(p), p.z) == p` for every `GridPosition p`. (This is the core formula-consistency property; the preserved Detailed Test Obligations make it a parametrized test over the full 20×20×7 sector.)
7. `scene_to_world` returns `None` only when post-rounding `x` or `y` is negative; never returns a `GridPosition` with negative coordinates (impossible — `GridPosition.__post_init__` would reject it).
8. `scene_to_world` raises `ValueError` exactly when `z < 0`, and `TypeError` exactly when `z` is non-int (matching step 3's `GridPosition` validation taxonomy).
9. The module imports zero PySide6 / Qt symbols. Mechanically enforced by the `.importlinter` `projection-is-qt-free` contract required by NFR-002, plus the static AST-import test in the preserved Detailed Test Obligations as redundancy. Only `stdlib` and `stmrr.model.world.GridPosition` appear in imports.
10. **`z_value_for` is a cell-level / layer-level orderer, not a same-cell sub-orderer.** Two distinct items at identical `(x, y, z)` produce identical `zValue`. Same-cell sub-ordering is a step 7 (item-class) concern.

#### Open questions for review

##### Locked decisions

- **Pure-function module, no PySide6 import.** First view-layer module deliberately keeps Qt out. The `tech-stack-pyside6.md` section 3.3 "apply iso transform once at scene level via `QTransform`" recommendation is a step 6 (`map_view.py`) decision — it applies to the grid-line layer where vector skewing is fine, but is wrong as a blanket scene-level transform for sprite items (sprites would skew unless individually counter-transformed). Per-item precompute via `world_to_scene` is the likely step 6 conclusion for the sprite layer; either way, both paths consume this module's pure-function API. No `as_qtransform()` adapter in this spec.
- **`(TILE_WIDTH, TILE_HEIGHT) = (64, 32)`, `Z_OFFSET = 32`.** A 20×20 sector spans ~1216×608 scene-pixels at 1× zoom — fits comfortably in the 1600×1000 minimum window with chrome budget intact. `Z_OFFSET = TILE_HEIGHT` is the standard one-tile-rise convention.
- **`MAX_Z_DEPTH = 10`.** Locked headroom over the `DESIGN.md` section 4.3 ceiling of 7. The preserved z-headroom invariant pins it.
- **Diamond / screen iso (x → NE, y → SE).** The preserved Forward formula and Inverse formula are explicit and documented; this is not staggered iso.
- **World origin, negative `sx` permitted.** Decouples projection from sector dimensions. `MapView`'s `setSceneRect()` in step 6 handles negative scene coordinates natively.
- **Constants live in `projection.py` as their permanent location**, not deferred-pending-step-6. Tile pixel dimensions are _geometric_ parameters of the iso formula, not theme. Theme (`view/theme/palette.py`) holds colors and fonts; projection holds geometry. See the Cross-references note below.
- **`scene_to_world` signature: `(sx: float, sy: float, z: int) -> GridPosition | None`.** Single function, returns `None` when post-rounding result has any negative axis. Sector-bounds checking is `SectorMap`'s job.
- **Round-then-check negativity.** Round first, then check `rounded_x < 0 or rounded_y < 0`. Clicks just outside the origin tile snap to `(0, 0)` rather than vanishing.
- **Negative z is a `ValueError` at the function boundary**, not a `None`. Caller bug, not a "click missed."
- **Painter formula `(x + y) * MAX_Z_DEPTH + z`, ties permitted.** The painter-correctness invariant `z_value_for` enforces is **"no occluding pair across distinct cells inverts"** (FR-009 and the bounded painter-order invariants), not "no ties period." Two tie cases exist: anti-diagonal ties (`(1, 0, 0)` and `(0, 1, 0)`) and same-cell ties (per `DESIGN.md` section 4.3, _"Each cell can contain multiple entities"_ — `SectorMap.at(position) -> list[GameObject]` per `SPEC-ML01` FR-002 returns a list, not a unique occupant). Both cases resolve via Qt's stable insertion-order stacking. Same-cell sub-ordering — which sprite paints on top when two ships occupy `(5, 5, 0)` — is a step 7 item-class concern, not `z_value_for`'s job. Encoding entity-kind precedence in the projection formula would couple step 4 to entity-class details.
- **The historical targeted mypy strict gate passed during Step 4.** Repository-wide BasedPyright strict now supersedes that one-off checker command.
- **The `projection-is-qt-free` contract shipped with this step.** It remains the current mechanical no-Qt guarantee and is exercised by the repository gate.

## Appendix A: ID Conventions

Stable IDs allow requirements to be referenced from commits, tests, issues, ADRs, and review comments — and let an implementer's completion claims be mechanically checked. Section numbers below match `spec-full-template.md`, so an ID keeps the same "Defined In" reference across every profile.

| Prefix | Meaning                     | Defined In     |
| ------ | --------------------------- | -------------- |
| `G-`   | Goal                        | §4             |
| `NG-`  | Non-goal (never)            | §2.2           |
| `WH-`  | Won't have in v1 (deferred) | §2.3           |
| `A-`   | Assumption                  | §3.3           |
| `C-`   | Constraint                  | §3.4           |
| `FR-`  | Functional requirement      | §7.1           |
| `NFR-` | Non-functional requirement  | §7.2           |
| `IR-`  | Interface requirement       | §7.3           |
| `DR-`  | Data requirement            | §7.4           |
| `D-`   | Design decision             | §8.3           |
| `AW-`  | Alternate workflow          | §10.2          |
| `EC-`  | Edge case                   | §10.3          |
| `ERR-` | Error-handling requirement  | §12.1          |
| `MS-`  | Milestone                   | §19            |
| `OQ-`  | Open question               | §21            |
| `DEV-` | Deviation                   | Deviations Log |

The `R-` (Risk) prefix is Full-tier (§15) and is not used at the Standard profile. Priority values (`Must/Should/Could`) are column values, not ID prefixes — IDs never change when priorities do.

## Appendix B: Agent Implementation Contract

Binding when this spec is implemented by a coding agent. (Applies equally well to human contractors.)

### B.1 Implementation Rules

The implementer shall:

- Read this entire specification before making changes; per session thereafter, re-read at minimum §7 (Requirements), §21 (Open Questions), and the Deviations Log — Background and References may be read once.
- Preserve all explicit non-goals, won't-haves, constraints, and design constraints.
- Treat **Must** requirements as mandatory and **blocking** open questions as hard stops for the affected work.
- On encountering underspecified behavior: file an `OQ-` row **with a proposed default assumption** and proceed on it only if non-blocking — never guess silently.
- On any divergence from the spec: record a `DEV-` row (spec reference, what, why) rather than adapting silently.
- Add or update tests for every implemented requirement; keep §17.3 (traceability) current.
- Follow the milestone order in §19; do not build later milestones on unproven earlier ones.
- Prefer small, reviewable changes; avoid broad refactors unless the spec requires them.
- Document any discovered mismatch between the spec and existing code as a `DEV-` or `OQ-` row.

### B.2 Prohibited Behaviors

The implementer shall not:

- Invent requirements not present in this spec.
- Remove existing behavior unless explicitly required.
- Introduce external services or dependencies not agreed with the owner without an approved `OQ-`.
- Store secrets in source control or print them in CI logs.
- Ignore failing tests unrelated to the change without documenting them.
- Treat examples as exhaustive or normative unless explicitly stated.
- Mark a requirement complete without a verification entry in §17.3.

### B.3 Required Completion Report (verification gate)

At completion, provide:

- Summary of changes and files changed.
- **Requirements implemented, each mapped to the test or command that proves it** — i.e., the completed §17.3 matrix. Claims without verification entries are not accepted.
- Tests added or changed.
- Deviations (`DEV-` rows) and their approval status.
- Known limitations and remaining open questions.
- Documentation deliverables completed (§18.7).

### B.4 Session Handoff

For multi-session implementations: record current milestone, in-progress requirement IDs, and unresolved `OQ-`/`DEV-` items in the repository's session-state/handoff documents at the end of each session, per the repo's documentation convention. The spec records _what and why_; handoff docs record _where work stands_.

## Appendix D: Tailoring

Pick the smallest profile that fits; upgrade if the project grows. Because numbering is stable across profiles, upgrading is **additive**: insert the missing sections at their canonical numbers and set `profile:` in the frontmatter — no existing section or ID reference changes.

| Profile | Template File | Use For |
| --- | --- | --- |
| **Light** | `spec-light-template.md` | Scripts, small tools, single-session agent tasks |
| **Standard** | this file | Typical features and services |
| **Full** | `spec-full-template.md` | Multi-service systems, durable data, external integrations, or multiple stakeholders |

Rules of thumb:

- Owns durable data → §18.6 Backup/DR is required.
- Talks to external paid/rate-limited APIs, makes automated decisions users must trust, or spans multiple services/stakeholders → upgrade to **Full** (adds §5, §8.4, §8.6, §14–§16, §18.4, §20, §19 Waves, and Appendix C modules).
- Implemented by a coding agent → Appendix B is required (it is the cheapest section and the highest-leverage one).
