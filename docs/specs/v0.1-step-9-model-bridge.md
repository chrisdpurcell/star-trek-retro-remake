## 1. Purpose & Background

Step 9 provides the sole model-to-view event seam. Model code publishes typed blinker payloads without importing Qt; `ModelBridge` observes those four signals and re-emits the exact payload objects through identically named Qt signals. This lets the controller and view use Qt's event surface while ADR-0003 keeps the entire model headless.

The v0.1 bridge deliberately stays small: one plain `QObject`, four mechanical receiver methods, a read-only initial-state hook, and explicit lifecycle cleanup. Later typing, threading, fault-isolation, and multi-bridge concerns remain possible without widening this release's seam.

## 2. Scope

### 2.1 In Scope

- One `ModelBridge(QObject)` with four class-level `Signal(object)` attributes.
- Strong blinker subscriptions, payload-identity forwarding, current-state delegation, explicit idempotent teardown, and package re-export.
- The controller-side import-linter contract and focused pytest-qt integration tests.

### 2.2 Out of Scope (Non-Goals — never)

| ID | Non-Goal | Reason |
| --- | --- | --- |
| NG-001 | The bridge shall not implement model rules, mutate game state, or unpack payloads. | It is a transport seam, not a domain service. |
| NG-002 | The bridge shall not make model modules import Qt. | ADR-0003 requires the dependency direction to remain controller-side. |
| NG-003 | The bridge shall not be an ABC or create one QObject per model signal. | Shiboken metaclass constraints and seam simplicity favor one plain object. |
| NG-004 | Teardown shall not depend on `QObject.destroyed`. | Cleanup must occur while the Python receiver and blinker subscriptions are still valid. |

### 2.3 Won't Have in v1 (deferred — not never)

| ID | Deferred Capability | Why Deferred | Revisit When |
| --- | --- | --- | --- |
| WH-001 | Typed Qt emission wrappers. | Four mechanical handlers are identity-tested and no second emitter exists. | Another caller emits bridge signals or the handler surface grows beyond one-screen review. |
| WH-002 | `@Slot` decoration and queued cross-thread delivery. | v0.1 model events are single-threaded direct calls. | A model worker thread or `QueuedConnection` crosses the seam. |
| WH-003 | Per-receiver model fault isolation. | The bridge is the only required model-event subscriber. | Another fallible subscriber connects to a model signal. |
| WH-004 | Registry or context-manager ownership for multiple bridges. | The application owns one bridge for one main window. | A second bridge or independent view subscription is introduced. |
| WH-005 | Free-threaded blinker synchronization. | v0.1 confines mutation and sends to one thread. | The project enables free-threaded multi-thread model mutation. |

| Boundary | Description |
| --- | --- |

| System depends on | Step 5 model events, Step 8 manager/state types, blinker, PySide6, and the controller import boundary. |

## 8. Architecture and Design

### 8.1 Architecture Summary

The bridge sits in `stmrr.controller` and imports both PySide6 and the model's event declarations. That one exception is explicit in import-linter. Model publishers remain unaware of Qt; view consumers remain unaware of blinker and model event declarations. `ModelBridge` holds the manager only to expose the initial state and otherwise forwards events mechanically.

### 8.2 Architecture Views

#### 8.2.1 Context View

Model action or state code sends a blinker event. `ModelBridge` receives the payload and emits its matching Qt signal. A view slot observes the same payload object.

#### 8.2.2 Container / Deployment View

The bridge is an in-process QObject owned by the main window in the Linux desktop application. Integration tests use the offscreen Qt platform. It has no separate service, datastore, or deployment unit.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| `ModelBridge` | Event forwarding, current-state delegation, and teardown. | Four Qt signals, property, teardown. | Plain QObject; no ABC. |
| `model.events` | Typed domain event declarations. | Four blinker signals and frozen payloads. | Remains Qt-free. |
| Import-linter | Single-seam enforcement. | `controller-events-via-bridge-only`. | Whitelists only the bridge edge. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Use one plain QObject for all four signals. | It keeps one lifecycle and one audited seam. | Per-signal objects and an ABC mixin add complexity or fail under Shiboken. | ADR-0003 |
| D-002 | Forward each payload as `object` without translation. | PySide6 lacks the needed parametric signal typing, while model payload identity is already strong. | Typed wrappers remain WH-001. | ADR-0003 |
| D-003 | Use `weak=False` plus explicit teardown. | Strong subscriptions keep the live bridge registered and require an explicit release point. | Default weak receivers and destroyed-signal cleanup were rejected by probes. | — |
| D-004 | Let Qt route slot exceptions to its exception hook. | This matches the locally verified PySide6 runtime and avoids a false propagation promise. | Catching in each receiver would hide Qt behavior and still not isolate model subscribers. | — |

> **§8.4 (Solution Alternatives Considered) is Full-tier** and is intentionally omitted at the Standard profile.

### 8.5 Design Constraints

- Signal names remain identical across the blinker and Qt sides.
- Every handler forwards the exact received payload to its matching signal.
- The bridge catches no model or view exception.
- The owner tears down blinker subscriptions before bridge destruction.
- No controller module other than `model_bridge.py` imports model events.

> **§8.6 (Dependency Policy) is Full-tier** and is intentionally omitted at the Standard profile.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. The application constructs the manager and bridge.
2. The bridge registers each bound receiver with `weak=False`.
3. Model code sends one named blinker signal with a frozen payload.
4. The matching receiver emits the exact object on the identically named Qt signal.
5. A view slot observes the payload; the model sender returns normally.
6. The owning window calls `teardown()` before destroying the bridge.

Expected result: one payload crosses the MVC seam without model Qt imports, translation, or stale subscriptions.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | The view needs an initial render before a transition. | It reads `bridge.current_state`. | The manager's exact current state is returned. |
| AW-002 | Shutdown calls teardown more than once. | Each disconnect operation remains safe. | No receiver remains and no error escapes. |

### 10.3 Edge Cases

| ID | Edge Case | Expected Behavior |
| --- | --- | --- |
| EC-001 | A Qt slot raises during direct delivery. | Qt captures the exception; `emit()` and blinker `send()` return normally. |
| EC-002 | External Python references to a live bridge are dropped. | Strong blinker registrations keep it alive until teardown. |
| EC-003 | A model signal fires after teardown. | No bridge handler or Qt signal runs. |
| EC-004 | A second bridge is proposed. | WH-004 must be resolved before ownership semantics expand. |

### 10.4 State Transitions

Not applicable: Step 9 transports Step 8 state events but defines no bridge lifecycle state machine beyond construction and teardown.

#### Purpose

The **first Qt-touching module in the codebase.** `controller/model_bridge.py` is the single seam where the Qt-free model layer meets PySide6 (`DESIGN.md` section 9.1 — _"the single seam where both worlds meet"_). The model emits four synchronous **blinker** signals on the `_stmrr_events` bus (`model/events.py`); the bridge subscribes to all four and **re-emits each as a Qt `Signal`** that the view layer connects to. This keeps ADR-0003 (`model/` imports no Qt) satisfiable: every PySide6 import lives on the controller side of this seam, and the `view-does-not-import-model-events` `import-linter` contract mechanically forbids the view from bypassing the bridge.

`ModelBridge` ships as a single `QObject` subclass exposing four `Signal(object)` attributes whose names mirror the blinker signals exactly (`ship_moved`, `docked`, `turn_advanced`, `state_changed`), so the translation is mechanical under SPEC-ML01 IR-001. It also holds the `GameStateManager` under the SPEC-ML01 application-ownership lock — _"constructed once in `app.py` and passed into the bridge"_ — and exposes a read-only `current_state` property so the view can render the **initial** mode on startup, before any `state_changed` event fires.

This is a **bridge-only** step: the module, its tests, and a new `tests/integration/conftest.py` fixture. The `app.py` wiring that owns the bridge's lifetime (GSM construction, owner-side `MainWindow.closeEvent` → `bridge.teardown()`) is specified here as the contract for a future `app.py` step but is **not** built now — building it would pull in `MainWindow`, `QGraphicsScene`, and view modules that have no spec yet.

#### Layering and constraints

- **ADR-0003 (model-is-Qt-free)** is _not_ weakened: the bridge lives in `stmrr.controller`, outside the `model-is-qt-free` contract's `source_modules = stmrr.model`. The bridge importing `PySide6` is correct and intended.
- **The bridge is the only module permitted to import both `stmrr.model.events` and `PySide6`.** ADR-0003 and `docs/handoff/architecture.md` both state this seam is _"enforced mechanically by import-linter"_ — so step 9 honors that accepted decision by adding a **fifth `.importlinter` contract** for the controller side, exactly mirroring the in-repo `blinker-only-in-events` idiom (a `forbidden` contract whose single allowed edge is whitelisted via `ignore_imports`):

  ```ini
  [importlinter:contract:controller-events-via-bridge-only]
  name = Only model_bridge imports model.events within the controller
  type = forbidden
  source_modules =
      stmrr.controller
  forbidden_modules =
      stmrr.model.events
  ignore_imports =
      stmrr.controller.model_bridge -> stmrr.model.events
  allow_indirect_imports = True
  ```

  The `ignore_imports` line whitelists the one direct edge the bridge needs (covering both its runtime signal import and its `TYPE_CHECKING` payload imports — import-linter sees both); `allow_indirect_imports = True` permits legitimate transitive paths such as a future `action_handlers → model_bridge → model.events`. The contract **lands in the same step/commit as `model_bridge.py`** so `lint-imports` stays green (adding it earlier would fail on the not-yet-existing `model_bridge` edge). The **view** side stays enforced by the existing `view-does-not-import-model-events`; the other four contracts (`model-is-qt-free`, `view-does-not-import-model-events`, `projection-is-qt-free`, `blinker-only-in-events`) are unchanged. (Round-1 review SA-003 surfaced the gap; an interim regex-scan test was considered but rejected at round 2 — an import-linter contract matches ADR-0003's wording and the `blinker-only-in-events` precedent, so **no ADR/architecture amendment is needed**.)

- **`blinker-only-in-events`** is unaffected: that contract forbids direct `blinker` imports _outside `model.events`_ within the model tree (`allow_indirect_imports = True`). The bridge imports the named **signals** (`from stmrr.model.events import ship_moved, ...`), not `blinker` itself, and is outside the model tree regardless.
- **`test_no_qt_imports.py` (SPEC-ML01 NFR-001)** is unaffected: it walks only `stmrr.model.*` in a **subprocess**, so PySide6 being loaded in the main pytest process by the integration tests does not pollute it. No change to that test.
- Python 3.14-native annotation semantics apply; a universal `from __future__ import annotations` directive is no longer required. BasedPyright strict governs the source and test trees.
- **Imports** (runtime vs. `TYPE_CHECKING`):
  - **Runtime:** `from PySide6.QtCore import QObject, Signal`; `from stmrr.model.events import docked, ship_moved, state_changed, turn_advanced` (the signal objects are needed for `.connect()` / `.disconnect()`).
  - **`TYPE_CHECKING` only:** `from stmrr.model.events import DockedPayload, ShipMovedPayload, StateChangedPayload, TurnAdvancedPayload` (used only as `_on_*` parameter annotations — strings under deferred evaluation); `from stmrr.model.state.game_state_manager import GameStateManager` and `from stmrr.model.state.states import GameState` (used only as annotations on `__init__`, the `_manager` attribute, and the `current_state` property). The bridge calls `self._manager.current_state` by duck-typed attribute access, never `isinstance`, so no runtime import of `GameStateManager`/`GameState` is required.
- No new dependencies (`PySide6>=6.5`, `blinker>=1.8`, `pytest-qt>=4.4` already declared in `pyproject.toml`).
- Module + class docstrings mandatory. Method docstring on `teardown` (the two-obligation teardown is non-obvious) and on `current_state` (initial-render rationale). `_on_*` handlers carry a one-line comment noting they are blinker receivers, not Qt slots.

#### `controller/model_bridge.py` specification

##### Class declaration

```python
from typing import TYPE_CHECKING

from PySide6.QtCore import QObject, Signal

from stmrr.model.events import docked, ship_moved, state_changed, turn_advanced

if TYPE_CHECKING:
    from stmrr.model.events import (
        DockedPayload,
        ShipMovedPayload,
        StateChangedPayload,
        TurnAdvancedPayload,
    )
    from stmrr.model.state.game_state_manager import GameStateManager
    from stmrr.model.state.states import GameState


class ModelBridge(QObject):
    """The single MVC seam: re-emits model blinker events as Qt signals.

    Subscribes to the four `model.events` blinker signals and re-emits each
    as an identically named Qt `Signal(object)` carrying the same frozen
    payload dataclass instance. This is the ONLY module that imports both
    `PySide6` and `stmrr.model.events` (DESIGN.md section 9.1); it is what keeps
    ADR-0003's model-is-Qt-free rule satisfiable.

    Holds the GameStateManager under the SPEC-ML01 application-ownership lock so the view can read the
    initial `current_state` on startup — before the first `state_changed`
    transition fires.

    NOT an ABC: subclassing `QObject` alongside `abc.ABC` raises a Shiboken
    metaclass TypeError (the plain-`QObject` decision). Plain QObject subclass only.
    """

    ship_moved = Signal(object)
    docked = Signal(object)
    turn_advanced = Signal(object)
    state_changed = Signal(object)

    def __init__(self, manager: GameStateManager, parent: QObject | None = None) -> None: ...
    @property
    def current_state(self) -> GameState: ...
    def teardown(self) -> None: ...
    # private blinker receivers: _on_ship_moved, _on_docked, _on_turn_advanced, _on_state_changed
```

The four `Signal(object)` declarations **must be class-level attributes** — declaring a `Signal` inside `__init__` raises `AttributeError` on `.connect()`/`.emit()` (the plain-`QObject` and class-level-signal decision). `Signal(object)` is the PySide6 idiom for a signal carrying an arbitrary Python value, including a frozen dataclass (the intact-payload decision).

##### `__init__(manager, parent=None)` semantics

1. `super().__init__(parent)` — pass `parent` through to `QObject`; `None` for the test fixture, the `MainWindow` under the owner-side teardown and future `app.py` wiring contract.
2. Store the manager: `self._manager: GameStateManager = manager`.
3. Connect each blinker signal to its private receiver with **`weak=False`**:

   ```python
   ship_moved.connect(self._on_ship_moved, weak=False)
   docked.connect(self._on_docked, weak=False)
   turn_advanced.connect(self._on_turn_advanced, weak=False)
   state_changed.connect(self._on_state_changed, weak=False)
   ```

   `weak=False` is **load-bearing** under the strong-subscription decision: blinker holds receivers weakly by default, and the receivers are bound methods of `self`. With the default `weak=True`, once the only external reference to the bridge is dropped, blinker silently stops invoking the handlers — no exception, no log. `weak=False` makes blinker hold the bridge strongly, so subscriptions survive for the bridge's lifetime; `teardown()` is the explicit counterpart that releases them.

No defensive `isinstance(manager, GameStateManager)` check — the annotation is the contract (consistent with the SPEC-S008 Q4 lock).

##### `current_state` property

```python
@property
def current_state(self) -> GameState:
    """The model's current state, for initial view render on startup.

    The view reads this once at wire-up to render the starting mode
    (e.g. MainMenu) before any `state_changed` transition fires; thereafter
    it tracks transitions via the `state_changed` Qt signal.
    """
    return self._manager.current_state
```

Read-only — no setter. This is the sole reason the bridge holds the manager; without it `self._manager` would be a stored-but-unread attribute.

##### Blinker receivers `_on_*`

Blinker invokes a receiver as `receiver(sender, **kwargs)`; the model sends `signal.send(self, payload=Payload(...))` under SPEC-ML01 IR-001. Each receiver therefore takes the sender positionally and `payload` keyword-only, and re-emits on the corresponding Qt signal:

```python
def _on_ship_moved(self, _sender: object, *, payload: ShipMovedPayload) -> None:
    # blinker receiver — not a Qt slot; @Slot is deferred by OQ-002.
    self.ship_moved.emit(payload)

def _on_docked(self, _sender: object, *, payload: DockedPayload) -> None:
    self.docked.emit(payload)

def _on_turn_advanced(self, _sender: object, *, payload: TurnAdvancedPayload) -> None:
    self.turn_advanced.emit(payload)

def _on_state_changed(self, _sender: object, *, payload: StateChangedPayload) -> None:
    self.state_changed.emit(payload)
```

- The `_sender` parameter is unused (named `_sender` to signal that). The bridge re-emits for any sender; v0.1 has exactly one sender per signal under SPEC-ML01 IR-001.
- The **same payload instance** is forwarded — no copy, no field unpacking. The payload is a frozen dataclass; the Qt slot narrows it with `assert isinstance(payload, ShipMovedPayload)` under the intact-payload decision.
- The typed `payload` parameter narrows the payload type **within the handler body**, but its Qt signal's `emit()` call itself is unchecked — the verified PySide6 stubs typed `SignalInstance.emit` as `*args: Any`. Bridge-to-Qt payload correctness is pinned by the per-signal payload-identity tests, not by the static checker.

##### `teardown()` — blinker disconnect

```python
def teardown(self) -> None:
    """Disconnect all four blinker subscriptions.

    Independent of Qt-side teardown: Qt object-tree parenting disconnects
    the *Qt signal* connections (view slots ← bridge signals) when the
    parent is destroyed, but does NOT touch the *blinker* subscriptions
    (bridge ← model events). Both are required for a clean shutdown; this
    method owns the blinker half. Must be called by the bridge's OWNER
    BEFORE the bridge is destroyed (e.g. `MainWindow.closeEvent`), NOT via
    `self.destroyed.connect(self.teardown)` — see the owner-side teardown decision.
    """
    ship_moved.disconnect(self._on_ship_moved)
    docked.disconnect(self._on_docked)
    turn_advanced.disconnect(self._on_turn_advanced)
    state_changed.disconnect(self._on_state_changed)
```

`blinker.Signal.disconnect(receiver)` of a receiver that is not currently connected is a no-op (does not raise), so `teardown()` is safe to call more than once; the bridge fixture always calls it once in teardown regardless of what a test did.

##### Error policy: the bridge catches nothing; Qt absorbs view-slot exceptions

The bridge wraps **nothing** in try/except. But — verified empirically against the project's pinned **PySide6 6.11.0** (`uv.lock`; see the focused slot-exception probe below) — a Qt slot that raises during its Qt signal emission does **NOT** propagate back through `emit()`. PySide6 routes the unhandled slot exception to `sys.excepthook` and `emit()` returns normally; the exception therefore does **not** travel `slot → emit() → _on_* → blinker send() → model method`. The blinker `send()` that the model called returns normally with the receiver-result list, oblivious to the view slot's failure.

The accurate v0.1 policy, then:

- The **bridge** never sees or suppresses a view-slot exception — there is nothing for it to catch, because the exception never reaches the `_on_*` frame.
- The **model mutation** that justified the event has already committed before `send()` was called under SPEC-ML01 NFR-002 and FR-011, and stays committed — consistent with SPEC-S008's propagate-without-rollback contract, though by a different mechanism (Qt's exception absorption, not synchronous propagation).
- A failing view slot surfaces through **Qt/Python exception reporting** (`sys.excepthook` in production; pytest-qt's automatic capture in the focused error test), **not** as an exception in model or controller code. Model/controller callers must **not** be promised synchronous propagation from view slots.
- Conversely, a **blinker-receiver** exception (i.e. a bug inside `_on_*` itself, before `emit()`) _does_ propagate out of `send()` per blinker's contract — but the bridge's `_on_*` bodies are a single `emit()` call and do not raise. SPEC-ML01 ERR-006 and WH-004 concern _blinker-side_ receiver faults (a second model subscriber), not the Qt-slot faults discussed here; they remain v0.2 escalations unchanged.

App-level handling of view-slot exceptions (fatal-error dialog, structured logging via a `sys.excepthook` install, or a Qt message handler) is deferred to the future `app.py`/bootstrap spec. v0.1 fixes the behavior of the bridge only: it neither catches nor masks slot exceptions, and it makes no propagation promise to its blinker/model callers.

##### Worked example

```python
from PySide6.QtCore import QObject
from stmrr.controller.model_bridge import ModelBridge
from stmrr.model.events import ShipMovedPayload, ship_moved
from stmrr.model.state.game_state_manager import GameStateManager
from stmrr.model.state.states import MainMenuState

bridge = ModelBridge(GameStateManager(MainMenuState()))
assert isinstance(bridge.current_state, MainMenuState)  # initial render hook

received: list[object] = []
bridge.ship_moved.connect(received.append)              # a view slot would do this

payload = ShipMovedPayload(ship_id=..., from_position=..., to_position=...)
ship_moved.send(object(), payload=payload)              # the model fires the blinker event
assert received == [payload]                            # same instance, re-emitted on Qt side

bridge.teardown()                                       # releases the blinker subscriptions
ship_moved.send(object(), payload=payload)              # no longer re-emitted
assert received == [payload]                            # unchanged
```

#### Cross-cutting design decisions

##### Single `ModelBridge` QObject, not one QObject per signal

One `QObject` owning all four `Signal`s — the `WorkerSignals(QObject)` idiom from Qt's own threading documentation. One object means one ownership point in `app.py`, one uniform thread affinity, and one teardown call. Per-signal QObjects would multiply ownership, parenting, and teardown surface for zero benefit at four signals. (OQ best-practice, research `…-open-questions.md`.)

##### Plain `QObject`, never `QObject + ABC`; `Signal`s are class-level

`class ModelBridge(QObject, ABC)` raises `TypeError: Shiboken.ObjectType.__new__(...) is not safe` — Shiboken's metaclass conflicts with `ABCMeta`. The bridge is a plain `QObject` subclass. This is a real trap because the model layer leans heavily on ABCs (`GameState`), so the instinct to reach for `ABC` must be explicitly resisted. Likewise, a `Signal` declared inside `__init__` rather than at class scope raises `AttributeError` on first `.connect()` — the descriptor protocol requires class-level declaration. (OQ footguns, both corroborated.)

##### `weak=False` on every blinker connection

blinker's `connect(receiver, weak=True)` default holds receivers via weak reference. The bridge's receivers are **bound methods** (`self._on_*`), whose weakref tracks the bridge instance; when the last external reference to the bridge is dropped, blinker silently stops calling them — no error, no log (`has_receivers_for()` even keeps returning `True` for the dead receiver). For a long-lived singleton bridge this is a latent "events silently stop arriving" bug. `weak=False` makes blinker hold the bridge strongly; `teardown()` is the explicit release. The GC-survival test in the focused integration matrix pins this. (OQ headline footgun.)

##### `Signal(object)` carrying the intact frozen payload

The four payloads carry non-primitive fields (`EntityId`/`NewType`, `GridPosition`, `type[GameState]`) that cannot be expressed as Qt primitive signal types. `Signal(object)` carries the whole frozen dataclass; the receiving slot narrows it with `assert isinstance(payload, ShipMovedPayload)`. No field unpacking — that would couple the bridge to each payload's shape and lose the single-`object` uniformity.

##### No typed `emit_*()` wrappers in v0.1 (OQ-001)

**Historical May 2026 stub evidence:** neither the official PySide6 stubs nor `PySide6-stubs` 6.7.3.0 provided a parametric `Signal[T]`. The bundled stub typed the emit method as `def emit(self, /, *args: typing.Any) -> None` (`QtCore.pyi:11015`), so a direct emission accepted any payload type under the then-current checker. A typed `emit_ship_moved(self, payload: ShipMovedPayload)` wrapper would add static protection against cross-wiring, but current acceptance continues to rely on the per-signal identity tests unless the installed stubs prove a stronger contract.

**Wrappers are nonetheless deferred** as a small-surface YAGNI tradeoff, not because a static checker covers the gap. The surface is four one-line handlers, each emitting on the identically named signal with the payload it just received; the mapping is mechanical and visually verifiable in one screen. **Correctness is pinned by tests, not the type checker:** the bridge integration suite fires each real blinker signal and asserts that the exact payload object arrives on the matching Qt signal. The wrapper becomes worthwhile in v0.2 if a second, non-blinker caller needs to emit a bridge signal, or if the handler count grows enough that visual verification stops being reliable. View slots annotate `payload: object` and narrow with `isinstance` under the verified stub surface.

##### No `@Slot` on `_on_*` in v0.1 (OQ-002)

`@Slot` is cosmetic on the `_on_*` handlers here, for two independent reasons: (a) they sit in blinker's receiver table and are invoked as plain Python callables — Qt's meta-object slot dispatch never touches them; (b) v0.1 is single-threaded (`DirectConnection`), which needs no `@Slot` regardless. `@Slot` becomes load-bearing on the **view-slot** side (not the bridge) only under a cross-thread `QueuedConnection`, where an undecorated slot's proxy can segfault (confirmed PySide6 6.6–6.8). **v0.2 trigger to document:** _when a background model thread is introduced, add `@Slot(object)` to view slots invoked via `QueuedConnection` — not to the bridge's blinker handlers._

##### Two orthogonal teardown obligations + the future `app.py` wiring (OQ-004)

Shutdown has **two** independent cleanup paths that must not be conflated:

| Obligation | What it disconnects | Mechanism |
| --- | --- | --- |
| Qt side | view slots ← bridge `Signal`s | Qt object-tree parenting: `~QObject` auto-disconnects when the parent (`MainWindow`) is destroyed |
| blinker side | bridge `_on_*` ← model events | **explicit** `bridge.teardown()` — Qt parenting does NOT touch blinker |

The future `app.py` owns both: it constructs the GSM, constructs `ModelBridge(manager, parent=main_window)` (Qt side handled by parenting), and calls **`bridge.teardown()` explicitly from the owner before the bridge is destroyed** — e.g. in `MainWindow.closeEvent()`.

**Do NOT wire `bridge.destroyed.connect(bridge.teardown)`.** A focused PySide6 6.11.0 probe verified that self-wiring does not perform the blinker disconnect: after `deleteLater()` + event processing, a subsequent blinker `send()` still invoked the bridge's `_on_*` handler (and, in the reviewer's environment, raised `RuntimeError: Signal source has been deleted` from the dead QObject). The root cause is that the blinker subscription is held with `weak=False` and is only released by the explicit `disconnect()` in `teardown()`; relying on the destroyed object's _own_ bound method to run that disconnect during/after destruction is unreliable. The validated pattern is an **external owner-side call** while the bridge is still alive:

```python
# future app.py / MainWindow — NOT built in step 9
def closeEvent(self, event):
    self._bridge.teardown()      # release blinker subs while bridge is alive
    super().closeEvent(event)
```

Qt object-tree parenting still handles the Qt-signal half automatically when the window is destroyed. This wiring is **specified, not built** in step 9 — but the focused integration matrix includes a lifetime test that proves the owner-side pattern: after an explicit `teardown()`, a real blinker `send()` invokes no bridge handler and raises nothing.

##### Manager injection over no-arg construction

The SPEC-ML01 application-ownership contract locks _"`GameStateManager` … constructed once in `app.py` and passed into the bridge."_ The bridge therefore takes `manager` as a required constructor argument (not the no-arg `ModelBridge()` the research sketch assumed). The `current_state` property is the concrete consumer of that reference. No singleton, no module-level instance, no DI container — the same rationale the umbrella gives for the GSM itself.

#### Invariants

Properties step 9 contributes; a reviewer should probe these.

1. **The bridge is the sole model→view event path.** It is the only module importing both `stmrr.model.events` and `PySide6`. Enforced on both sides by import-linter: `view-does-not-import-model-events` blocks the view; the new `controller-events-via-bridge-only` contract blocks every controller module except `model_bridge.py`. (DESIGN section 9.1 / ADR-0003, _"mechanically enforced"_.)
2. **Qt signal names equal blinker signal names** (`ship_moved`, `docked`, `turn_advanced`, `state_changed`). A rename on either side without the other breaks the mechanical mapping; tests assert each pairing.
3. **Payloads cross the seam by identity, unmodified.** `_on_*` forwards the exact frozen dataclass instance; no copy, no field unpacking. Tested by an `is`-identity assertion.
4. **All four blinker connections use `weak=False`.** blinker wraps bound-method receivers in a `WeakMethod` that dies only when the bridge _instance_ is collected — so `weak=False` (a strong ref) is what keeps a long-lived bridge subscribed once external references drop. Pinned by the focused GC-survival test, which drops all strong refs + `gc.collect()` and asserts the bridge survives (proven to fail under the `weak=True` default).
5. **`teardown()` releases exactly the four blinker subscriptions and is idempotent.** It does not touch Qt-side connections (those are Qt-parenting's job). It must be called **owner-side, before the bridge is destroyed** (`MainWindow.closeEvent`), never via `self.destroyed.connect(self.teardown)` — the latter does not perform the disconnect (SA-002).
6. **The bridge catches nothing, and a raising view slot does NOT propagate back to model/controller code.** On PySide6 6.11.0 (verified by the focused slot-exception probe and error-policy contract), a slot exception during `emit()` is routed to `sys.excepthook` (pytest-qt's capture in tests); `emit()` and the model's blinker `send()` return normally. The model mutation stays committed under SPEC-ML01 NFR-002 and FR-011 (same end-state as SPEC-S008's propagate-without-rollback contract, different mechanism). No synchronous-propagation promise is made to callers.
7. **`ModelBridge` is a plain `QObject`, not an ABC.** No `abc.ABC` in its MRO (Shiboken metaclass constraint and the plain-`QObject` decision).
8. **`Signal`s are class-level attributes.** They are not declared in `__init__` (the class-level-signal decision).
9. **`current_state` is read-only and delegates to the injected manager.** It is the only consumer of `self._manager`; the bridge performs no `isinstance`/`type` dispatch on the manager.
10. **One new `.importlinter` contract (`controller-events-via-bridge-only`); no umbrella amendment.** The new contract conforms to ADR-0003's "enforced mechanically by import-linter" for the controller-side seam. No umbrella amendment: step 9 is the first controller module, and the SPEC-ML01 module table and DAG describe `stmrr.model.*` only — they are not extended by a controller module. The bridge is described by `DESIGN.md` section 9.1 and the umbrella layering/event contracts.
11. **`stmrr.controller` re-exports `ModelBridge`.** `controller/__init__.py` exposes `ModelBridge` with `__all__ == ["ModelBridge"]`, mirroring Step 8's `state/__init__.py` discipline. Pinned by the focused package-export test.

#### Open questions

##### Locked decisions

- **Single `ModelBridge(QObject)` holding four `Signal(object)`** — not per-signal QObjects.
- **Plain `QObject` subclass, no `ABC`; `Signal`s declared at class scope.**
- **`weak=False` on all four blinker connections; explicit `teardown()` for release.**
- **Payload carried intact as `object`; view narrows with `isinstance`.**
- **No typed `emit_*()` wrappers in v0.1** — the verified stub surface typed `.emit()` as `*args: Any`, so a wrapper would add static safety, but it is deferred as a small-surface YAGNI tradeoff with correctness pinned by per-signal payload-identity tests, not the checker (SA-004).
- **No `@Slot` on `_on_*`** — blinker receivers, single-thread; v0.2 trigger (`QueuedConnection` across threads) documented by OQ-002.
- **Error policy: the bridge catches nothing; on PySide6 6.11.0 a raising view slot is routed to `sys.excepthook` (pytest-qt capture in tests) and `emit()`/`send()` return normally — no propagation to model/controller** (SA-001). Model mutation stays committed (same end-state as SPEC-S008's propagate-without-rollback contract).
- **`__init__(manager, parent=None)`; manager required** by the SPEC-ML01 application-ownership contract; `current_state` is its consumer.
- **`current_state` read-only, delegates to manager** — initial-render hook for the view.
- **Bridge-only scope; `app.py` wiring (owner-side `MainWindow.closeEvent` → `bridge.teardown()`, GSM construction) specified but not built. NOT `destroyed.connect(teardown)`** (SA-002).
- **One new `.importlinter` contract (`controller-events-via-bridge-only`, mirroring `blinker-only-in-events`); no umbrella amendment** — conforms to ADR-0003, SPEC-ML01 C-004, and SPEC-S009 NFR-001 (SA-003).
- **Tests under `tests/integration/` (qtbot) via a function-scoped `bridge` fixture in a new `tests/integration/conftest.py`**; the single-seam controller rule is enforced by the import-linter contract, not a test.

##### Still open (v0.2 concerns, NOT v0.1 blockers)

1. **Parametric `Signal[T]` typing.** Historical May 2026 stubs exposed no supported path; stronger type-checker or stub support may change that. View slots accept `object` and narrow with `isinstance` for now. Track `python-qt-tools/PySide6-stubs`. (Research OQ-001.)
2. **`@Slot` + `QueuedConnection` when a model worker thread lands.** v0.2 must add `@Slot(object)` to _view_ slots crossing threads (not the bridge handlers), or a non-decorated proxy may segfault on PySide6 6.6–6.8. (Research OQ-002.)
3. **`_send_robust` fault isolation.** When a second non-bridge subscriber connects to any signal, a raising receiver could skip the bridge (or vice versa). Implement the per-receiver try/except utility then under SPEC-ML01 WH-004 and SPEC-S007 WH-005.
4. **Python 3.14 free-threading.** blinker's `receivers` dict is unlocked; safe under v0.1's single-thread assumption, a data race under a free-threaded multi-thread model. Confine model mutation/sends to one thread or lock `send()` in v0.2. (Research, compatibility.)
5. **A bridge registry / multi-bridge ownership.** If a second `ModelBridge` instance or multiple independent view subscribers appear, revisit single-instance ownership and the context-manager-vs-`teardown()` choice. (Research OQ-004.)

## 12. Error Handling and Recovery

### 12.1 Expected Failures

| ID | Failure Mode | User/System Behavior | Logging / Observability | Recovery |
| --- | --- | --- | --- | --- |
| ERR-001 | A connected Qt slot raises. | Qt routes the exception to its exception hook; model `send()` returns normally. | pytest-qt `capture_exceptions()` and `sys.excepthook` observe the error. | Repair or disconnect the view slot. |
| ERR-002 | The owner destroys the bridge without teardown. | Strong blinker receivers may target a deleted QObject. | Lifetime regression tests reproduce the unsafe ordering. | The owner must call `teardown()` before destruction. |
| ERR-003 | A model receiver other than the bridge raises. | Blinker's synchronous send may stop before later receivers run. | The original exception propagates from model publication. | Resolve WH-003 when another fallible subscriber is introduced. |
| ERR-004 | A bridge signal is cross-wired. | A payload reaches the wrong view channel. | Per-signal identity tests fail. | Correct the mechanical handler-to-signal mapping. |

### 12.2 Retry and Idempotency

Event forwarding is synchronous and is not retried. Retrying a model event could duplicate an already observed view update. `teardown()` is intentionally idempotent so repeated owner cleanup remains safe.

### 12.3 Rollback / Recovery

The bridge stores no event data and performs no model mutation, so there is no bridge-local rollback. Recovery consists of repairing the failing view receiver or ownership order, calling `teardown()` when needed, and recreating a bridge only under the application's single-owner policy.
