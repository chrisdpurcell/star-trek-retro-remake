## 1. Purpose & Background

Step 6 establishes the model's bounded entity container and first dock target before the action layer depends on either contract. It combines `SectorMap` and `Station` so identity lookup, position bounds, docking eligibility, deterministic query order, and forward-compatible station data are reviewed as one world-surface boundary.

## 2. Scope

### 2.1 In Scope

- A validated, dict-backed, three-dimensional `SectorMap`.
- Deterministic entity insertion, lookup, removal, position queries, containment, count, and snapshot behavior.
- A starbase-only v0.1 `Station` with an intentionally wider future-facing type alias.
- Immutable service normalization and the private `_Dockable` predicate contract.
- Package exports, focused tests, umbrella-spec reconciliation, and the implemented import-cycle deviation.

### 2.2 Out of Scope (Non-Goals — never)

| ID | Non-Goal | Reason |
| --- | --- | --- |
| NG-001 | `SectorMap` shall not own action logic or emit action events. | Action methods own validation, mutation, and event emission. |
| NG-002 | `SectorMap` shall not expose an ambiguous public `__iter__`. | Callers must choose the ordered `entities` snapshot or an explicit query. |
| NG-003 | `Station` shall not import `Starship` or other later action-layer types. | The docking predicate depends only on the private structural contract and must not create a backedge. |
| NG-004 | `SectorMap` shall not provide a second position-mutation API. | Entity action methods own position changes and their preconditions. |

### 2.3 Won't Have in v1 (deferred — not never)

| ID | Deferred Capability | Why Deferred | Revisit When |
| --- | --- | --- | --- |
| WH-001 | Spatial indexing, multi-cell pathing, line of sight, and field of view. | v0.1 entity counts and single-cell actions do not require the added mutation complexity. | Profiling or v0.2 pathfinding demonstrates a need. |
| WH-002 | Sector and station TOML serialization. | Persistence is owned by a later specification. | Save/load schema work begins. |
| WH-003 | Civilian, military, and neutral station instances. | v0.1 requires only the starbase Dock target. | A later release implements those station behaviors. |
| WH-004 | Faction or reputation docking gates. | v0.1 eligibility is exactly the dockable's active state. | The faction/reputation model is approved. |

## 8. Architecture and Design

### 8.1 Architecture Summary

`SectorMap` is a mutable identity-equal container whose only runtime project dependency is `GridPosition`; `GameObject` and `EntityId` are type-only because eager package re-exports create a cycle. `Station` is a `GameObject` runtime subclass that owns constructor validation and a private structural docking predicate. Neither module imports the action layer or emits events.

### 8.2 Architecture Views

#### 8.2.1 Context View

The wire-up layer owns one `SectorMap`. Step 7 actions resolve entities and query bounds through it; `Station` supplies the approved Dock target.

#### 8.2.2 Container / Deployment View

Both modules run in-process in the local desktop application and headless test processes; neither is independently deployed.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| `world/sector_map.py` | Bounded membership and spatial queries. | `SectorMap`. | Dict-backed; `GameObject` and `EntityId` are type-only. |
| `entities/station.py` | Starbase validation, service normalization, and docking predicate. | `Station`, `StationType`. | `_Dockable` remains private. |
| Package and leaf surfaces | Stable public imports. | `world.__all__`, `entities.__all__`, `station.__all__`. | `StationType` is leaf-only; private helpers stay hidden. |
| Focused tests | Behavioral, identity, and import evidence. | pytest, import-linter, BasedPyright. | Current repository gate uses coverage.py. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Use a plain dict-backed `SectorMap` with identity equality and no public iterator. | It preserves deterministic order without a second mutable index or ambiguous iteration. | Dataclass, spatial shadow index, and implicit iteration were rejected for v0.1. | — |
| D-002 | Use `ValueError` for invalid adds and `KeyError` for missing removes. | One is a wrong-value setup condition; the other is a failed key deletion. | Action-layer exceptions and symmetric error types were rejected. | — |
| D-003 | Type `accepts_dock()` through a private `_Dockable` protocol. | The method reads only `active` and must not import the later Starship module. | `GameObject`, a Starship stub, and an ignored missing import were rejected. | ADR-0003 |
| D-004 | Declare four station types but accept one through an immutable runtime subset. | v0.1 saves remain forward-compatible without enabling unimplemented behavior. | A one-value literal and exhaustive branch chain were rejected. | ADR-0004 |
| D-005 | Validate every Station-specific argument before allocating identity. | Failed construction must leave `_entity_id_counter` contiguous. | Post-super validation was rejected. | — |
| D-006 | Keep `SectorMap` entity types under `TYPE_CHECKING`. | The eager import cycles through package re-exports; annotations and duck-typed bodies do not require it at runtime. | The originally specified runtime import was implemented only long enough to expose the cycle. | ADR-0003 |

> **§8.4 (Solution Alternatives Considered) is Full-tier** and is intentionally omitted at the Standard profile.

### 8.5 Design Constraints

- Dict insertion order is the replay-determinism anchor.
- Soft deletion and hard removal remain distinct.
- Station validation precedes identity allocation.
- `SectorMap` imports `GridPosition` at runtime and entity types only for static analysis.
- Neither module creates a runtime or type-only dependency on Step 7 action modules.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. The wire-up layer constructs a positive-dimension `SectorMap`.
2. It constructs a validated `Station`; invalid input fails before identity allocation.
3. It adds the station after the bounds and duplicate-ID checks.
4. Later actions resolve the same object by ID or query it by position.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | A map lookup uses an absent ID. | `get()` returns `None`. | The action owner classifies the missing target. |
| AW-002 | A caller deactivates an entity without removing it. | Position and snapshot queries still include it. | Soft-deleted membership remains inspectable. |
| AW-003 | A services generator is supplied. | Materialize it once, validate every element, then freeze it. | The stored services are deterministic and immutable. |

### 10.3 Edge Cases

| ID | Edge Case | Expected Behavior |
| --- | --- | --- |
| EC-001 | One entity violates bounds and duplicates an existing ID. | The bounds `ValueError` wins and membership is unchanged. |
| EC-002 | Services contain an unhashable non-string. | The Station-specific element `TypeError` wins before `frozenset()` runs. |
| EC-003 | Two maps or stations have identical visible values. | They remain unequal, identity-hashed objects. |

#### Purpose

Two modules that complete the v0.1 model layer's **world surface** — the bounded grid container plus the first non-ship inhabitant:

- `model/world/sector_map.py` — `SectorMap(width, height, depth)`: dict-backed entity container with bounds checking, ID-keyed lookup, position-indexed lookup, and snapshot iteration. Owns no actions; owned by the wire-up layer per the SPEC-ML01 world-ownership contract.
- `model/entities/station.py` — `Station(GameObject)`: dock-target subclass with a forward-compatible `station_type` Literal (v0.1 accepts only `"starbase"`), an immutable `services` set, and the `accepts_dock` predicate the action pipeline calls.

They land together because (a) `Station.accepts_dock` is what `Starship.dock_at` (step 7) will call, and `Starship.dock_at` will resolve the station via `SectorMap.get`; designing the container and the dock-target together surfaces ID-resolution and bounds-check decisions a per-module spec would miss. (b) Both are runtime leaves of the not-yet-landed action layer — no `Starship`, no `TurnManager` — so step 7 can build on a finished world surface without circular review pressure. (c) Both depend only on already-landed step-3 code (`GridPosition`, `GameObject`); reviewer cognitive load stays bounded.

This spec also surfaces and amends an inconsistency between the umbrella spec's Runtime DAG and SectorMap policy: `sector_map` is listed as runtime-importing `model.exceptions`, but the policy specifies `add(entity)` raises plain `ValueError` (not a model exception). Step 6 raises `ValueError` (research-grounded by the error-semantics section of [`docs/research/2026-05-23-python314-idioms-game-model-layer.md`](../research/2026-05-23-python314-idioms-game-model-layer.md)) and amends the Runtime DAG to drop the stale import.

#### `model/world/sector_map.py` specification

##### `SectorMap` class declaration

```python
from typing import TYPE_CHECKING

from stmrr.model.world.grid_position import GridPosition

if TYPE_CHECKING:
    from stmrr.model.entities.game_object import EntityId, GameObject


class SectorMap:
    """A bounded 3-D entity container indexed by EntityId.

    Owned by the wire-up layer (the SPEC-ML01 world-ownership contract), passed by reference into
    action methods (Starship.move_to, Starship.dock_at, TurnManager.advance_turn).
    Owns no game logic — it is the storage + spatial-bounds primitive.
    """

    def __init__(self, width: int, height: int, depth: int) -> None:
        ...
```

`SectorMap` is a **plain class, not a dataclass**: it carries a mutable `_entities` dict, the public dimension attributes are read-only by convention (not by enforcement — see Construction validation below), and it has no need for the `frozen`/`eq`/`order` machinery a dataclass would provide. Equality is identity (the default `object.__eq__`); two `SectorMap` instances with identical contents are not equal — they're different worlds.

##### Construction validation

`__init__(width, height, depth)`:

1. **Type check** (each axis, in order `width`, `height`, `depth`): `isinstance(value, int) and not isinstance(value, bool)`. On failure: `TypeError(f"{axis_name} must be int, got {type(value).__name__}")`. Same `bool`-is-an-int-subclass footgun mitigation as the SPEC-S003 GridPosition validation contract.
2. **Range check** (each axis): `value >= 1`. On failure: `ValueError(f"{axis_name} must be >= 1, got {value}")`. A 0-dimension sector is degenerate — every `bounds_check` returns `False` and every `add` raises. `DESIGN.md` section 4.3 caps dimensions at 20×20×7, but the lower bound `>= 1` is the only sanity check v0.1 enforces; the upper bound is a `SectorMap` _caller_ concern (config validation), not a `SectorMap` invariant.
3. Assign `self.width: int = width`, `self.height: int = height`, `self.depth: int = depth`, `self._entities: dict[EntityId, GameObject] = {}`.

Public attributes are conventionally read-only — no `@property` machinery, no `__setattr__` overrides. Mutation of `self.width` after construction is undefined behaviour; reviewers should not add tests for it.

##### Method contracts

| Method | Signature | Semantics | Complexity | Errors |
| --- | --- | --- | --- | --- |
| `bounds_check` | `(self, position: GridPosition) -> bool` | `True` iff `0 <= position.x < self.width` and same for `y < height` and `z < depth`. **Never raises** — predicate, not a guard. | O(1) | none |
| `add` | `(self, entity: GameObject) -> None` | Insert `entity` keyed by `entity.id`. See the `add` precondition order below. | O(1) | `ValueError` (see the `add` precondition order) |
| `remove` | `(self, entity_id: EntityId) -> None` | `del self._entities[entity_id]`. Mirrors `dict.__delitem__` semantics — strict, not idempotent. | O(1) | `KeyError` if `entity_id not in self._entities` (raised by `del`) |
| `get` | `(self, entity_id: EntityId) -> GameObject \| None` | `self._entities.get(entity_id)`. Returns `None` for missing IDs. | O(1) | none |
| `at` | `(self, position: GridPosition) -> list[GameObject]` | Linear scan; returns every entity whose `.position == position`, **including inactive** entities. Order matches dict insertion order (Python 3.7+ guarantee). Returns `[]`, never `None`. | O(n) over `len(self._entities)` | none |
| `entities` | `@property -> tuple[GameObject, ...]` | `tuple(self._entities.values())` — fresh snapshot, safe against concurrent mutation during iteration. Order matches dict insertion order. | O(n) | none |
| `__contains__` | `(self, entity_id: EntityId) -> bool` | `entity_id in self._entities`. Lets callers write `if some_id in sector:` instead of `if sector.get(some_id) is not None:`. | O(1) | none |
| `__len__` | `(self) -> int` | `len(self._entities)`. Lets callers write `len(sector)` for entity count without exposing the private dict. | O(1) | none |

###### `add` precondition order

Checks in this order; first failure raises and the dict is not mutated:

1. **Out-of-bounds:** `self.bounds_check(entity.position)` is `False` → `ValueError(f"entity position {entity.position} is outside sector bounds ({self.width}, {self.height}, {self.depth})")`.
2. **Duplicate ID:** `entity.id in self._entities` → `ValueError(f"entity id {entity.id} already present in sector")`.
3. Insert.

**Why `ValueError` for both, not `KeyError` for duplicate-ID and not `OutOfBoundsError` for out-of-bounds:**

- Per CPython convention (`Built-in Exceptions` docs, ["passing arguments with the wrong value"](https://docs.python.org/3/library/exceptions.html#ValueError)), `ValueError` signals "the value is wrong"; `KeyError` signals "a key being looked up was not found." The duplicate-add case is "this value (entity) is wrong for the current state" — it's not a failed lookup. The research error-semantics finding, corroborated across the Python docs + the `esper`/`tcod-ecs`/`mecs` ECS surveys, records `KeyError` on missing remove (lookup-style) and `ValueError` on wrong-shape add (value-style). The asymmetry is intentional.
- `OutOfBoundsError` (declared in step-5's `model/exceptions.py` as an `IllegalActionError` subclass) is specifically for **action preconditions** — `Starship.move_to`'s bounds check. `SectorMap.add` is a setup/spawn operation, not a player action; routing it through `IllegalActionError` would conflate setup failures with player-facing action failures in `except IllegalActionError:` blocks. Plain `ValueError` keeps the action-error namespace clean. This is the research-supported resolution to the SPEC-ML01 Runtime DAG inconsistency; see Cross-references and the umbrella amendment.

###### `at(position)` includes inactive entities

`at(position)` returns every entity at that position regardless of `active` state. Rationale: `at` is a spatial query primitive; callers know best whether they want to filter (`[e for e in sector.at(p) if e.active]` is one line at the call site). Filtering inside `at` would force every caller that _does_ want inactive entities (debug overlays, post-mortem queries, persistence dumps) to bypass it — and there is no analogous "include inactive" flag on `dict.values()` that this method mirrors.

The same applies to the `entities` property: every entity in the dict is returned, inactive or not. `GameObject.deactivate` is soft-delete under the SPEC-S003 lifecycle contract; `SectorMap.remove(entity_id)` is the hard-delete primitive. The two are not the same operation, and `at`/`entities` reflect the dict state, not a filtered view of it.

##### Iteration and snapshot semantics

`SectorMap` does **not** implement `__iter__`. Callers iterate via `for e in sector.entities:` (snapshot tuple, safe to mutate during iteration) or `for entity_id in sector._entities:` (private — single-purpose, mostly tests). Explicit:

- **No `__iter__` on the public surface.** A hypothetical `for e in sector:` is ambiguous between "iterate by ID key" (dict behaviour) and "iterate by entity value." Avoiding it forces the call site to be specific.
- **`entities` is a `tuple`, not a `frozenset`.** Order matters for the SPEC-ML01 deterministic-simulation invariant: given the same seed and action sequence, the simulation is deterministic. Dict insertion order is the determinism anchor; `frozenset` would lose it.

##### What's deliberately not on `SectorMap`

- **No spatial index.** `at(position)` is O(n); v0.1 entity counts make this fine. Adding a `dict[GridPosition, list[GameObject]]` shadow index doubles the storage cost and adds a mutation hazard (every `add`/`remove`/position-mutation must touch both structures). v0.2 picks this up if AI pathfinding profiles it as hot.
- **No `move(entity_id, new_position)` helper.** Position assignment is the action method's job (`Starship.move_to` writes `self.position = target` directly per the SPEC-ML01 Move action contract). A `SectorMap.move` would either (a) duplicate the bounds check action methods already do, or (b) skip it and become a footgun. Keeping the mutation responsibility on action methods is part of the SPEC-ML01 action-state ownership contract.
- **No event emission.** `SectorMap` is the storage primitive; events are the action layer's job. Mutation of `_entities` (via `add`/`remove`) does not emit. If v0.2 needs spawn/despawn events (e.g., for the bridge to track entity creation), the action layer adds them, not the container.
- **No `__hash__` override.** `SectorMap` inherits `object.__hash__` (identity-based). Putting a `SectorMap` in a set is a code smell (worlds are not values), but Python's default behaviour is fine.

##### `station_type` runtime validation + constructor order

`__init__` validates **both** `station_type` and `services` element types **before** calling `super().__init__(position)`. The full constructor body:

```python
def __init__(
    self,
    *,
    position: GridPosition,
    station_type: StationType,
    services: Iterable[str],
) -> None:
    # Validate BEFORE super().__init__() so failed construction does not
    # consume an EntityId from the module-global monotone counter
    # (Codex pass-1 SA-002; see "Why validate before super()" below).
    if station_type not in _V1_ALLOWED_STATION_TYPES:
        raise ValueError(
            f"station_type {station_type!r} is reserved for v0.2; "
            f"v0.1 supports only: {sorted(_V1_ALLOWED_STATION_TYPES)}"
        )

    # Reject string-shaped containers BEFORE freezing — `frozenset("repair")`
    # would silently produce a character set (Codex pass-2 SA-003).
    if isinstance(services, (str, bytes)):
        raise TypeError(
            f"services must be an iterable of str, not a bare "
            f"{type(services).__name__} (which iterates as individual "
            f"characters/bytes); pass a list/tuple/set/frozenset of str"
        )
    # Materialize ONCE — `services` may be a generator that can only be
    # iterated once, and we need to scan elements before frozenset().
    services_tuple = tuple(services)
    # Element-type check BEFORE frozenset() so unhashable non-str elements
    # raise the project's TypeError with a useful message, not the stdlib
    # generic `unhashable type: TYPE_NAME` from frozenset() (Codex pass-2 SA-003).
    bad_types = sorted({type(s).__name__ for s in services_tuple if not isinstance(s, str)})
    if bad_types:
        raise TypeError(
            f"services must contain only str elements; "
            f"got non-str types: {bad_types}"
        )

    super().__init__(position)  # ID allocation happens here
    self.station_type: StationType = station_type
    self.services: frozenset[str] = frozenset(services_tuple)
```

**Why validate before `super().__init__(position)` (Codex pass-1 SA-002):** `GameObject.__init__` calls the allocator function `_next_entity_id()`, which advances the mutable module-level `_entity_id_counter` regardless of whether the constructed instance is returned to the caller. If validation ran _after_ `super().__init__()` and then raised, the counter would have advanced but no entity would be bound to the consumed ID — silently introducing a gap in the otherwise contiguous-monotone sequence. v0.1 tests assert _relative_ ordering rather than absolute values under the SPEC-S003 identity-test convention, so a gap is invisible to those tests, but the SPEC-ML01 persistence-readiness contract and the v0.2 persistence + replay specs may rely on the contiguous-monotone property. Validate-first keeps the contract clean now rather than discovering the leakage during v0.2 spec work. The final preserved invariant below locks this behavior.

**Why `ValueError`, not a model exception:** constructor validation = `ValueError`, matching the SPEC-S003 GridPosition validation contract. No model exception class fits — `IllegalActionError` subclasses are for action preconditions on already-constructed entities; this is "the value you passed me to construct with is wrong for v0.1."

**Why `if station_type not in _V1_ALLOWED_STATION_TYPES`, not `if station_type == "starbase"`:**

Both work in v0.1 (set has one element). The membership form scales when v0.2 widens `_V1_ALLOWED_STATION_TYPES` — no code change to the guard. The equality form would force re-touching `__init__` for every v0.2 widening.

**Why NOT an exhaustive `if/elif` chain over `get_args(StationType)`:** strict static analysis narrows on `if x == "literal_value":` and treats the `else` as `Never` (the research wide-type/narrow-runtime section and its FastAPI footgun in a different form). When v0.2 widens `StationType`, the checker would flag the now-missing branches as a `return` violation — a useful safety property in some codebases, but here the _intent_ is "v0.1 rejects everything except the v0.1 subset; widening the Literal must NOT require touching this guard." The membership-test form preserves that intent; the if/elif form fights it.

##### `services` normalization + element-type validation

`services: Iterable[str]` accepts any iterable of strings; `__init__` performs **three** validation steps before freezing — the full code listing appears in Station runtime validation above:

1. **Reject string-shaped containers** (`isinstance(services, (str, bytes))` → `TypeError`). A bare `str` is technically `Iterable[str]` because iterating a string yields characters — `frozenset("repair")` produces `frozenset({'a', 'e', 'i', 'p', 'r'})` without complaint. The caller almost always meant "a station providing repair", not "a station with 5 single-char services." Same for `bytes`. Catching this at the door eliminates a silent-corruption footgun that bypasses every downstream check (Codex pass-2 SA-003).
2. **Materialize the iterable to a tuple** (`tuple(services)`). Generators can only be iterated once; if we element-check before freezing, the subsequent `frozenset()` would see an empty iterator. Tuple materialization is O(n) and lets us scan + freeze independently.
3. **Element-type check before `frozenset()`**. Computing `bad_types` over the tuple lets the project's `TypeError("services must contain only str elements; got non-str types: ...")` fire _before_ `frozenset()` would raise the stdlib's generic `TypeError: unhashable type: 'list'` for inputs like `services=[["repair"]]` — a useful-message-vs-generic-message reordering (Codex pass-2 SA-003).

Then `self.services: frozenset[str] = frozenset(services_tuple)`. Each step closes a footgun the prior one couldn't see.

**Iterable-and-normalize** is the dominant idiom across pydantic v2, attrs, and stdlib dataclasses (the research iterable-normalization section). The TOML load path returns `list[str]`, so requiring `frozenset[str]` strictly would force every load-time call site to wrap. The normalization is one operation; the type is locked as `frozenset[str]` post-init (immutable, hashable, TOML-round-trippable per the SPEC-ML01 persistence-readiness contract).

**Element-type runtime validation (Codex pass-1 SA-003):** BasedPyright strict catches typed callers that pass non-`str` elements, but `frozenset(["repair", 1])` happily produces a mixed frozenset under untyped callers (test fixtures, future TOML load paths, reflection). Worse, v0.2 save serialization will canonicalize via `sorted(self.services)`, and `sorted()` raises `TypeError` on heterogeneous types in Python 3 — a v0.2 time-bomb planted in v0.1 construction. The `isinstance` check seals it now. Same defensive pattern as SPEC-S003 FR-001/FR-002 validation on `GridPosition` axes (the checker catches typed callers while runtime guards protect untyped input). All three steps live in the preserved Station validation pipeline so they run _before_ `super().__init__()` for the same EntityId-non-consumption reason.

**No other validation on the elements.** Empty strings, whitespace, duplicates, unicode (any `str` subclass that isn't blocked by `isinstance(s, str)`) — all accepted. v0.1 has no service registry to validate against; v0.2 may add one when stations expose actual services. Cost of deferring: a typo in a service name silently becomes a unique service. Acceptable for v0.1.

**`bytes` is rejected at both levels.** A `bytes` _argument_ is the str/bytes rejection in step 1 above. A `bytes` _element_ inside an iterable — `services=[b"repair"]` — is rejected by the element-type check in step 3 because `bytes` is not a `str` subclass. TOML has no native bytes type, so neither rejection is gratuitous; both prevent the v0.2 persistence layer from inheriting a hidden mixed-type contract.

**Order is lost.** `frozenset` discards insertion order. Tests must not assert on order — they assert on set equality. Save serialization will canonicalize via `sorted(self.services)` per the SPEC-ML01 persistence-readiness contract; this is the persistence spec's concern.

##### `accepts_dock(ship)` semantics

```python
def accepts_dock(self, ship: _Dockable) -> bool:
    """v0.1: returns ship.active. v0.2 will extend with faction/reputation
    gating per the SPEC-ML01 Dock action contract; the predicate shape is locked now so v0.2
    additions are conjunctive (return ship.active and faction_ok(ship))."""
    return ship.active
```

**Why `return ship.active`, not `return True`:** the SPEC-ML01 module surface and Dock action contract say "v0.1 always returns True for any active Starship." Reading this literally: _active_ is the precondition, and the predicate must return `False` for an inactive ship. Returning `ship.active` directly is the cleanest expression: it makes the v0.2 extension purely conjunctive (`return ship.active and faction_ok(ship)`) instead of requiring a refactor. Defensive value also: `accepts_dock` is callable outside the `Starship.dock_at` precondition chain (UI tooltips, debug overlays, future query APIs) where the caller has not pre-checked `ship.active`.

**Why `ship: _Dockable` (Protocol) and not `ship: Starship`:** the umbrella Dock action contract originally said `accepts_dock(ship: Starship)`, but Step 7's `Starship` did not yet exist as a Python module. A `TYPE_CHECKING` import of a not-yet-existing module fails under BasedPyright strict because the checker resolves guarded imports during static analysis. `_Dockable: Protocol` captures the actual structural contract — any object with `active: bool` qualifies — and Step 7's `Starship` satisfies it through `GameObject.active` inheritance. The Protocol is a more honest contract because the predicate depends only on `active`, not on Starship-specific attributes.

**Why `ship: _Dockable` and not `ship: GameObject`:** `_Dockable` is the _minimum_ contract this method requires; `GameObject` is broader (carries `id`, `position`, `deactivate()`) than necessary. Using the narrower Protocol documents intent — any future GameObject subclass with `active` (whether or not it's a Starship) can dock against the predicate, but the contract is tied to the actual surface used. Step 7 may optionally tighten back to `Starship` once available; the current Protocol stays valid either way.

##### What's deliberately not on `Station`

- **No `dock(ship)` method that mutates state.** `accepts_dock` is a predicate; the actual dock action lives on `Starship.dock_at(station_id, sector_map)` (step 7, per the SPEC-ML01 Dock action contract). Mutating `Station` state on dock would couple step 6 to step 7 and create a back-edge in the runtime DAG.
- **No service registry validation.** See the services-normalization contract above; registry validation is a v0.2 concern.
- **No `Faction` field, no shield/weapon/sensor systems, no hull/health.** The SPEC-ML01 module surface explicitly excludes these from v0.1 (v0.2 per `DESIGN.md` section 10.1).
- **No `__eq__` override.** Inherits the identity-based `GameObject.__eq__` contract from SPEC-S003. Two `Station` instances at the same position with identical `station_type` and `services` are not equal — they're different stations.

#### Invariants

Properties the rest of the model layer relies on; reviewer should probe these.

1. `SectorMap.__init__` rejects `width`/`height`/`depth` that are not `int`, are `bool`, or are `< 1`. No `SectorMap` instance reaches code with degenerate dimensions.
2. `SectorMap.bounds_check(position)` is a total function: returns `bool` for any `GridPosition` input, never raises.
3. `SectorMap.add(entity)` is atomic on failure — neither the out-of-bounds case nor the duplicate-ID case mutates `_entities`.
4. `SectorMap` raises `ValueError` on `add` failures (wrong-value semantics) and `KeyError` on `remove` of missing entity (wrong-key semantics, mirroring `dict.__delitem__`). Asymmetry is intentional per the research error-semantics section and the Python docs convention on `ValueError` vs `KeyError`.
5. `SectorMap.entities` returns a fresh snapshot tuple per access; iteration over the snapshot is safe under concurrent `add`/`remove`. Order matches dict insertion order (Python 3.7+ language guarantee).
6. `SectorMap.at(position)` and `SectorMap.entities` return entities regardless of `active` state. Soft-delete (`GameObject.deactivate`) and hard-delete (`SectorMap.remove`) are distinct operations; container queries reflect membership, not activation.
7. `Station.kind` is the class-level string `"station"` for every `Station` instance — the TOML save-format discriminator per the SPEC-ML01 persistence-readiness contract.
8. `Station.__init__` rejects every `StationType` value not in `_V1_ALLOWED_STATION_TYPES` at runtime, regardless of which v0.1 callers pass it. The `StationType` annotation is intentionally wider than the v0.1 runtime contract — forward-compatibility for the v0.2 persistence layer per the SPEC-ML01 module surface.
9. `Station.services` is a `frozenset[str]` post-init regardless of the input iterable's concrete type. Element types are enforced at construction time: a `services` iterable containing any non-`str` element raises `TypeError` before `super().__init__()` runs (SA-003). Hash-stable, TOML-round-trippable per the SPEC-ML01 persistence-readiness contract because no non-`str` element can ever survive construction.
10. `Station.accepts_dock(ship)` returns `False` for any ship with `ship.active == False`. v0.2 extension is purely conjunctive (`return ship.active and faction_ok(ship)`) — predicate shape is locked.
11. `SectorMap` and `Station` import **nothing** from `entities.starship` or `combat.turn_manager` — neither at runtime nor under `TYPE_CHECKING`. Step 6 modules pass `uv run basedpyright` and `uv run lint-imports` without those dependencies. The `accepts_dock` parameter type is `_Dockable: Protocol`, not `Starship`. This is stronger than the original "runtime leaves" wording: a guarded import of a missing module still breaks strict static analysis, so Step 6 avoids the dependency in every sense.
12. `Station.__init__` validates all arguments BEFORE calling `super().__init__(position)`. Failed construction (`ValueError` on `station_type`, `TypeError` on non-`str` `services` element) does NOT consume an `EntityId`: `GameObject.__init__()` allocates through `_next_entity_id()`, and the validation path leaves mutable `_entity_id_counter` unchanged (Codex pass-1 SA-002). The contiguous-monotone property of the SPEC-S003 allocator remains intact even when invalid Station construction is attempted. This preserves the SPEC-ML01 persistence-readiness contract and the v0.2 persistence/replay specs' likely dependency on contiguous IDs.

#### Open questions for review

##### Locked decisions

- **Two-module scope, one PR.** Both modules are runtime leaves of step 7 (`Starship`, `TurnManager`); landing them together unblocks step 7 without forcing step 7 to pick which container/dock-target conventions to use under review pressure. Stations need a container to live in; the container's `add` semantics inform what action methods later expect.
- **`SectorMap.add` raises `ValueError` on both out-of-bounds and duplicate-ID; `remove` raises `KeyError` on missing entity.** The research error-semantics section and Python `ValueError` vs `KeyError` convention support the asymmetry; each exception communicates the actual failure type. `OutOfBoundsError` (declared in step-5 `model/exceptions.py`) is reserved for _action preconditions_ (`Starship.move_to`'s bounds check), not setup operations.
- **`SectorMap` does not import `model.exceptions` at runtime.** Resolves the stale SPEC-ML01 Runtime DAG claim; see Cross-references and the umbrella amendment. Plain builtin `ValueError`/`KeyError` cover every error condition step-6 introduces.
- **`SectorMap.at` and `entities` include inactive entities.** Container queries reflect dict membership, not activation. Filtering belongs at the call site.
- **`SectorMap` exposes no `__iter__`.** Ambiguous (key vs value iteration); callers use `entities` or `_entities` explicitly. `__contains__` and `__len__` are unambiguous so they are exposed.
- **`StationType: TypeAlias = Literal["starbase", "civilian", "military", "neutral"]` (NOT PEP 695 `type StationType = Literal[...]`).** PEP 695 syntax wraps the Literal in a `TypeAliasType` and breaks `typing.get_args(StationType)` (returns the TypeAliasType args, not the Literal args). This is the research TypeAlias footgun.
- **v0.1 runtime restriction enforced by `_V1_ALLOWED_STATION_TYPES: frozenset[str]` membership test, not by `if/elif` chain.** Membership testing does not narrow under the current strict checker; widening `_V1_ALLOWED_STATION_TYPES` in v0.2 requires zero guard-code changes. An exhaustive literal branch chain would force every widening to touch the guard. This follows the research wide-type/narrow-runtime section.
- **`Station.__init__` rejects v0.2-reserved `station_type` values with plain `ValueError`, not a model exception.** Constructor validation = `ValueError`, matching the SPEC-S003 GridPosition validation contract. No `IllegalActionError` subclass applies — `IllegalActionError` is for action preconditions on already-constructed entities.
- **`Station.services` accepts `Iterable[str]`, normalizes to `frozenset[str]` in `__init__`.** The research iterable-normalization section records this dominant pydantic/attrs/dataclasses idiom. TOML load path returns `list[str]`, so strict-`frozenset` typing would force every load-time call site to wrap.
- **`Station.accepts_dock(ship)` returns `ship.active` (not `True`).** Inactive ships cannot dock. v0.2 extension is conjunctive (`return ship.active and faction_ok(ship)`); the predicate shape is locked now.
- **`Station.accepts_dock`'s parameter type is `_Dockable: Protocol` (defined inline in `station.py`), not `Starship`.** Codex pass-1 (SA-001) flagged that the originally drafted `TYPE_CHECKING` import of `entities.starship` would fail strict static analysis because guarded imports are still resolved and Step 7's module did not yet exist. `_Dockable` requires only `active: bool`, the actual surface read by `accepts_dock`; Step 7's `Starship` satisfies it through `GameObject.active`. Alternatives considered and rejected: (a) `ship: GameObject` — too broad; (b) a minimal Starship stub — scope creep; (c) an ignored missing import — hides a real dependency error. **Step 7 inherits `_Dockable` unchanged**; tightening requires an explicit later amendment supported by a Starship-specific need. This closes the ambiguity finding about protocol permanence.
- **Keyword-only `__init__` on `Station`** (leading `*` after `self`). Matches step-5 exception kwarg-only pattern. Forces call sites to name the literal-typed `station_type` argument.
- **`SectorMap` is a plain class, not a dataclass.** Mutable `_entities` dict, identity equality, no need for `frozen`/`eq`/`order` machinery. Equivalent to the SPEC-S003 choice for `GameObject`.

| ERR-001 | A dimension is ill-typed or below one. | Construction raises the approved `TypeError` or `ValueError`; no map exists. | Constructor tests capture every axis and branch. | Correct the caller or configuration value and construct again. |
| ERR-002 | An add target is out of bounds or duplicates an ID. | `add()` raises `ValueError` in the locked order without mutation. | Focused atomicity and dual-failure tests capture the branch. | Correct the position or identity before retrying. |
| ERR-003 | A removal ID is absent. | `remove()` raises `KeyError`. | Missing-removal test captures strict deletion. | Resolve membership before retrying or treat absence explicitly. |
| ERR-004 | Station type or services are invalid. | Construction raises the approved `ValueError` or Station-specific `TypeError` before identity allocation. | Validation and counter-preservation tests capture the result. | Correct the input and construct again. |

### 12.2 Retry and Idempotency

`bounds_check()`, `get()`, `at()`, containment, length, and snapshot access are repeatable reads. A failed `add()` is safe to retry after correction because it does not mutate. A successful `add()` is intentionally not idempotent; repeating it raises duplicate-ID `ValueError`. `remove()` is intentionally strict rather than idempotent.

### 12.3 Rollback / Recovery

The only mutable durable-in-process state is sector membership. Validation and add failures occur before mutation, so rollback is unnecessary. After a successful add or remove, callers recover by applying the inverse operation with a valid entity or ID.
