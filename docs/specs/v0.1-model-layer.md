## 1. Purpose & Background

The model layer is the headless game simulation: entities, geometry, turns, action points, state transitions, errors, and events. It is authoritative for game state while the controller is the single seam to the Qt view. This umbrella fixes the cross-module behavior required by the v0.1 vertical slice and prevents later module specifications from making incompatible local choices.

## 2. Scope

### 2.1 In Scope

- Three-dimensional coordinates and lifetime entity identity.
- Sector storage and lookup, the player `Starship`, the starbase `Station`, and turn orchestration.
- Model exceptions, four typed events, the two-state game-state lifecycle, and the three v0.1 actions.
- Cross-module import direction, deterministic behavior, persistence-ready shapes, and headless verification.

## 8. Architecture and Design

### 8.1 Architecture Summary

The model is a Qt-free in-process graph of small modules. Runtime leaves provide coordinates, errors, events, and state classes; entities and containers build above them; action owners mutate their own state and emit after mutation. The application creates the world, manager, bridge, and view. Annotation-only imports break potential package-initialization cycles without changing runtime behavior.

### 8.2 Architecture Views

#### 8.2.1 Context View

Application wire-up supplies world and manager objects to model actions and the controller bridge. The bridge receives model events and is the only route to Qt views.

#### 8.2.2 Container / Deployment View

All model modules run in the local Python desktop process and independently in headless pytest processes. There is no model service or datastore in v0.1.

#### 8.2.3 Component View

| Component | Responsibility | Interfaces | Notes |
| --- | --- | --- | --- |
| Foundation | Coordinates, IDs, entity lifecycle. | SPEC-S003 public types. | Qt-free. |
| World/entities | Sector storage, Station, Starship. | Lookup and action methods. | Cross-references by ID. |
| Turns/state | AP restoration and state lifecycle. | `TurnManager`, `GameStateManager`, concrete states. | Ordered synchronous effects. |
| Events/errors | Change notification and typed failure taxonomy. | Four signals/payloads; `ModelError` hierarchy. | Runtime leaves except blinker. |

### 8.3 Design Decisions

| ID | Decision | Rationale | Alternatives Considered | ADR |
| --- | --- | --- | --- | --- |
| D-001 | Keep the model entirely Qt-free and use one controller bridge. | Headless simulation and one auditable seam. | QObject model classes were rejected. | ADR-0003 |
| D-002 | Use ID-based cross-module references and persistence-ready plain data. | TOML save/load can map the graph without serializing object cycles. | Stored object references were rejected. | ADR-0004 |
| D-003 | Use a hand-rolled instance-based state machine. | The small graph and explicit lifecycle do not justify a framework. | `QStateMachine` and `transitions` were rejected. | ADR-0005 |
| D-004 | Keep AP on `Starship`, not `TurnManager`. | The entity owns its mutable action budget; the manager owns sequencing. | Manager-owned debit was rejected. | — |
| D-005 | Use synchronous typed blinker events with undefined receiver order. | v0.1 needs simple immediate delivery and one safe bridge subscriber. | Queued delivery and raw kwargs were deferred/rejected. | — |

> **§8.4 (Solution Alternatives Considered) is Full-tier** and is intentionally omitted at the Standard profile.

### 8.5 Design Constraints

- Mutate before emit; state transition order is exit, mutate, enter, emit.
- Model modules perform no file I/O and store no Qt object.
- Runtime and annotation-only dependency edges remain as documented.
- Mutable private state uses snake_case; uppercase names are constants.
- A state-machine library reassessment trigger is above approximately 15 states or unwieldy callbacks, not the approximately seven-state planning baseline.

> **§8.6 (Dependency Policy) is Full-tier** and is intentionally omitted at the Standard profile.

## 10. Behavior and Workflows

### 10.1 Primary Workflow

1. Application wire-up constructs the world, player, Station, state manager, turn manager, and bridge.
2. A controller calls one approved model action.
3. The action validates all preconditions without mutation.
4. The owner performs effects in the documented order.
5. The owner sends the typed event after mutation; the bridge forwards it to Qt.

### 10.2 Alternate Workflows

| ID | Trigger | Behavior | Expected Result |
| --- | --- | --- | --- |
| AW-001 | End Turn resolves an inactive `Starship`. | Restore AP, increment, and emit normally. | End Turn remains always available. |
| AW-002 | A state transition is unsupported, self-directed, or same-instance. | Raise `IllegalTransitionError` before exit or mutation. | Current state and event stream remain unchanged. |
| AW-003 | A model-event receiver raises. | The synchronous exception propagates after the already-completed mutation. | Caller sees the failure; no rollback is attempted in v0.1. |

### 10.3 Edge Cases

| ID | Edge Case | Expected Behavior |
| --- | --- | --- |
| EC-001 | Failed Station or Starship validation. | Raise before consuming an EntityId. |
| EC-002 | Sector add is both out of bounds and duplicate. | Bounds failure wins and storage is unchanged. |
| EC-003 | A transition `enter()` hook raises. | New state remains current, no event is emitted, and no rollback occurs. |
| EC-004 | A model event has multiple receivers. | Each receiver is independent; no ordering assumption is permitted. |

### 10.4 State Transitions

| State | Meaning | Entry Condition | Exit Condition |
| --- | --- | --- | --- |
| `MainMenuState` | Menu lifecycle is active. | Initial construction or valid transition from sector map. | Valid transition to `SectorMapState`. |
| `SectorMapState` | Sector-map lifecycle is active. | Valid transition from main menu. | Valid transition to `MainMenuState`. |

#### Layering and the Qt-free rule

ADR-0003 ([`docs/adr/0003-model-qt-free.md`](../adr/0003-model-qt-free.md)): _"`src/stmrr/model/` must not import `PySide6`, `shiboken6`, or any other Qt module."_ The rule is enforced mechanically by `import-linter`'s `model-is-qt-free` contract in `.importlinter`, run on every CI push and pre-commit. A secondary contract (`view-does-not-import-model-events`) forbids the view from subscribing to model events directly — the only path is through `controller/model_bridge.py`. `DESIGN.md` section 9.1 calls this the _"single seam"_.

Python 3.14-native annotation semantics apply; a blanket future import is not required. Public APIs and tests require complete type hints that pass BasedPyright strict (`DESIGN.md` section 10.6). Naming follows that coding-standard section: `PascalCase` classes, `snake_case` functions, `UPPER_SNAKE_CASE` constants, and **`snake_case` past-tense events** (`ship_moved`, `turn_advanced`) so bridge translation is mechanical.

#### Cross-cutting concerns

##### Entity ID space

- IDs are `EntityId = NewType("EntityId", int)` minted by a module-level monotone generator in `model/entities/game_object.py` per `SPEC-S003` FR-008. **v0.1 locks monotone `int`** through `SPEC-S003` D-002; UUID4 migration, if any, is a v0.2 persistence-spec concern.
- **Cross-module entity references are by ID, not by object reference.** `TurnManager` references the player as `player_id: EntityId`, not `player: Starship`. `SectorMap.get(id)` is the resolution mechanism.
- **Why ID-based references:** save/load (v0.2) must serialize a graph; object references would force the deserializer to fix up arbitrary cycles, while IDs round-trip through TOML as plain integers and re-resolve at load time via `SectorMap.get`. `DESIGN.md` section 9.5 + ADR-0004.
- **Cost:** code that wants to act on an entity does an `O(1)` dict lookup. Acceptable; small entity counts (per `DESIGN.md` section 9.4).

##### Event vocabulary

- Names are `snake_case` past-tense, matching Qt's `Signal` convention so `controller/model_bridge.py` can rename mechanically (`DESIGN.md` section 10.6).
- **Payload shape:** `blinker.signal(...).send(sender, payload=Payload(...))`. The first positional argument to `send` is the `sender`; the single `payload` kwarg carries a frozen dataclass declared in `model/events.py`. The `sender` value is part of the event contract — subscribers can filter by sender, and bridge tests assert on it. Frozen dataclass payloads (vs. raw `**kwargs`) provide strict structural typing at the codebase's highest-risk seam — the bridge, the only place model and Qt meet — at the cost of one type per event. Four payloads in v0.1; landing them now spares v0.2's event explosion a migration.
- **Delivery is synchronous for v0.1:** each `send()` call invokes every connected receiver before returning. Queued delivery is a v0.2 problem if combat needs it.
- **Receiver invocation order is undefined.** Blinker calls receivers in connection order in current implementations, but its API does not document this as a contract; receivers **must** be order-independent — no receiver may rely on another running first or last. The `controller/model_bridge.py` is the single subscriber per event in v0.1, which makes the constraint trivial to satisfy; v0.2 must continue to honor it.

| Event | `sender` | Payload type | Emitted by |
| --- | --- | --- | --- |
| `ship_moved` | the `Starship` instance that moved | `ShipMovedPayload(ship_id: EntityId, from_position: GridPosition, to_position: GridPosition)` | `Starship.move_to` |
| `docked` | the `Starship` instance that docked | `DockedPayload(ship_id: EntityId, station_id: EntityId)` | `Starship.dock_at` |
| `turn_advanced` | the `TurnManager` instance | `TurnAdvancedPayload(turn_number: int)` | `TurnManager.advance_turn` |
| `state_changed` | the `GameStateManager` instance | `StateChangedPayload(from_state: type[GameState], to_state: type[GameState])` | `GameStateManager.transition_to` |

```python
# model/events.py
from dataclasses import dataclass
from typing import TYPE_CHECKING

from blinker import Namespace

if TYPE_CHECKING:
    from stmrr.model.entities.game_object import EntityId
    from stmrr.model.state.states import GameState
    from stmrr.model.world.grid_position import GridPosition


@dataclass(frozen=True, slots=True)
class ShipMovedPayload:
    ship_id: EntityId
    from_position: GridPosition
    to_position: GridPosition


@dataclass(frozen=True, slots=True)
class DockedPayload:
    ship_id: EntityId
    station_id: EntityId


@dataclass(frozen=True, slots=True)
class TurnAdvancedPayload:
    turn_number: int


@dataclass(frozen=True, slots=True)
class StateChangedPayload:
    from_state: type[GameState]
    to_state: type[GameState]


_stmrr_events = Namespace()

ship_moved = _stmrr_events.signal("ship_moved")
"""Sender: Starship. Payload: ShipMovedPayload."""

docked = _stmrr_events.signal("docked")
"""Sender: Starship. Payload: DockedPayload."""

turn_advanced = _stmrr_events.signal("turn_advanced")
"""Sender: TurnManager. Payload: TurnAdvancedPayload."""

state_changed = _stmrr_events.signal("state_changed")
"""Sender: GameStateManager. Payload: StateChangedPayload."""
```

- **Where events and payloads are declared:** `model/events.py` only. No module-local signals; no payload classes outside `events.py`. Enforced by the three layers required by `SPEC-S005` FR-008: (1) `.importlinter` `blinker-only-in-events` forbidden contract on direct `blinker` imports, (2) `.signal(` regex grep over model source, (3) `*Payload` class-declaration regex grep over model source. The blinker `Namespace` instance is named `_stmrr_events` (leading underscore = internal); subscribers import named signals only.
- **`events.py` stays a runtime leaf.** Payload field types are imported under `TYPE_CHECKING` only. Python 3.14-native deferred annotation evaluation does not resolve those names at class-definition time, so `@dataclass` adds no runtime import edge. This preserves the runtime DAG documented below.
- **Deferred-annotation footgun — runtime type introspection.** `typing.get_type_hints()` outcomes vary per payload depending on whether field types resolve at runtime:

  | Payload               | `get_type_hints()` outcome                           |
  | --------------------- | ---------------------------------------------------- |
  | `ShipMovedPayload`    | raises `NameError` (refs `EntityId`, `GridPosition`) |
  | `DockedPayload`       | raises `NameError` (refs `EntityId`)                 |
  | `StateChangedPayload` | raises `NameError` (refs `GameState`)                |
  | `TurnAdvancedPayload` | succeeds; returns `{'turn_number': int}`             |

  The three TYPE_CHECKING-only-ref payloads cannot have their annotations resolved at runtime; `TurnAdvancedPayload`'s `int` field is always in scope. Direct attribute access (`payload.ship_id`) is safe across all four, and the v0.1 bridge uses plain attribute access. If a future caller needs resolved hints, expose a typed accessor in the bridge; for unresolved safe inspection, use `annotationlib.get_annotations()` with a non-evaluating format.

##### State machine contract

Per ADR-0005 ([`docs/adr/0005-hand-rolled-state-machine.md`](../adr/0005-hand-rolled-state-machine.md)) — hand-rolled, ~200 lines, no `transitions` library, no `QStateMachine`.

`GameStateManager.transition_to(target_state)` semantics:

1. Validate that `type(target_state)` is in `current_state.allowed_transitions`. If not, raise `IllegalTransitionError` (declared in `model/exceptions.py`, peer to `IllegalActionError` per FR-016) with both states named.
2. Call `current_state.exit()`.
3. Update `current_state` reference to `target_state`.
4. Call `target_state.enter()`.
5. Emit `state_changed(from_state=…, to_state=…)`.

The order matters: `exit()` before mutation, `enter()` before emission. Subscribers reading `manager.current_state` inside a `state_changed` handler see the new state. Mutating before exit, or emitting before enter, breaks observer semantics in subtle ways under v0.2's combat ↔ sector transitions.

`GameState` ABC: `enter()`, `exit()`, `allowed_transitions: frozenset[type[GameState]]`. Concrete v0.1 states: `MainMenuState` allows transition to `SectorMapState`; `SectorMapState` allows transition to `MainMenuState`. The full state set lands as features arrive.

##### Time, turns, AP — single source of truth

**AP lives on the entity, not on the `TurnManager`.** `Starship` owns:

```python
ap_remaining: int   # current pool, debited by actions
ap_max: int = 5     # cap, restored on turn advance, modifiable later by difficulty mode
```

`TurnManager` owns the turn counter and orchestrates restoration; it has no `debit_player_ap` method. Collaboration:

1. **Action side:** `Starship.move_to` and `Starship.dock_at` debit `self.ap_remaining` via an internal `_debit_ap(cost)` helper that raises `InsufficientAPError` if short. FR-006 and FR-007 define the action contracts.
2. **Turn-advance side:** `TurnManager.advance_turn(sector_map)` resolves `sector_map.get(self.player_id)`, asserts the result is a `Starship` (the concrete runtime edge is documented in the Runtime DAG below), calls `player.restore_ap()`, increments `self.current_turn`, and emits `turn_advanced`.
3. **No reentrancy:** restoration completes before the event is emitted (`SPEC-ML01` FR-008).

`TurnManager` takes a single `player_id: EntityId` for v0.1; v0.2 generalizes when NPC ships join. Per `DESIGN.md` section 3.1, unused AP does not carry over; `restore_ap()` overwrites.

##### Save/load round-trip readiness

Out of scope to _implement_ in v0.1, but every entity must be shaped so the round-trip can land in v0.2 without breaking changes:

- **Plain-attribute state.** No closures, lambdas, generators, or live Qt objects. Attributes are primitives, a frozen dataclass (`GridPosition`), an `EntityId`, a `frozenset[str]`, or another `GameObject` reference _resolvable by ID_.
- **Subclass discriminator.** Every `GameObject` subclass declares `kind: ClassVar[str]` (`"starship"`, `"station"`). The persistence spec uses it as the TOML table tag for subclass dispatch on load. v0.1 lands the field even though no save code reads it yet, avoiding a save-format migration later.
- **Cross-entity references by `EntityId`** (`SPEC-ML01` C-003). Persistence serializes `dict[EntityId, GameObject]` as a TOML array keyed by `kind`+`id`; `EntityId` round-trips as a plain integer.
- **Set normalization.** `Station.services: frozenset[str]` serializes as a sorted list, deserializes back into a `frozenset`. Hash-stable, TOML-compatible (TOML has no native set). Lock now so v0.2 doesn't migrate from `set`.
- **No file I/O in the model** (`SPEC-ML01` FR-018).

ADR-0004 ([`docs/adr/0004-toml-not-pickle.md`](../adr/0004-toml-not-pickle.md)) bans `pickle` and `dill`.

##### v0.1 action contracts

The v0.1 vertical slice exercises three actions. Each names a single owner method, a precondition list, an ordered side-effect sequence, and the event it emits. `DESIGN.md` section 10.1 DoD items #5, #6, #7 are not satisfied until all three pass tests.

**Error types** (declared in `model/exceptions.py` and governed by FR-016): all action preconditions raise an `IllegalActionError` subclass (`InsufficientAPError`, `OutOfBoundsError`, `NotAdjacentError`, `InactiveEntityError`, `NotDockableError`). Subclasses let the controller produce precise error messages without inspecting a string `kind`.

###### Move

- **Owner:** `Starship.move_to(target: GridPosition, sector_map: SectorMap) -> None`
- **Preconditions** (checked in this order; first failure raises):
  1. `self.active` (else `InactiveEntityError`)
  2. `sector_map.bounds_check(target)` is `True` (else `OutOfBoundsError`)
  3. `self.position.is_adjacent(target)` is `True` (else `NotAdjacentError`) — v0.1 is single-cell moves only; multi-cell pathing is v0.2.
  4. `self.ap_remaining >= 1` (else `InsufficientAPError`) — v0.1 cost is fixed at 1 AP per cell. The Pythagorean-diagonal cost rule (`DESIGN.md` section 5.1) lands in v0.2 when movement extends beyond single-cell.
- **Effects** (ordered):
  1. Capture `from_position = self.position` (local, before mutation).
  2. `self.ap_remaining -= 1`.
  3. `self.position = target` — direct attribute assignment. There is no base `GameObject.move_to` to delegate to; `Starship.move_to` owns the action semantics end-to-end (precondition → AP debit → position assignment → event), and a base `move_to` with a different signature (`(self, position)` vs. `(self, target, sector_map)`) violates strict override compatibility. See `SPEC-S003` FR-013 and D-004.
  4. `ship_moved.send(self, payload=ShipMovedPayload(ship_id=self.id, from_position=from_position, to_position=target))`.

###### Dock

- **Owner:** `Starship.dock_at(station_id: EntityId, sector_map: SectorMap) -> None`
- **Preconditions** (in order):
  1. `self.active` (else `InactiveEntityError`).
  2. `target = sector_map.get(station_id)` is not `None` and `isinstance(target, Station)` and `target.active` (else `NotDockableError` — combined check; the controller doesn't care which sub-failure triggered it). The conflation of "stale ID" / "wrong type" / "destroyed" under one error is fine for v0.1; v0.2 may split it once the UI distinguishes "stale ID" vs. "wrong faction" vs. "destroyed" for player-facing messaging.
  3. `self.position.is_adjacent(target.position)` (else `NotAdjacentError`).
  4. `target.accepts_dock(self)` is `True` (else `NotDockableError`). v0.1 returns `ship.active` (i.e. `True` for any active dockable, `False` for any inactive one). The parameter is typed as `_Dockable: Protocol` (defined by the preserved `_Dockable` contract in [`v0.1-step-6-sector-map-and-station.md`](v0.1-step-6-sector-map-and-station.md)) rather than `Starship`, because Step 7's `Starship` module did not exist at Step 6 specification time and an annotation-only import of a missing module fails under strict static analysis. `Starship` satisfies `_Dockable` structurally via `GameObject.active` inheritance. The predicate is the v0.2 extension point for faction/reputation gating; widening adds attributes to `_Dockable`.
  5. `self.ap_remaining >= 1` (else `InsufficientAPError`).
- **Effects** (ordered):
  1. `self.ap_remaining -= 1`.
  2. `docked.send(self, payload=DockedPayload(ship_id=self.id, station_id=station_id))`.
- No state on the `Station` mutates. Service application (repair, resupply, mission briefing) is UI-side / mission-system-side in later versions; v0.1 only proves the action pipeline, per ADR-0011.

###### End Turn

- **Owner:** `TurnManager.advance_turn(sector_map: SectorMap) -> None`
- **Preconditions:** none — End Turn is always available.
- **Effects** (ordered):
  1. `player = sector_map.get(self.player_id)`. If `None` or not a `Starship`, raise `InactiveEntityError`. **This branch is unreachable in v0.1 by construction** — the player ship is added to `SectorMap` at session start and is never removed during a v0.1 session. The check lands now to harden against v0.2 persistence-layer foot-guns where a stale `player_id` could survive a save/load round-trip without its referent.
  2. `player.restore_ap()` — sets `player.ap_remaining = player.ap_max`.
  3. `self.current_turn += 1`.
  4. `turn_advanced.send(self, payload=TurnAdvancedPayload(turn_number=self.current_turn))`.

These three contracts are the v0.1 model's entire action surface. Any other "action" the UI offers in v0.1 (selection, camera pan, z-level switch) is view-side only.

##### `SectorMap.bounds_check` and `add` policy

**`bounds_check(position) -> bool`** returns `True` iff `0 <= position.x < self.width` and the same for `y < height` and `z < depth`. **Never raises** — it's a predicate, used in conditions.

**`add(entity)`** checks (1) `bounds_check(entity.position)` — raises `ValueError` if `False`; (2) `entity.id not in self._entities` — raises `ValueError` if already present. Checks in that order; first failure raises and the dict is not mutated. Duplicate-ID is `ValueError` rather than `KeyError` because the failure is a wrong-value condition ('this entity is wrong for the current sector state'), not a failed key lookup. See the preserved `SectorMap.add` contract in [`v0.1-step-6-sector-map-and-station.md`](v0.1-step-6-sector-map-and-station.md) and `docs/research/2026-05-23-python314-idioms-game-model-layer.md` section 3.

Predicate returns bool, mutator raises on contract violation — a stable pattern across the model layer.

##### World ownership lives at the wire-up layer

`SectorMap` instances are owned by `app.py` (or a session object outside the model layer), **not** by `GameStateManager` and **not** by any `GameState` subclass. `TurnManager.advance_turn(sector_map)` and `Starship.move_to(target, sector_map)` take the sector as a parameter precisely because the model layer does not own world construction; the wire-up layer does. `SectorMapState.enter()` is a state-machine hook for view/UI cueing, not a constructor — it does **not** instantiate `SectorMap`. Without this rule, `SectorMapState` accumulates world-construction logic and the model leaks lifecycle concerns into a state-machine hook, which v0.2 combat-vs-sector transitions then have to untangle.

#### Invariants for the model layer

1. No module under `stmrr.model.*` imports `PySide6` or `shiboken6`. Enforced by three layers: (a) `import-linter`'s `model-is-qt-free` contract — static parse-time check; (b) `tests/unit/model/test_no_qt_imports.py` — model-layer-wide subprocess-isolated runtime guard that imports every `stmrr.model.*` module via `pkgutil.walk_packages` and asserts `"PySide6" not in sys.modules` and `"shiboken6" not in sys.modules`. Catches imports executed at module-scope, class-body, decorator, or default-argument positions — not imports inside uncalled function bodies; (c) controller-layer integration tests (step 6+) exercise the action methods, which catches function-body Qt imports inside live code paths. AST-based function-body scanning is the v0.2 escalation if a regression slips through.
2. Every active entity is reachable from a `SectorMap` (live entities) or the `GameStateManager`'s active state (transitional). No orphan references; no dangling IDs.
3. Every model event fires _after_ the state mutation that justifies it, never before. Subscribers reading mutated state inside an event handler see the new value.
4. The blinker bus in `model/events.py` is the only allowed cross-module change-notification channel. Modules do not hold direct references to each other's mutable state for change notification.
5. All randomness in the model is seeded; given the same seed and input sequence, the simulation is deterministic. Required for replay tests, save/load fidelity, and AI determinism (`DESIGN.md` section 5.6).
6. Model code does not call `print` or stdlib `logging` directly; it uses `loguru`.
7. Model code performs no file I/O; persistence is the persistence layer's job.
8. Cross-module entity references are by `EntityId`, never by object reference. Local references inside a single method are fine.
9. State transitions follow exit → mutate → enter → emit. No exceptions.
10. `model/events.py` is the canonical declaration site for every signal and every payload dataclass in the model layer. Enforced by the three layers required by `SPEC-S005` FR-008: (a) `.importlinter` `blinker-only-in-events` forbidden contract — direct `blinker` imports forbidden outside `events.py`, with `allow_indirect_imports = True` so legitimate transitive paths like `entities.starship → events → blinker` are not flagged; (b) `tests/unit/model/test_invariant_10_enforcement.py` `.signal(` regex grep — no `.signal(` call exists in model source outside `events.py`, blocking the namespace-import escape route; (c) the same test's `*Payload` class-declaration regex grep — no `^class \w*Payload\b` declaration exists in model source outside `events.py`. The blinker `Namespace` instance is named `_stmrr_events` (leading underscore = internal).

#### Open questions for review

##### Locked decisions

- **Sync vs. queued events:** synchronous for v0.1 per FR-015 and the preserved Event vocabulary. Receiver order is undefined; receivers must be order-independent.
- **`EntityId` stability:** monotone `int` for v0.1 per `SPEC-S003` D-002. UUID migration, if any, is a v0.2 persistence-spec concern.
- **`GameStateManager` emission:** GSM emits `state_changed` directly via `model.events` per FR-011 and FR-014.
- **Entity authoring:** plain Python classes (mutable) for entity subclasses; `GridPosition` stays a frozen dataclass; pydantic schemas land at the persistence boundary, not on entities.
- **`SectorMap.bounds_check`:** returns `bool`, never raises; `SectorMap.add` raises `ValueError` on both branches of its precondition check — out-of-bounds (`entity.position` fails `bounds_check`) and duplicate-ID (`entity.id` already present); checks bounds first; first failure wins, no mutation. `SectorMap.remove` raises `KeyError` (mirrors `dict.__delitem__`). See FR-002 and the preserved Step 6 `SectorMap.add` contract.
- **`TurnManager` ↔ `Starship` coupling:** `combat/turn_manager.py` imports `Starship` at runtime and uses `isinstance` directly, as documented in the Runtime DAG. No `_starship_cls` injection, no `Protocol` indirection.
- **`GameStateManager` lifecycle:** constructed once in `app.py` and passed into the bridge. No singleton (couples tests); no module-level instance (awkward to swap in tests); no DI container in v0.1 (verbose for one consumer).
- **Typed event payloads:** frozen dataclasses (`ShipMovedPayload`, `DockedPayload`, `TurnAdvancedPayload`, `StateChangedPayload`) declared in `model/events.py`, passed via a single `payload=` kwarg. The bridge is the codebase's highest-risk seam (only place model and Qt meet); strong typing there is worth four small dataclasses in v0.1, and lands now so v0.2's event explosion does not have to migrate from raw kwargs.

##### Still open

1. **Replay-log integration: subscriber to model events, or a side-channel that records action invocations?** The first is decoupled but reconstructs state from events (lossy if events ever lack data); the second is precise but couples replay to every action method. v0.2 mission log + v1.0 replay both need this answered.

#### Risks and unknowns

- **State-mutation order.** Subscribers reading `manager.current_state` mid-handler may see the old reference if the `SPEC-ML01` FR-011 lifecycle (validate → exit → mutate → enter → emit) slips. Mitigation: FR-011 plus NFR-002's post-mutation event rule; bridge tests assert post-emit state.
- **`EntityId` migration when persistence lands.** v0.1 monotone `int` IDs reset on process restart, so v0.2 must choose between persisting the counter, switching to UUID4, or rebuilding ID maps at load time. The v0.2 persistence spec owns this decision; v0.1 keeps the door open through DR-001 and DR-002.
- **State-machine growth past ~7 states.** ADR-0005 already defines the off-ramp ("revisit `transitions` if state count exceeds ~15").
- **Accidental Qt dependency.** `import-linter` is in force as of the v0.1 scaffold; the residual risk is a Qt import that the static contract misses (e.g., a dynamic import pattern). `SPEC-ML01` C-001 and NFR-001 mitigate it through static `import-linter`, a subprocess-isolated runtime guard catching module-load-time imports (top-level + class body + decorator + default-argument scope), and controller-layer integration tests catching function-body imports inside live action paths. AST-based function-body scanning is the v0.2 escalation if a regression slips through.
- **Object references vs. IDs.** If `SectorMap` ever stores object references and the persistence layer later wants ID-based serialization, every entity needs auditing. Mitigation: `SPEC-ML01` C-003 and DR-001 require ID-based cross-module references from day one.
- **blinker receiver exceptions during synchronous emit.** `turn_advanced.send(...)` is the canonical v0.1 multi-subscriber dispatch point. Per blinker's documented contract, a receiver exception propagates out of `send()` immediately and skips subsequent receivers — while the model-state mutation (incremented `current_turn`, restored AP) is already committed. v0.1 has exactly one known-safe subscriber (controller bridge), so the failure mode is bounded. **`blinker.send_robust` does not exist** (PRs #3 and #27 in `pallets-eco/blinker` were proposed but never merged; spec must NOT reference it). v0.2 mitigation: implement a local `_send_robust(signal, sender, **kw)` utility iterating `signal.receivers_for(sender)` with per-receiver try-except, appending `(receiver, value-or-exception)` to a results list, logging caught exceptions at ERROR level via loguru. Trigger: second non-bridge subscriber lands.

## 12. Error Handling and Recovery

### 12.1 Expected Failures

| ID | Failure Mode | User/System Behavior | Logging / Observability | Recovery |
| --- | --- | --- | --- | --- |
| ERR-001 | Coordinate, entity, manager, or value-object construction receives an invalid type or value. | The documented `TypeError` or `ValueError` is raised before an invalid object becomes observable; Station and Starship failures do not consume an `EntityId`. | Focused constructor and validation tests pin type, message, and counter behavior. | Correct the caller input and retry construction. |
| ERR-002 | A Move, Dock, or End Turn precondition fails. | The first applicable `IllegalActionError` subtype is raised before action mutation, except that the defensive End Turn lookup failure occurs before restoration or increment. | Ordered action tests record the exact exception and unchanged state. | The controller reports the typed failure or changes the requested action; no automatic retry occurs. |
| ERR-003 | `SectorMap.add()` receives an out-of-bounds or duplicate-ID entity, or `remove()` receives a missing ID. | `add()` raises `ValueError` in bounds-before-duplicate order without mutation; `remove()` raises `KeyError`. | SectorMap error-order and no-mutation tests pin the behavior. | Correct the entity or ID and retry the container operation. |
| ERR-004 | A state transition is unsupported, self-directed, or same-instance. | `IllegalTransitionError` is raised before `exit()`, mutation, or event emission. | State-manager rejection tests capture current-state and event-stream stability. | Select an allowed target state. |
| ERR-005 | A state lifecycle hook raises. | An `exit()` failure leaves the old state current; an `enter()` failure leaves the new state current. Neither path emits `state_changed`, and the exception propagates. | Hook-failure tests distinguish the two commit points. | Caller handles the exception; v0.1 performs no rollback. |
| ERR-006 | A synchronous model-event receiver raises. | The receiver exception propagates after the model mutation has committed; remaining receivers are not guaranteed to run. | Event and integration tests expose the propagation boundary. | The caller handles the failure. A robust local dispatcher is deferred until the WH-004 trigger. |

### 12.2 Retry and Idempotency

Failed validation and precondition checks can be retried after caller input or state changes because they do not partially mutate their owner. `GameObject.deactivate()` is idempotent. Successful Move, Dock, End Turn, and state transitions are not retry-idempotent: repeating them intentionally performs another action or transition.

### 12.3 Rollback / Recovery

The v0.1 model has no transactional or persistent rollback layer. Validation, ordered preconditions, and mutate-before-emit sequencing prevent partial action mutation. The explicitly documented `enter()` and receiver-exception paths propagate after their commit point and do not roll back.

### 13.5 Threats and Mitigations

| Threat | Impact | Mitigation |
| --- | --- | --- |
